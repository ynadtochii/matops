# matops — project guide for Claude

**matops** is a multi-academy admin SaaS for grappling gyms: an **Expo** student app + a **Next.js** owner/instructor web app, one TypeScript monorepo. It is a from-scratch rebuild; the old app **MAT** (`/Users/kuna/projects/mat`) is reference only, never a base.

## Current state — Phases 0-4 done, every product wave through v6.7, the v7.2 organization/entity pivot, and v7.7

Everything through **v7.2** is built and static-gates green (`pnpm typecheck` 17/17 · `next build`). **`pnpm test` is green: 1620 tests across 130 files (checked 2026-09-06, run twice).** `@matops/domain` 721 · `@matops/api` 636 · `@matops/db` 215 · `@matops/validators` 45 · `@matops/notifications` 3. The nine over v7.7's 1611 are the PR #6 review fixes' regression tests. It had been red since v7.5/v7.6 (25 failures on `b237f03`); v7.7 fixed all of them. The big one was the api harness: `ctxFor` pinned `activeOrganizationId` to the id passed to `as()` and never read back what the fake `authApi` had activated, so any test that called `organization.create` and then used the gym it just made got "No active organization selected". It now falls back to the fake's session map, which is what Better Auth's session row does. The dummy `POSTGRES_URL` in `packages/api/vitest.config.ts` stays and is correct, since every base-connection helper takes a required `exec` and the tests inject PGlite as `baseDb`. **`pnpm lint` at the workspace root is green again, 15/15** (checked 2026-09-02 with both eslint caches cleared). The long-standing "type that could not be resolved" failure on `@matops/nextjs` and `@matops/expo` is gone; nothing in v7.2 targeted it, so if it returns, treat it as its own slice.

**The tenant model changed in v7.2 and this is the one that runs (ADR 124).** An **organization** is the owner group and keeps only a name, a slug and a logo. A typed **entity** is the place — the only type is `bjj_academy` — holding the name every screen shows, the time zone, country, address, map link and six-digit code, with its per-academy settings on `academy_profile`. **`entity_membership`** is the operational access record: one person can own one mat and train at another, and approve/suspend/archive/remove all act on one academy. Creating a gym makes one organization and one default entity whose **id equals the organization id**, through one idempotent `provisionOrganization`. **The session never picks the academy:** every request names it in the **`x-matops-entity`** header, from `/entities/[entityId]` on web and from secure-store in the app, so two tabs show two mats and a URL is shareable; a missing header is `BAD_REQUEST`, a foreign one `FORBIDDEN`, both before a transaction opens. **RLS stays exact:** `academy_id` and `app.academy_id` keep their names and hold an **entity** id, `app.organization_id` sits beside them, no BJJ table carries an `organization_id`, and `/overview` reads one entity at a time and combines on the server. Twelve `member_id` columns key on `entity_membership.id`, held by ten composite foreign keys. Read `docs/organization-entity-pivot.md` before touching tenancy.

## Run it

- `pnpm install`, then `pnpm dev:next` → **http://localhost:3004** (port 3000 is kept free on purpose). Sign in via the magic-link form; copy the `[auth] magic link …` URL from the terminal into the browser (no email provider needed — it prints to the terminal).
- **`pnpm dev:ios`** — one command to prepare + run the whole iOS stack: installs deps if needed, starts the web/API on 3004, then boots the Expo app in the iOS Simulator (Metro + dev-client build). Env-tolerant: missing email (Resend) / push (EAS) config just no-ops. `pnpm dev:ios "iPhone Air"` picks a simulator.
- `pnpm test` — `turbo run test` across every package that has a suite, **no database needed** (PGlite is embedded): RLS leak tests in `packages/db/test`, router tests in `packages/api/test` (real routers + real middleware over PGlite, ADR 60), pure rules in `packages/domain/test`, schema sanitization in `packages/validators/test`, and the notification transport.
- `pnpm -F @matops/db migrate` applies migrations to `POSTGRES_URL`, which on a laptop is always the **dev** database (see below); `pnpm -F @matops/db verify` checks any database it is pointed at (migration count vs `_journal.json`, the `matops_app` role, RLS + policy + four grants on every reachable table); `pnpm -F @matops/db seed:health` writes a probe row.
- **Demo data (ADR 51):** two modes.
  - **Fill your real academy (recommended):** `pnpm -F @matops/db seed fill <code>` adds ~20 fake students (+ memberships/bookings/attendance/ranks) around the real owner of the academy with that 6-digit code, using its **existing** plans + classes — your real data is never touched. A branch on shared memberships gets assignments and paid months; one still on branch dues gets dues rows. `seed clear <code>` removes only the fakes; `seed status <code>` counts them.
  - **The beta demo academy (ADR 51/65):** `seed up <your-email>` builds **one** isolated demo gym, **"Alma beta"** (`seed_org_alma`, code `990001`), with you as its owner - sign in once first. It runs on **shared memberships** (ADR 126-129), not on the legacy branch dues: access plans with a price history, an assignment per student, this month across paid / silent / reminded / claimed, a plan change waiting for the 1st, a manager who holds no branch membership, and one student with a claimed purchase to confirm. The seed writes **no curriculum blocks**, so that screen starts empty. `seed down` / `seed reset`. Also `pnpm db:seed` / `db:seed:down` / `db:seed:reset` from the root. To start from nothing, `psql "$POSTGRES_URL&sslrootcert=system" -f packages/db/src/seed/wipe-academies.sql` deletes **every** academy first (destructive, keeps real `user` rows).
- `.env` holds `POSTGRES_URL` (the Neon **dev** branch, pooled, `sslmode=verify-full`) + `DB_ENV=dev` + `AUTH_SECRET` (its own, never production's). **`CRON_SECRET`** is set in Vercel Production and as a GitHub Actions repository secret, and the two must match; locally it is optional and only guards the manually-callable `/api/cron/*` seams. Note: `.env.example` still shows a Supabase placeholder (it was permission-locked during scaffolding).

## Branching, databases and deploys (since 2026-09-01, real academies use this)

- **Work on `dev`. Merging `dev` into `main` IS the production deploy.** Never commit to `main` directly. Say plainly that a merge deploys, rather than treating it as a merge.
- **Two Neon branches in one project.** Local `.env` and Vercel **Preview** point at the `dev` branch (it holds the old test data: Alma beta, ~30 users, the fakes). Vercel **Production** points at the production branch, which was emptied and rebuilt from `0000`, holds only real academies, and **is still empty** (confirmed 2026-09-02: no organizations, no rows). Different host **and** password.
- **`.env` must carry `DB_ENV=dev`.** Without it `assertDevDatabase` (`packages/db/src/env-guard.ts`) makes every drizzle-kit command and the seed CLI refuse. That is the guard working. It is called from `drizzle.config.ts` and `assertSeedableTarget`; `ALLOW_PROD_WRITE=1` is the override.
- **Migrations reach production only through the deploy.** `apps/nextjs/package.json`'s `vercel-build` runs `@matops/db migrate:deploy` before the new deployment is promoted, so a failed migration blocks the deploy and the old one keeps serving. It no-ops unless `VERCEL_ENV=production`, takes an advisory lock, and asserts the applied row count against `_journal.json` — because `drizzle-kit` skips stale-`when` entries and still reports success. **Never run a migration against production from a laptop.**
- **A migration lands while the OLD code is still serving**, for the length of a build. Add columns and tables freely; drop one only in a later deploy, after the code that used it is gone.
- **Never use Neon's "Reset from parent" on `dev`** — the parent is empty now, so it would wipe dev. Rebuild dev data with `pnpm db:seed`.
- Runbook and rationale: [docs/beta-launch-plan.md](docs/beta-launch-plan.md) §1.1-1.3.

## Phase 0 gotchas (do not "fix" these)

- **`@matops/api` and `@matops/auth` are consumed from SOURCE** — `exports.types` point at `src`, tsconfig extends `base.json` (noEmit). The tRPC `AppRouter` embeds the full Better Auth `Auth` type, too large to serialize into a `.d.ts` (TS7056). Do NOT switch them back to `compiled-package.json`.
- **RLS needs `SET LOCAL ROLE matops_app` + a role grant.** The request tx sets that role and `app.academy_id`. Migration `0003` does `GRANT matops_app TO current_user` because a managed-Postgres connection role isn't a superuser — without it you get "permission denied to set role". PGlite (superuser) masks this.
- **Migrations are STRUCTURE ONLY.** Tables, columns, indexes, constraints, RLS policies, grants. **No `UPDATE`, no `INSERT`, no backfill.** A data fill goes in `packages/db/scripts/<date>-<name>.sql` and is run by hand (`psql "$POSTGRES_URL&sslrootcert=system" -f <file>`), because a migration runs everywhere forever while a fill is usually right once, on one database. Six migrations from before this rule (`0010`, `0029`, `0032`, `0034`, `0035`, `0037`) carry backfills; they are applied and append-only, so leave them.
- **Use `migrate`, not `db:push`.** The RLS role/policy live in hand-written migrations (`0001`, `0003`); `push` only diffs the schema file and skips them.
- **After `drizzle-kit generate`, fix the new entry's `when` in `_journal.json`.** Migrations from `0028` on were hand-stamped with round day boundaries that run **ahead** of the real clock, and `generate` stamps the real clock. `drizzle-kit migrate` skips any entry not newer than the last applied row **and still prints "migrations applied successfully"**, so a whole wave can look applied and be absent. Bump `when` one day past the previous entry, then re-run and check `select count(*) from drizzle.__drizzle_migrations`.
- **Tests:** RLS/DB behavior → PGlite in `packages/db/test`; router + middleware behavior → `packages/api/test` (PGlite injected as `ctx.baseDb`, ADR 60); pure logic → `packages/domain/test`; schemas → `packages/validators/test`. Each has its own `test/tsconfig.json` (keeps `build`/`typecheck` on `src`).

## Stack (locked — do not re-litigate; see docs/map.md)

- **Monorepo:** Turborepo + pnpm, `create-t3-turbo` layout. Package scope `@matops/*`.
- **API:** tRPC v11 colocated in Next.js (`packages/api`). Both clients consume the same router. Internal-only (no public REST).
- **Auth:** Better Auth + Organization plugin (org = academy, `academyId === organization.id`) + magic-link, plus **Google** when `GOOGLE_CLIENT_ID`/`SECRET` are set (ADR 35). Expo secure-store sessions.
- **DB:** Drizzle + Postgres (**Neon**). Driver = **`pg`** on the Neon **`-pooler`** endpoint (needed for the per-request RLS transaction — the HTTP driver can't do interactive tx).
- **Tenancy:** Postgres **RLS**, one **entity** per request (ADR 124). `withScope({ organizationId, entityId? })` sets `app.organization_id` and, when given, `app.academy_id` in one round trip; the entity policy is `USING (academy_id = current_setting('app.academy_id', true))` and `entity` / `entity_membership` match on `app.organization_id` instead. `academy_id` is **text** and holds an entity id (the default academy's equals the organization id), never cast to uuid. The client names the entity in `x-matops-entity`; the session never does.
- **Web:** Next.js App Router on Vercel + shadcn/ui + Tailwind. **Mobile:** Expo/React Native + NativeWind, via EAS. **State:** TanStack Query.
- **Notifications (Phase 4):** Expo Push, thin `packages/notifications`; the notification center is the durable copy. Resend carries the sign-in magic link only, and no gym message goes out by email (v3.8, ADR 77 amendment). No WebSocket/live-UI in v1 (polling; a worker comes later).
