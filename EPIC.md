# Epic: finish the organization and branch pivot

Loop file for `/epic`. One invocation does one unchecked item, then stops.

## Goal

Registration creates an organization only. The owner lands in the organization shell and creates the first branch there. The release also completes guided setup, shared membership pricing, bulk migration, manager permissions, type-aware product language, and product measurement.

Background and the reasoning behind each decision live in [PLAN.md](PLAN.md) and [docs/post-pivot-product-handoff.md](docs/post-pivot-product-handoff.md). Those two files are the source of decisions. This file is the source of loop state. Do not edit PLAN.md while working an item.

## Constraints

- Work on `dev`. **Never commit and never push.** Leave every change in the working tree.
- **Never run tests.** Write and update them, then put the focused command in `## Log` for the user to run.
- Run lint and typecheck on the packages you touched after each item.
- No comments on edits. See the repo rule in `CLAUDE.md`.
- Migrations are **structure only**. No `UPDATE`, no `INSERT`, no backfill. A data fill goes in `packages/db/scripts/<date>-<name>.sql` and is listed in `## Log` for the user to run by hand.
- After `drizzle-kit generate`, set the new entry's `when` in `_journal.json` one day past the previous entry, then run `pnpm -F @matops/db migrate` and check `select count(*) from drizzle.__drizzle_migrations`. `drizzle-kit` prints success while skipping a stale entry.
- Migrations for this epic start at **0060**. `0059` is reserved for the later `payment_settings.bank_details` drop. Do not reuse it.
- `.env` must carry `DB_ENV=dev`. Migrations reach the Neon **dev** branch only. Never migrate production from this machine.
- Manual acceptance, the Expo device checklist, the four-week design partner and the commercial commitment are **out of this epic**. They stay in PLAN.md as human work.
- If an item is blocked, mark it `- [!]`, write the reason in `## Log`, and move to the next item. If the same item fails twice, stop.

- **10.4 migration `0064`, one `product_event` table.** Columns: gym, branch, `kind`, `name`, `actor_role`, `occurred_at`. **No user id, no email, no phone, no amount**, so the table cannot become a second copy of the roster, and three checks hold the shape (the two enums, plus a name pattern).
- **Two kinds, because the questions differ.** A `milestone` happens once per gym or per branch, and a partial unique index on `(organization_id, name, coalesce(entity_id,''))` makes a second write a no-op, so "first booking" keeps the date it really happened. An `activity` row repeats, which is what a weekly count of gyms with real student use is made of.
- **The app role cannot reach it.** Migration `0001`'s default privileges would have granted all four to `matops_app`, so `0064` revokes them, and RLS is enabled with no policy, which denies every role but the table owner even if a grant appeared later. `matops_debug_ro` gets SELECT, since the rows carry nothing personal.
- `product_event` has an `entity_id`, so `erase-coverage.test.ts` demanded a decision: it is listed as **not member data**, because there is nothing in a row that belongs to a person. Journal idx 64, `when` 1790726400000. **Written, not applied.** The partial expression index cannot be expressed in drizzle, so it lives in the SQL alone. Files: the migration, `packages/db/src/product-event-schema.ts` (new), `schema.ts`, `erase-coverage.test.ts`; gates: `@matops/db` typecheck and lint clean.

- **10.5 eleven events, written from the procedures that already do the thing.** `recordMilestone` and `recordActivity` in `packages/db/src/product-event.ts` are the whole writer, plus `eventRole` which keeps a role string inside the five the check allows. Call sites: `organization.create` (organization_created), `entity.create` (first_branch / second_branch, from a live count), `template.create` and `class.create` (first_schedule), `membership` join (first_student), `booking.book` (first_booking + student_booking), `attendance.mark` and `markAll` (first_attendance + student_attendance), `accessPlan.create` (first_plan), `assign` and `assignMany` (first_assignment), `entity.setMembershipEnforced` (branch_activated).
- **The writer never throws.** A booking that worked is not a failure because its event did not land, so a failure is logged and swallowed, the same contract `packages/notifications` has.
- **Every write goes on the base connection, after the transaction commits.** `matops_app` has no grants on `product_event`, so an insert inside the request's scoped transaction would be refused; scoped procedures therefore use `ctx.afterCommit`, which hands back the base connection. An event for a rolled-back booking is impossible for the same reason.
- **Only a student's own act counts as student activity**: `booking.book` records nothing when a coach books their own training, so the weekly metric cannot be inflated by staff. Attendance records the act whoever marked it, since the person attending is a student either way, and `actor_role` says who marked.
- **Paid commitment has no procedure, because nothing here charges anybody.** `packages/db/scripts/2026-09-04-paid-commitment.sql` is the one hand-run write: it sets the offer, the agreed price and clears the pilot date, and inserts the `paid_commitment` milestone in the same transaction, so the funnel ends in money rather than clicks. Gates: `@matops/db` and `@matops/api` typecheck and lint clean.

- **10.6 the weekly report, as a function first and a command second.** `weeklyRetainedUse(since, exec)` in `packages/db/src/product-report.ts` groups `product_event` by Postgres week and answers one main number per week: **how many gyms had real student use**, counted only from `student_booking` and `student_attendance`. The booking-only and attendance-only counts sit beside it, so a gym that books and never marks attendance is visible rather than averaged away.
- **It takes `since` and the `exec` as arguments**, with `weeksBack(weeks, now)` as a separate pure function, so the query can be tested against PGlite with a fixed clock and no hidden `now()`.
- Built with the drizzle query builder rather than `execute(sql...)`, because the raw result shape differs between the `pg` driver and PGlite, and the tests run on PGlite. `pnpm -F @matops/db report [weeks]` prints it, default 12. Files: `product-report.ts`, `report-cli.ts` (new), `index.ts`, `package.json`; gates: `@matops/db` typecheck and lint clean.

- **10.7 the funnel, six numbers, all read from the same events.** `organizationMilestones` pivots `product_event` into one row per gym holding the first time of each milestone, and the pure `funnelSummary` turns those rows into how many gyms reached each step, **median days to first schedule** and **median days to first student booking**. Splitting the query from the arithmetic means the arithmetic tests with plain objects and no database.
- **Setup completion is derived, not recorded.** The setup checklist is computed on every read, so recording it would mean writing on a page load; a gym counts as set up when it has reached all five of first branch, first schedule, first student, first plan and first assignment.
- **Two-branch weekly use** is `weeklyTwoBranchUse`, a subquery counting distinct branches per gym per week and then the gyms with two or more, which a single flat aggregate cannot express. **Week-two student booking** is `weekTwoBookers`, joining each gym's creation time and counting the gyms with a student booking between day 7 and day 14, which is the honest read of "they came back".
- All of it prints from `pnpm -F @matops/db report`. Files: `product-report.ts`, `report-cli.ts`; gates: `@matops/db` typecheck and lint clean.

- **10.8 the counter-metric needed a signal that did not exist yet.** Milestones happen once, so they cannot say whether staff were busy *this week*. A `staff_action` activity row now goes beside the milestone at the five places staff already act: a template, a one-off class, marking attendance, creating a plan and assigning one. No new plumbing, the `afterCommit` blocks from 10.5 were already there.
- **`weeklyOwnerOnly(since, exec)` counts the weeks that should worry us**: gyms where `staff_action` happened and neither `student_booking` nor `student_attendance` did. That is an owner tidying a schedule nobody books, which reads as use in every other number and is the opposite of use.
- Marking attendance records both a student row and a staff row, which is right: the students trained and staff did the marking, so that week is not counted against us. The CLI prints only the weeks with a non-zero count, since a wall of zeros hides the one line that matters. Files: `product-report.ts`, `report-cli.ts`, and the four routers; gates: `@matops/db` and `@matops/api` typecheck and lint clean.
