# Drop-in booking implementation plan

## Goal

Give every first-time and returning drop-in one shared-link flow to book or attend a class without an account. Let staff see each visitor's level and training restrictions. Student registration uses the same academy questions but starts with blank answers.

## Context

The public `/checkin/<academyId>` form currently captures leads, checks visitors in to a live class, or books a nearby class. Staff can also create a visitor directly in Attendance. The Expo Scan tab and `checkin` router serve member QR check-in. These paths are replaced, not supplemented. `drop_in` and `drop_in_visit`, the owner lead list, and staff attendance marking remain.

## Decisions

- One public, rotatable drop-in link per academy. Owners and managers create or rotate it; instructors can read and share it. Staff and visitors use the same web form. Never accept an academy id or a lead id from the browser as authority; resolve the academy from the live token.
- The visitor sees only class title, local date, and time. Offer scheduled classes within seven local academy days, plus classes running now for attendance. A future booking stays `booked` and `unmarked`; choosing a class on now records `present`. No class selection means no lead submission. Do not show coach, capacity, roster, or member data. Soft capacity never refuses a visitor booking.
- Ask for email and phone first. After both fields lose focus or Continue is pressed, normalize them and look for one lead in this academy where **both** values match. Respond with only the matched first name, or the same no-match result for every mismatch. The visitor confirms "Are you {name}?" to skip the full form; No or no match opens the full form. The server rechecks both values on submit, does not trust a client lead id, and does not overwrite a returning lead's profile. A lead with missing email, absent contact consent, missing required answers, or an outdated required agreement uses the full form or accepts the current agreement before proceeding. No saved health or contact details return through lookup.
- Match plus confirmation is not proof of identity. A person who knows both contact values can book under the lead and see its first name; it never permits reading private answers, changing member data, or skipping authenticated registration. Rate-limit lookups across instances, not only in memory.
- The first-visit form and student registration read the same academy question settings and use the same field definitions, validation rules, agreement version checks, and news opt-in semantics. Extract the existing web training and agreement fields for both web forms. Expo invite and code join render the same questions with native controls backed by the same server rules. No generic form builder. Student registration always asks for answers anew, including after a drop-in visit.
- Drop-in answers stay on `drop_in`: belt choice/stripes, optional health text when enabled, email news choice, and accepted agreement version/time. Never write these directly to member rank, member notes, or member agreement acceptance. Staff may read health only for a booked visitor at their academy. Extend academy erase/export handling for these fields. Retain existing joined-lead history but remove `dropIn.promote` and the owner "Make them a member" control. Do not build conversion plumbing now.
- No new follow-up tracking. Keep the existing lead stages and manual Mark contacted action. Remove direct `attendance.addVisitor` and its roster form; an instructor registers someone through the link with the visitor present. Staff must not consent or agree on the visitor's behalf. Staff attendance corrections remain.
- Remove both QR check-in paths: the public `/checkin/<academyId>` form and member Scan tab, deep link, and `checkin` router. Keep regular member booking and staff attendance marking. Old posters and old mobile builds need a rollout notice and an overlap period before server removal.

## Implementation Steps

1. **Shared questions and pure rules.** In `packages/domain/src/signup.ts` and `packages/validators/src/fields.ts`, make student answers and their limits one reusable contract for invite join, code join, and first-time drop-in. Keep membership writes in `packages/db/src/signup.ts`; do not route visitor answers through it. Extract the web question fields from `apps/nextjs/src/app/join/[token]/join-flow.tsx` for use in both web forms. Continue to read the live `entity.signup_health_question` and required current `academy_waiver` rather than copying a question list into a new table.
2. **Additive data migration.** Extend `packages/db/src/scheduling.ts` and add an academy-scoped drop-in link schema/helper following `packages/db/src/invite.ts`. Store visit answers on `drop_in`, with bounded health text and current agreement version/time. Add academy-scoped indexes, foreign keys, RLS and grants for the lead data; keep the public link table on the base connection like `academy_invite`. Update `packages/db/src/erase.ts`, seed teardown, and export/privacy handling. Generate a new structure-only migration after `0008`; inspect `_journal.json` timestamps and verify the target ledger before deployment. Do not run a laptop migration on production.
3. **Public link contract.** In `packages/api/src/router/dropin.ts`, add staff link read/create/rotate, public resolve/classes, exact two-field lookup, and submit. Source comes from the server-side entry path, never client input. Validate the token on each lookup and submit; return only name on lookup and title/start on class reads. Use short client-side cache for class choices only; never cache lookup responses or authorize a submit from cached data. Extend `packages/validators/src/checkin.ts` or replace its obsolete QR schemas in place.
4. **Atomic booking.** Refactor `packages/db/src/dropin.ts` so a submission resolves token, lead match, class eligibility, and booking transition in a transaction. Lock the lead/visit as needed, count a newly booked visit exactly once, and recheck class state and seven-day window at write time. Remove the hard-cap predicate. Treat repeated and concurrent submits as one visit per lead and class. Preserve tenant pinning on every base-connection query. Show an actionable error if a class changed while the form was open.
5. **Web and staff UI.** Replace `apps/nextjs/src/app/checkin/[academyId]` with a token-addressed drop-in page using the existing form, unfolding contact match and full shared questions. Put link copy/rotate in the student invite area; instructors get copy access only. Extend `packages/api/src/attendance-review.ts`, `packages/api/src/router/attendance.ts`, and `apps/nextjs/src/app/_components/class-roster.tsx` to show class-specific level and training restrictions to staff. Keep the owner lead list in `apps/nextjs/src/app/_components/leads.tsx`, remove promotion, and show relevant answers there. Remove the direct Add visitor action and procedure.
6. **Registration clients.** Update `packages/api/src/router/membership.ts` and the code-join lookup contract so invite and code joins validate the live academy questions server-side. Use blank, newly submitted answers in web join, `apps/expo/src/app/join/[token].tsx`, and `apps/expo/src/app/onboarding.tsx`. Never prefill from a drop-in record. Update clients before making new questions mandatory for mobile calls.
7. **QR cutover and cleanup.** Remove `apps/expo/src/app/(tabs)/scan.tsx`, `apps/expo/src/app/checkin/[academyId].tsx`, the Scan tab, QR deep-link handlers, `packages/api/src/router/checkin.ts`, `packages/api/src/member-checkin.ts`, and QR-only domain rules, validators, tests, imports and navigation. Remove `dropIn.promote`, its validation and promotion-only helpers after migrating all callers. Keep unrelated join-link QR sharing. Remove obsolete direct visitor-add tests; replace them with changed-path behavior tests. Coordinate removal of the server QR procedures after updated mobile builds have been released.
8. **Product record and release.** Update `docs/spec.md`, `docs/architecture.md`, `docs/roadmap.md`, `docs/map.md`, `CHANGELOG.md`, the privacy notice, and a new ADR that supersedes QR and owner promotion decisions without rewriting old ADRs. Document that printed check-in posters and old mobile Scan builds no longer work after the cutover.

## Acceptance and Verification

- New visitor: minimal class list, academy-specific belt/health/news/agreement questions, consent, one booked or present visit, visible on staff roster and owner lead list.
- Returning visitor: both email and phone must match the same lead; name-only confirmation, no private detail response, no full form for a valid existing answer set; one-field match and cross-academy match reveal nothing. Old or incomplete leads use the full form. Repeated/concurrent submits do not duplicate a booking or seat count.
- Eligibility: cancelled, deleted, started (unless currently checkable into), out-of-window, wrong-academy and rotated-link submissions fail. Full classes remain bookable. Agreement changes require current acceptance.
- Staff: instructors can copy the link and view restrictions for booked visitors in their academy, but cannot see the full leads list, rotate the link, or consent for a visitor. There is no direct visitor-add, QR check-in, or lead-promotion entry point.
- Registration: web and Expo invite/code join show current academy questions and require fresh answers even when the user was a lead. No answer transfer or automatic membership.
- Write behavior tests for these boundaries in the existing domain, DB, API and validator suites; do not run tests during the implementation session unless the user explicitly requests them. Give the user the focused `pnpm test` command afterward. Run `pnpm lint` and `pnpm typecheck`. Smoke the public link in a browser and exercise visitor booking, returning lookup, rotation and staff roster detail. Smoke the mobile tab bar on a device/simulator if available; otherwise report that limit.

## Rollout and Risks

- Release additive database structure first. Deploy the new web form and mobile join questions before enforcing the new code-join contract. Release the three-tab Expo build and tell gyms to discard QR posters before removing old QR API procedures; old mobile builds otherwise fail on Scan. Do not tie runtime removal to a destructive migration in the same deploy.
- Protect public lookup and submit with a small Postgres fixed-window counter keyed by hashed caller IP and link token, with expiry cleanup. The current `packages/api/src/rate-limit.ts` counters are per process, so they are not enough for a contact lookup. Do not expose raw contact pairs in logs or cache. Log rejected lookups, invalid tokens and booking conflicts through existing logging only; no new telemetry platform.
- If booking fails after release, stop sharing the new link and roll back the web/API build while retaining additive columns and link rows. Only remove obsolete QR procedures after compatible mobile adoption. Confirm production migration state separately.
