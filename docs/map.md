# Map: matops — MVP rebuild (product spec + architecture)

> **Naming (read first).** Two distinct projects:
>
> - **matops** — THIS project, the from-scratch rebuild being designed here. Repo: `/Users/kuna/projects/matops`. When these docs say "the app", "v1", "the rebuild", or "we build", they mean **matops**.
> - **MAT** — the OLD, existing app, kept only as a **reference** (patterns, product context, schema instincts). Repo: `/Users/kuna/projects/mat`. Any mention of "the old app" means **MAT**. We do not build on it.

## Destination

A **first-iteration deliverable pair** for **matops** (the from-scratch rebuild of MAT):

1. an **MVP product spec** (owner web + student mobile, "standard" class-management scope), and
2. an **architecture design doc** — a portable, expandable foundation that a build team can start from without a major refactor later.

Reaching the end of this map means every decision below is locked and those two documents exist. This effort **carries execution to the point of those two documents** (see Notes override) — but not to code.

## Notes

**Domain:** **matops** is a greenfield rebuild of the grappling-academy admin SaaS. The old app **MAT** lives at `/Users/kuna/projects/mat` — it is a **reference, not a base**. Product context digest (from MAT) was gathered in the first session (see `/Users/kuna/projects/mat/docs/product/` and `docs/technical/`).

**Execution override:** unlike default wayfinder (decisions only), this effort's destination _is_ two deliverable documents. The synthesis tickets ([MVP product spec](issues/09-mvp-product-spec.md) and [Architecture design doc](issues/10-architecture-design-doc.md)) produce them. Every other ticket resolves a decision those two documents depend on.

**Settled at charting (destination-fixing decisions — inputs, not tickets):**

- **Codebase:** greenfield new codebase; carry forward the _patterns_ that earned their place in the old app — domain partitioning (ADR-001), the pure booking-policy engine, the tenant seam (ADR-004) — as design lessons re-derived fresh, not copied code.
- **Vendor lock:** portable / ejectable. Standard Postgres (any host), open auth, plain HTTP API. **Convex is OUT** (proprietary reactive engine = deep lock). **Clerk is OUT** (auth must be open/portable). No proprietary service in the critical data path that can't be migrated.
- **MVP scope (standard):** academies (tenant), owner + instructor + student accounts, recurring class schedule, student book/cancel against capacity, member roster + approval, instructor attendance marking.
- **Clients:** Expo/React Native student app + Next.js owner web, in one TS monorepo with shared packages.

**Constraints (sessions 3–4):**

- **Internal-only API → tRPC.** ~~Client-agnostic API~~ retracted: the API is consumed _only_ by our own web + mobile in one monorepo, never handed to third parties. So tRPC's TS-coupling is a non-issue and its zero-codegen DX wins. OpenAPI is retrofittable later via `trpc-to-openapi` if an external need ever appears. Locked in [01](issues/01-api-contract-and-runtime.md).
- **Multi-academy native, NOT "typical SaaS."** The requirement is clean tenant separation + scaling across many academies — _not_ billing/plans/self-serve-signup/marketing machinery. So keep tenancy **simple**: shared DB + `academyId` + an app-level scoped seam (a tRPC middleware injecting academyId + a scoped db client). No RLS / schema-per-tenant in v1. Simplifies [05](issues/05-multitenancy-model.md).
- **Solo builder (1 person, FE+BE).** Every removable moving part is worth real time. Bias hard to fewer services, shared types, no sync/codegen burden.
- **Move fast, DX-first, simple-but-scalable.** Velocity over architectural purity; don't over-engineer, don't paint into a corner.
- **Agentic-coding first.** Prefer stacks agents know cold (most training data, most conventional). This is a first-class selection criterion, and it points the whole effort at the **create-t3-turbo** pattern (see below).
- **Flawless, simple UX** — crowded niche; wins on UX, not feature count. Quality bar on [09](issues/09-mvp-product-spec.md) + design system [11](issues/11-design-system.md).

**Settled FE stack (input):** Next.js (App Router) + shadcn/ui + Tailwind + TanStack Query, web → **Vercel**. shadcn/ui is web-only → Expo needs its own RN system ([11](issues/11-design-system.md)).

**Through-line — the `create-t3-turbo` pattern.** All the above converge on this canonical, agent-famous template: Turborepo monorepo · Next.js (web) + Expo (mobile) · **tRPC** (colocated in Next, both clients consume it) · Tailwind + NativeWind · Prisma-or-Drizzle · Better Auth. It IS this stack, is maximally known to coding agents, and is built for a solo dev. Treat it as the reference skeleton the build phase scaffolds from. Downstream tickets ([03](issues/03-postgres-access-layer.md) ORM, [06](issues/06-hosting-topology.md) hosting, [07](issues/07-monorepo-structure.md) monorepo, [11](issues/11-design-system.md) design system) should default to its conventions unless there's a reason to diverge.

**Skills every session should consult:** `/grilling` and `/domain-modeling` for decision tickets; `/research` for the research tickets; `/prototype` for the product-spec ticket.

**Stack (whole effort is TypeScript end to end.)**

- [A streamed tRPC response cannot carry a cookie](issues/83-streamed-responses-drop-set-cookie.md) — _(web client only; one link swap, no migration, no procedure change)_ Sign in, land on the post-login gate, and the page sits on "Opening your gym…" until it heals itself minutes later. The row was already written: `academy.setActive` had set `active_organization_id` and returned without error, yet `academy.current` kept answering "no active academy". The five-minute session cookie cache ([81](issues/81-api-latency.md)) was reading a cookie written before the switch. ADR 81 assumed `nextCookies()` copies Better Auth's fresh `Set-Cookie` onto the tRPC response; replaying the same call with and without `trpc-accept: application/jsonl` showed the streamed one carries no `set-cookie` at all. **A streamed response sends its headers before the resolver runs**, so a cookie written during the resolver is dropped silently. The web client moves to `httpBatchLink` (buffered, which is what Expo always used), and the same repair lands for every other write that re-signs the cookie: "Start a gym", the invite-link join, and the profile rename, whose `refreshSessionCookie` call was a no-op through the streaming link. The rule left behind: a response that streams cannot set a cookie, so a future switch back takes the cookie cache with it. Still open, its own slice: the gate asks once and shows a spinner with no retry and no error state.
- [The membership booking gate](issues/82-membership-booking-gate.md) — _(S9 / S11 / O7 / §4; migration `0025`)_ Dues existed (ADR 40) but nothing connected them to booking: a student who never picked a plan or stopped paying kept the full app forever. Now an owner can switch on **"Members need an active membership to book"** (O7 → Bank details, **off by default** — with it off, nothing anywhere changes). One derived clock, `bookingAccess` in `@matops/domain`: an approved student books through a **grace window** (owner-set 0–30 days, default 7) past their due day — or, with **no plan**, past the later of joining and the moment enforcement went on, so flipping the switch grants everyone the window with a countdown instead of an instant lock. Past the window `booking.book` refuses, the S11 strip goes error-tone, and the web Book buttons disable — all speaking the same `bookingAccessMessage`. **An open "I paid" claim unblocks instantly** (a reject re-locks by derivation); **never gated:** pending members, staff, cancel, and the QR check-in — the person is at the gym, the owner handles money face to face. Membership choice embeds in onboarding without touching the one-step join: a sole active plan is **auto-assigned at approval**, several plans give the student a one-confirm picker on S9, and either way the first due date is the **1st of next month** (the join month costs nothing in-app; the owner can charge it by setting an earlier date). The roster shows a per-student "booking locked" tag.
- [Every page load paid the Frankfurt round trip forty times](issues/81-api-latency.md) — _(no spec ID, no migration, nothing a member can see)_ "Loading data from the API feels slow", on a 663 Mbps line. Bandwidth was never it: a probe against the live Neon pooler put **one statement at 45 ms**, and the dashboard sends about forty of them. Per procedure, before the resolver reads a row: 90 ms for the session (two rows), 45 ms for the membership, **179 ms for `withTenant`** (BEGIN, SET ROLE, set_config, COMMIT), plus in dev a random **100-500 ms sleep** inherited from create-t3-turbo, paid once per query on a ten-query page. Then three serial waves: the RSC layout awaits the session, `AppShell` blocks on `academy.current` + `academy.memberships`, and only then do ten queries fire at once, which is exactly the `pg` pool default. Six changes, none structural. **The dev sleep is deleted** (the timing log stays, it is how the next person measures this). **The session is cached in its own signed cookie** for five minutes, so an authed request costs zero identity queries — the stated price is that a revoked session outlives its revocation by up to five minutes; role, status and academy switching are unaffected, the last one only because Better Auth refreshes the cookie on `set-active` and `nextCookies()` copies it onto the tRPC response. **Functions move to `fra1`**: `vercel.json` held only a `$schema` key, so every function ran in Washington DC against a Frankfurt database (inferred, not measured — confirm on the next deploy). **The tenant transaction sets role and academy in one statement**, since `SET LOCAL ROLE x` is `SET LOCAL role = x` and the role is a plain GUC, which also makes both values bound parameters instead of an interpolated identifier. **`prefetch()` finally gets called** — it was defined and used nowhere, so the shell's two queries now start on the server and stream with the HTML instead of waiting for hydration. Plus pool `max` 10 → 20 with keepalive, and a 5-minute stale time on the two slow-moving academy queries. Left for its own note: **one transaction per HTTP batch**, the largest win remaining, which touches the tenant seam ([12](issues/12-tenant-isolation-mechanism.md)) and the `baseDb` injection point ([60](issues/60-backend-review-fixes.md)).
- [Three kinds of waiting, and only one of them gets a spinner](issues/80-loading-states.md) — _(both clients; no spec ID beyond §3's states line, no migration, no procedure)_ Every screen was disciplined about the empty state and the failed state and had one shape for the loading state: `SkeletonRows`, four grey bars 48px tall, standing in for a week grid, a coach card, a hairline rail, anything. The page jumped every time data landed, no route under `(app)/` had a `loading.tsx` at all, and the boot drew a skeleton of a layout that a new member never reaches. **Three tiers now, picked by whether there is anything to be faithful to.** No chrome yet (the app boot, the academy gate) gets the **mat loader**: the basketweave mark from `@matops/ui/logo` with its seam path split into six, each drawing on with `stroke-dashoffset` 90ms apart in weave order, the two centre seams then the four planks, which is how a gym lays mats before class. Nothing new enters the identity, and the wrapper fades in on a **180ms delay with `backwards` fill**, so a fast boot shows nothing rather than one frame of flash. The label says what is happening (`Opening your academy`), not `Loading…`. Chrome already drawn gets a **skeleton cut from the real shape**: `skeletons.tsx` builds every piece out of the component it replaces (`cardClass()`, `Section`'s own hairlines, the O1 tile geometry, the O2 column template and 64px hour rows), and structural lines are drawn for real rather than pulsed, because they are not the unknown part. **A route's `loading.tsx` and its screen render the same component**, so the placeholder appears once and is replaced once instead of re-flowing in between. Two routes stay deliberately vague: `/` is the dashboard or the student week and `/payments` is claims or dues, and a server file that runs before the shell mounts knows no role, so both draw only what the two versions share. **The phone gets the same rule in two tiers instead of three**, since Expo Router has no route-level boundary and a screen's own `isPending` is the only place a placeholder goes: `Loading` became the mat loader (drawn with positioned Views and the native driver, no SVG dep per ADR [44](issues/44-mobile-dark-first-design-system.md)), so all six gates took it without a call-site change, and `components/skeletons.tsx` mirrors the web file for the week, my classes, the feed, class detail, dues, rank and the walk-in list. `InlineLoading` is gone: its last caller duplicated the **Find gym** button's own spinner, and a spinner's one remaining job is an action in flight, which `Button` already owns. Neither loader has been seen running — no browser extension and no simulator in the build env.
- [The notification center: every message gets a durable copy, and the owner gets a voice](issues/77-notification-center.md) — _(spec S13 / O12 / §4; migration `0023`)_ Phase 4 built a sending engine and stored nothing, so a student with push off had no way to learn Tuesday's class was cancelled, and the owner had no way to say "mats closed Friday" without leaving the product. One `notification` table, academy-scoped inside the tenant seam, **one row per recipient per event**: fan-out on write rather than an announcement table plus read receipts, because unread count is then one indexed count and the feed one flat query, and gym-scale rows are cheaper than joins. `deliver()` writes the row in its own `try` **before** it pushes or mails, so a dead Expo token cannot cost the member the message — all five existing kinds became inbox entries with no new call sites. The row stores a `link` path (`/class/<id>`, `/payments`), not a payload; the push `data` blob stays for the phone's tap router. `announce` on `ownerProcedure` fans out through the pure `announcementRecipients`, which reaches **active members only** — three audiences (everyone, students, coaches), and the button says `Post to 34` from the same function that picks them, so nobody posts blind. The compose box sits on the feed it writes to rather than on a screen of its own. `notification_pref` carries **one switch, gym news by email**: class and dues messages are transactional and always send, but an owner posting weekly to 200 people with no way out is how a sending domain gets marked as spam, and a missing row means opted in. Opening the center marks everything read, with the dots kept for that render. The daily tick from ADR [75](issues/75-daily-cron-on-github-actions.md) is unchanged and now leaves a copy behind; live UI stays parked, the badge polls.
- [A daily cron on GitHub Actions, dues reminders only](issues/75-daily-cron-on-github-actions.md) — _(spec §4 + O7/R.1; no migration, no domain change, one line in the reminder route)_ ADR [46](issues/46-no-scheduler-v1.md) removed **Vercel Cron** and, with it, every scheduled job, so **dues reminders never fired** and the owner had to chase each member in person. The scheduler does not have to be the host: `.github/workflows/cron.yml` is free, already lives in this repo, and calls an HTTPS endpoint with the existing `CRON_SECRET` bearer token, so it re-locks us to nothing (ADR 46's real objection stands). **One tick a day, 09:00 in Lisbon, one curl.** GitHub cron is UTC-only and Portugal shifts between UTC+0 and UTC+1, so both hours are scheduled and a guard line keeps the tick that is 09:00 local. The cadence is set by **Neon, not by the cron**: Neon Free sleeps after 5 minutes idle on ~100 compute-hours/month, so every ping buys at least 5 minutes of compute and a 15-minute cadence keeps the database awake permanently (~730 h/month) until it **hard-suspends**. Daily costs ~2.5 h/month. Dues reminders are the job worth having: the sweep stamps `dues_reminder_period` as the `YYYY-MM` of the due date, so a member gets **at most one message per billing period** and someone who stays overdue is never nagged twice. `/api/cron/materialize` is **not** scheduled: lazy-on-save and `healHorizon` on the schedule read (ADR 46 Option B) already keep the horizon full, so a sweep would only reach an academy nobody edits and nobody opens. **Class reminders stay off**: the phone schedules them on the device (ADR [54](issues/54-local-class-reminders.md)), their benefit (fewer no-shows) is a v1 non-goal and cannot be measured, and a daily tick would reach only the classes inside the 2h lead window. `leadMinutes: 0` empties the claim window, so nothing is claimed and **nothing is stamped**. GitHub's scheduler drifts by minutes, and the claim is per billing period, so a dropped tick moves a reminder to the next day rather than losing it. Nothing time-sensitive should be built on this.
- [The web shell owns the academy, the access table, and the booking call](issues/74-web-shell-seams.md) — _(web client only; no spec ID beyond §3's role split, no migration, no procedure)_ An architecture pass after ADR [73](issues/73-student-web-parity.md) put the student and the owner in one shell. Thirteen screens fetched `academy.current` and re-wrote its loading / failed / none branches, although `AppShell` already refuses to render a child until that value is a real membership: the academy is a **React context** now (`_components/academy.tsx`), and `useAcademy()` hands every screen a non-null membership with no branch. Book and cancel had been copied into three screens and **two of them invalidated different query paths**, so one list could go stale while the other updated: `_components/use-booking.ts` owns the pair, the web twin of the Expo `book-control.tsx`. Only the sidebar knew which pages a role has, so an instructor who typed `/members` still rendered the owner screen and watched its queries get refused; `_components/routes.ts` is one access table that the sidebar and the shell both read, and the shell shows `NoAccessState` rather than the failed screen. **The tRPC tier is still the guard** — this decides what a person is offered. Twenty-four `Intl.DateTimeFormat` instances across fourteen screens became twelve in `~/lib/format.ts`, the mirror of the Expo `utils/format.ts`. Three rules that existed once per client moved down to `@matops/domain` with tests: `dayKey`, `groupByDay` (identical in all three schedule screens) and `PAYMENT_STATUS_LABEL`.
- [The owner rebuilds the schedule, six months at a time](issues/79-manual-schedule-rebuild.md) — _(spec **O3** + **S5**; no migration)_ **Supersedes the horizon half of [78](issues/78-notification-and-horizon-seams.md)** and closes out ADR [46](46-no-scheduler-v1.md)'s Option B lineage (`healHorizon`, [76](issues/76-pilot-blockers.md)); both stand as written. Who pushes the class horizon forward had been answered three ways in three waves, all of them "it should fill itself". Three reasons that is the wrong shape for a pilot where nobody from matops is in the room. **The owner had no button**, so a calendar that looks wrong cannot be fixed by the person standing in the gym. **Stale classes never left**: pausing a template keeps its classes, and a template whose days or time changed leaves its old instants behind as real bookable rows, so a gym that reorganises its week ends up with two schedules at once. **Students could book six weeks out** through a direct `/class/<id>` link, which is worthless because the gym's plans change first. So: horizon **42 → 180 days**, filled on every template save; one owner-only **Rebuild schedule** button that throws the forward schedule away and regenerates it from the active templates alone; **booking capped at 7 days**. The delete rule is the pure `staleClassIds` (set difference on template + instant), and what it refuses to touch is the load-bearing part — **past classes and all attendance** (which share the participation row with the booking), **one-off classes** nothing would recreate, and a class the owner **deliberately cancelled** at a still-wanted instant. It does take bookings and per-instance edits, and the confirm dialog names the count first. Students are **not** told their booking went, which is the weak point: revisit it the first time a pilot owner rebuilds a live week. The cross-academy sweep and its tests stay, unscheduled.

- [One fan-out, one horizon owner, and the seat rule in the domain](issues/78-notification-and-horizon-seams.md) — _(architecture pass over v3.6/v3.7; no migration, no dependency, nothing a member sees)_ **Supersedes the `healHorizon` half of [76](issues/76-pilot-blockers.md) and the "materialize is not scheduled" half of [75](issues/75-daily-cron-on-github-actions.md)** — both stand as written, this note is the supersede. Four shapes worth fixing before the wave is committed. **The notification fan-out was written twice**: ADR [77](issues/77-notification-center.md) added `deliverEach` beside `deliver` because the dues sweep gives each person a different message, and the copies drifted inside one wave (one `sendPush` for a whole class versus one per person; a failure count returning recipients rather than intended emails; `sentBy` and `emailOptOuts` honoured by one reader of a shared type and not the other). One `deliver(items)` now, with `each(userIds, msg)` for the callers that send everyone the same thing, and `sendPush` takes addressed messages like `sendEmailBatch` already did. **The email opt-out went back where it belongs**: `notifyAnnouncement` decides who gets mail, the transport stopped knowing what a preference is. **The schedule read stopped materializing**: `healHorizon` did unbounded serial writes in front of two reads, where `runMaterializationSweep` does the same job with a row limit and a time budget — the sweep now rides the daily GitHub Actions tick (ADR 46's objection was the host, and the host is GitHub), takes an injected `exec`, and finally has tests. The trade is a horizon that heals daily instead of per read, which needs 42 days without a template edit **and** a broken workflow to show, and `curl -fsS` makes that red rather than quiet. **`canDecideSeat(actor, member)`** moved the coach-queue escalation rule out of a router throw into `packages/domain`, next to `canApprove`. Plus `notificationKindLabel` shared by both clients and `clientIp` moved to where the rate-limiter's tests live.

- [Pilot blockers: the head coach runs the desk, the calendar heals itself, and the wall poster has a brake](issues/76-pilot-blockers.md) — _(spec O1 / O4 / §4; no migration)_ Five gaps found by reading the code against `docs/pilot-plan.md`, whose defining constraint is that nobody from matops is in the room. **Sentry** ran on the wizard's defaults (`tracesSampleRate: 1`, logs on, 10% session replay) against a free plan of 5,000 errors and 50 replays a month, so the quota could run out mid-pilot and the failure mode is silence: traces and logs off, replay on error only, extension noise ignored. **The calendar ran dry at week six** because materialization only happens on template save, 42 days out, and ADR [46](issues/46-no-scheduler-v1.md) removed the scheduler: `healHorizon` now tops the horizon up on `class.week` and `class.mine`, inside the tenant transaction, reusing `materializeTemplate` (idempotent on `UNIQUE(template_id, starts_at)`) and costing one indexed select that returns nothing on a healthy gym. **The public surface had no brake** although the join QR goes on a wall: an in-memory fixed window on `dropIn.submit`, `dropIn.academyInfo` and `invite.resolve`, plus a Better Auth `rateLimit` block capping magic-link send, which spends a Resend quota shared by every academy. Per-instance on Fluid compute, and that ceiling is written down. **A stranger's name, phone and email** were collected behind one sentence with no link, so a public `/privacy` page ships with `[ENTITY]` placeholders left visible, linked from the drop-in and join forms (outside the `<label>`, or the link ticks the box). **The head coach runs the desk** in most gyms, so `approve` / `reject` / `members` / `memberHistory` moved to `staffProcedure` and `/members` became a staff route: an instructor approves, declines, ranks and writes notes, sees `dues: null`, and never gets invites, leads, CSV, suspend, remove or the role picker. Plus a feedback `mailto:` and a first-run checklist, because an empty gym's dashboard said "All clear."
- [The student web app reaches parity with the phone app](issues/73-student-web-parity.md) — _(S4-S7, S9, S11, S12 + shell IA; no migration, no new procedure, no new domain rule)_ ADR [57](issues/57-student-onboarding-funnel.md) sized the student web as the **first session** before the app install, which is one screen: the week, Book, Cancel. [pilot-plan.md](pilot-plan.md) moved the pilot to **web from day one** (no device testing since v1.8, no Apple account, `expo-camera` landed after the last dev-client build), so the only client a student has became the half-built one, missing My classes, stats, class detail, dues, rank and the overdue strip. The student now gets the app's four jobs minus Scan — Schedule `/` · My classes `/training` · Dues `/payments` · Profile `/profile` — plus `/class/<id>`, inside the **owner's own shell**: both nav blocks were already wrapped in `items.length > 1` and a student qualified for exactly one item, so the sidebar, the bottom tabs, the pending banner, the switcher, the theme toggle and sign-out were all built and switched off. **No backend work**: every procedure was already on the right tier and every pure rule the screens call is the one the Expo app calls, so the clients cannot drift. Two live defects closed on the way: `/payments` served a student a screen of failed owner queries (it branches on role now), and the switcher read `academy.listMine`, whose `isWebLensMembership` filter meant a student in two gyms saw no switcher at all (it reads `academy.memberships`, the ADR [49](issues/49-web-login-routing.md) gate's own list). The in-app **scan** stays app-only, because the poster encodes a web page that already works in a phone browser; push and class reminders stay app-only too (ADR [46](issues/46-no-scheduler-v1.md), ADR [54](issues/54-local-class-reminders.md)), which the pilot brief names as a known gap.
- [Sentry for error tracking (web)](issues/72-sentry-error-tracking.md) — _(roadmap 5.2, the errors half; no spec ID, no migration)_ The only way to learn the app broke was for someone to tell us, and the pilot gives real academies no support channel, so a crash reads as an owner quietly giving up. `@sentry/nextjs` covers all three Next runtimes: server and edge through `src/instrumentation.ts` (which also exports `onRequestError`, so a throw inside a tRPC procedure arrives with its request instead of as an anonymous 500), the browser through `src/instrumentation-client.ts`, and a crash escaping the root layout through a new `global-error.tsx`. `withSentryConfig` uploads source maps, without which every trace is minified and useless. The DSN is **hardcoded on purpose**: it is public, ships in the bundle anyway, and a t3-env `client` var would fail the build when unset, which is a worse failure than reporting nothing. `tracesSampleRate: 1` is right for a few academies and wrong later. The wizard's own output **broke the build** and had to be rewritten: it appended CommonJS (`require`, `module.exports`) into an ESM `next.config.js`, which Node refuses outright (`ERR_AMBIGUOUS_MODULE_SYNTAX`), and would have wrapped an unassigned `module.exports` and dropped `transpilePackages` even if it had loaded. `SENTRY_AUTH_TOKEN` must be set in Vercel or source maps silently stop uploading. Mobile reports nothing, and the rate-limit half of 5.2 is untouched.
- [A pinned map link for the academy](issues/71-academy-map-link.md) — _(O6 / S7; migration `0022`, one column)_ ADR [68](issues/68-academy-time-zone-address-and-delete.md)'s "Open in Maps" link is a Google **search** for the typed address, and a search misses for ordinary gyms: a unit in a mall, a basement, a building with no number. Only a new student on their first visit ever finds out. An address cannot be validated without a geocoder, and a geocoder means an API key and billing for one field, so this does two cheaper things instead: the settings card shows a **Check the pin ↗** link built by the same `academyMapUrl` the student taps, so the owner sees the real result before saving, and `organization.map_url` holds an optional **share link** from a map app that the tap prefers over the search. A share link came out of a map, so it always resolves. `MapUrlSchema` allows https only and only map hosts (`maps.google.com`, `maps.app.goo.gl`, `maps.apple.com`, `openstreetmap.org`, `osm.org`, `waze.com`, and `google.com` under `/maps`), because the value becomes a tappable link for every member — bare `google.com` and `goo.gl` are excluded as open redirectors, and the host comes from `new URL()` so a backslash cannot forge it. The field is disabled until an address exists, since students tap the address **text**. On mobile the no-link fallback now opens the phone's own map app (`maps://`, `geo:`) instead of the browser.
