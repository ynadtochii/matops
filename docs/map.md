# Map: matops — MVP rebuild (product spec + architecture)

> **Naming (read first).** Two distinct projects:
>
> - **matops** — THIS project, the from-scratch rebuild being designed here. Repo: `/Users/kuna/projects/matops`. When these docs say "the app", "v1", "the rebuild", or "we build", they mean **matops**.
> - **MAT** — the OLD, existing app, kept only as a **reference** (patterns, product context, schema instincts). Repo: `/Users/kuna/projects/mat`. Any mention of "the old app" means **MAT**. We do not build on it.

## Destination

A **first-iteration deliverable pair** for **matops** (the from-scratch rebuild of MAT):

1. an **MVP product spec** (owner web + student mobile, "standard" class-management scope), and
2. an **architecture design doc** — a portable, expandable foundation that a build team can start from without a major refactor later.

Reaching the end of this map means every decision below is locked and those two documents exist. This effort **carries execution to the point of those two documents** (see Notes override) — but not to code.

## Notes

**Domain:** **matops** is a greenfield rebuild of the grappling-academy admin SaaS. The old app **MAT** lives at `/Users/kuna/projects/mat` — it is a **reference, not a base**. Product context digest (from MAT) was gathered in the first session (see `/Users/kuna/projects/mat/docs/product/` and `docs/technical/`).

**Execution override:** unlike default wayfinder (decisions only), this effort's destination _is_ two deliverable documents. The synthesis tickets ([MVP product spec](issues/09-mvp-product-spec.md) and [Architecture design doc](issues/10-architecture-design-doc.md)) produce them. Every other ticket resolves a decision those two documents depend on.

**Settled at charting (destination-fixing decisions — inputs, not tickets):**

- **Codebase:** greenfield new codebase; carry forward the _patterns_ that earned their place in the old app — domain partitioning (ADR-001), the pure booking-policy engine, the tenant seam (ADR-004) — as design lessons re-derived fresh, not copied code.
- **Vendor lock:** portable / ejectable. Standard Postgres (any host), open auth, plain HTTP API. **Convex is OUT** (proprietary reactive engine = deep lock). **Clerk is OUT** (auth must be open/portable). No proprietary service in the critical data path that can't be migrated.
- **MVP scope (standard):** academies (tenant), owner + instructor + student accounts, recurring class schedule, student book/cancel against capacity, member roster + approval, instructor attendance marking.
- **Clients:** Expo/React Native student app + Next.js owner web, in one TS monorepo with shared packages.

**Constraints (sessions 3–4):**

- **Internal-only API → tRPC.** ~~Client-agnostic API~~ retracted: the API is consumed _only_ by our own web + mobile in one monorepo, never handed to third parties. So tRPC's TS-coupling is a non-issue and its zero-codegen DX wins. OpenAPI is retrofittable later via `trpc-to-openapi` if an external need ever appears. Locked in [01](issues/01-api-contract-and-runtime.md).
- **Multi-academy native, NOT "typical SaaS."** The requirement is clean tenant separation + scaling across many academies — _not_ billing/plans/self-serve-signup/marketing machinery. So keep tenancy **simple**: shared DB + `academyId` + an app-level scoped seam (a tRPC middleware injecting academyId + a scoped db client). No RLS / schema-per-tenant in v1. Simplifies [05](issues/05-multitenancy-model.md).
- **Solo builder (1 person, FE+BE).** Every removable moving part is worth real time. Bias hard to fewer services, shared types, no sync/codegen burden.
- **Move fast, DX-first, simple-but-scalable.** Velocity over architectural purity; don't over-engineer, don't paint into a corner.
- **Agentic-coding first.** Prefer stacks agents know cold (most training data, most conventional). This is a first-class selection criterion, and it points the whole effort at the **create-t3-turbo** pattern (see below).
- **Flawless, simple UX** — crowded niche; wins on UX, not feature count. Quality bar on [09](issues/09-mvp-product-spec.md) + design system [11](issues/11-design-system.md).

**Settled FE stack (input):** Next.js (App Router) + shadcn/ui + Tailwind + TanStack Query, web → **Vercel**. shadcn/ui is web-only → Expo needs its own RN system ([11](issues/11-design-system.md)).

**Through-line — the `create-t3-turbo` pattern.** All the above converge on this canonical, agent-famous template: Turborepo monorepo · Next.js (web) + Expo (mobile) · **tRPC** (colocated in Next, both clients consume it) · Tailwind + NativeWind · Prisma-or-Drizzle · Better Auth. It IS this stack, is maximally known to coding agents, and is built for a solo dev. Treat it as the reference skeleton the build phase scaffolds from. Downstream tickets ([03](issues/03-postgres-access-layer.md) ORM, [06](issues/06-hosting-topology.md) hosting, [07](issues/07-monorepo-structure.md) monorepo, [11](issues/11-design-system.md) design system) should default to its conventions unless there's a reason to diverge.

**Skills every session should consult:** `/grilling` and `/domain-modeling` for decision tickets; `/research` for the research tickets; `/prototype` for the product-spec ticket.

**Stack (whole effort is TypeScript end to end.)**

- [The academy gets a time zone, an address, and a delete](issues/68-academy-time-zone-address-and-delete.md) — _(O6 / O3 / S2 / S7; migration `0021`, three nullable columns on `organization`)_ ADR 63 emptied Settings down to a name and a code, and what it left out was load-bearing. **No academy time zone existed anywhere**: each template carried its own, defaulted from the creator's **browser** into a free-text box, and `academyTimeZone()` guessed the gym's zone by counting which one the templates used most — so a typo mis-timed every class it materialized, two coaches in two zones split the schedule silently, and a gym with no templates yet had its stats drawn in **UTC**. The zone now lives on the academy, picked from `Intl.supportedValuesOf("timeZone")` so an unresolvable one cannot be stored; templates **inherit** it at create and existing ones keep theirs, because re-timing them would run the ADR 60 cancel-and-re-materialize path and drop classes students had booked — Settings names the strays and the form offers a one-click move instead. **Address** is one sanitized free-text block with a Maps **search** link (never geocoded — we did not verify the string), shown where someone needs to know where to go: Settings, the mobile Profile, and the join confirm step on both clients. **Delete** is **soft** and gated on typing `delete <academy name>`: the code is never reissued to another gym and a mistake is one `UPDATE` away from undone. Its cost is seven filters, one per path that resolves an academy — `getMembership` is the load-bearing one, so a deleted gym fails every tenant procedure at the middleware and its members land on the post-login gate. No restore UI, no export, no hard purge.
- [A web Profile, reached from the sidebar footer](issues/67-web-profile-screen.md) — _(O11; web IA + one additive read field, no migration)_ The web had settings for the gym and nothing for the person running it: an owner or instructor could not see or edit their own name and phone in a browser, and the name is what students read as the coach of a class. `account.updateProfile` had existed since slice B.3 and only Expo ever called it. A **`/profile`** route now serves it, opened by making the **sidebar footer** (avatar, name, role) a link and giving the mobile top bar the same avatar — a route with no nav item, the pattern O5 Attendance set, so a primary nav already carrying seven items for an owner does not grow. Name and phone editable, email read-only because it is the sign-in identity, plus the active academy's role and join month, the theme toggle and sign out. The page reads the session **server-side** and calls `router.refresh()` after a save, so the sidebar name updates with the screen and the web auth client needs no `inferAdditionalFields`. `academy.current` gains `joinedAt` from Better Auth's own `member.created_at`. Every role, students included. Extends the "Settings is only the academy" line of ADR [63](issues/63-settings-split-by-job.md).
- [One demo academy for the beta test](issues/65-beta-demo-academy.md) — _(dev tooling only; no product / migration change)_ The database held five academies: three scratch gyms from development plus the two fake ones from [51](issues/51-db-seed-module.md). A beta tester who sees a gym picker is testing our leftovers. `SEED_ACADEMIES` (two) becomes **`SEED_ACADEMY`** (one), **"Alma beta"** (`seed_org_alma`, code `990001`); `seedAcademyList`/`seedAcademyIds` stay lists so teardown, status and the IO layer are unchanged. You own it; the tester joins through the seeded **instructor** link. Every other academy goes in one hand-run `wipe-academies.sql` (all tenant tables, memberships, orgs, `seed_` users and **all sessions**, since a session pins an `activeOrganizationId` that is about to vanish); real `user` rows survive. The dataset also grows the states it was missing: all four **drift bands** (past window 28 → **42 days**, and `run.ts` keeps drifters out of future bookings), **one-off** and **cancelled past** classes, all five **disciplines**, an **archived plan** someone is still on, a **third coach who has taught nothing** plus belts for all three, a **class-linked** and a **no-consent** lead, all three **referral audit actions**, and a two-note member. Supersedes the two-academy half of [51](issues/51-db-seed-module.md). Mobile demo data is the cost: `up` no longer gives you a student membership.
- [The instructor link grants the instructor role](issues/64-invite-role-and-coach-queue.md) — _(O4 / O6 / O10; API + one DB rule, no migration)_ Three defects on one seam. Opening the instructor link while already **pending** kept the stale `invitedRole`, so an invited coach was approved as a student; a pending row now takes the newest link's role, while an **active** row is still left alone because re-roling an approved member is the owner's call, not a link's. An already-active member who re-joined was told "You're in, pending approval" when nothing was written; the join screen now says what actually happened. A pending instructor queued next to pending students, where approving them silently granted schedule and attendance tools; one pure rule (`isPendingCoach`) now splits the Members queue, the Coaches queue and the two O1 counts. And `membership.demote` becomes **`setRole`** — same locked never-ownerless transaction, now both directions, `InviteRoleSchema` so it can never grant `owner`. Replaces the `demote` half of ADR [50](issues/50-settings-staff-management.md).
- [Settings splits by job](issues/63-settings-split-by-job.md) — _(web IA; client-side only, no procedure or migration change)_ Settings had become the drawer for anything academy-wide: the staff list, both invite links, the bank details, the check-in poster. Four of the five were the setup step of a job on another screen, and the copy showed it ("share the instructor invite link from Settings", on the screen where coach requests are approved). Each control moved to the screen that owns its outcome — **Staff + instructor link** to the bottom of **Coaches** (below the workload cards, pending approvals still on top), the **student link** above the **Members** tabs, the **check-in poster** inside the **Drop-in leads** tab it fills, **bank details** to a fourth **Payments** tab. Settings keeps the academy name and code, which is the honest size of it. Supersedes the placement half of ADR [50](issues/50-settings-staff-management.md); the never-ownerless and pending-until-approved rules are unchanged.
- [Coach workload and coverage](issues/62-coach-workload-and-coverage.md) — _(O10; staff web + one shared domain module, no migration)_ `class.instructor_id` had existed since Phase 2 but nothing set it on purpose: both create paths fell back to the acting user, no client sent the field, and the web never called the edit that changes it. It recorded who typed the template in, not who taught, so the wave fixes attribution before reporting on it: a **coach picker** on both class forms, a **change-the-coach** control on every class roster for cover nights, and `requireInstructor` closing a column that had no FK and no RLS of its own. Credit is automatic and read-time, so reassigning a past class moves its history (the ADR 52 rule). `canReassignCoach` lets any staff set the coach on an upcoming class and only an owner rewrite a finished one; `classChange` now takes `now` and stays silent when both starts are in the past, so a correction never pushes "your class changed". Averages divide by **marked** classes, drop-ins are not visits, and the screen is name-ordered with **no ranking by headcount** because that measures the timeslot. The planned O1 unmarked nudge was dropped: `needsAttendance` already drives that queue and its rule is better.
- [Identity reads run on the tenant transaction](issues/66-identity-reads-run-on-the-tenant-transaction.md) — _(amends the `ctx.baseDb` rule in ADR 60; no migration, no user-visible change)_ `architecture.md` claimed identity tables "can never be read through the tenant transaction". They can, the routers already did it (`template.list` left-joins `user` on `ctx.db`), and migration `0020` says so in its own comment. Fourteen call sites read identity on the **base** connection from inside `withTenant`, checking out a **second** pool connection and holding both for the length of the request: with `pool.max` at 10, ten concurrent requests deadlock. On PGlite (one connection) it was certain, not probabilistic, which is why `member-scope` / `payments` / `coach-stats` had been timing out and the api suite took **366s** to fail. Reads inside a tenant resolver now use `ctx.db` (`DbReader = DbExec | TenantTx`); the base connection is for pre-transaction lookups and identity **writes** only. `listMembershipsForUser` gained the required `exec` ADR 60 missed. Suite: 62 tests green in 18s.
- [Attendee names include pending members](issues/55-attendee-names-include-pending.md) — _(amends the §4 schedule-privacy rule locked in session 12)_ The rule bundled two gates: who may see names, and whose name may be shown. The second one reads as a bug in use — a class showed eight names and "+1 other", and the hidden person was an ordinary member awaiting approval. Keeps the viewer-side gate (a pending viewer still sees counts alone, so a self-join is not a member directory), drops the subject-side one: an approved viewer now sees **every booked member** by name, pending included. **Drop-ins stay a count** — they consented to gym contact, not to being listed to students. `class.attendees` loses its `listMembersOf` lookup as a result.
- [Local class reminders](issues/54-local-class-reminders.md) — _(student mobile; no server change)_ The Settings toggle promised class reminders that no code path could send, because ADR 46 removed every cron. The phone now schedules its own `expo-notifications` local notification 2h before a booked class and drops it on cancel, sign-out, or when the toggle goes off. Payload matches the server push so the existing tap router still opens the class detail. `/api/cron/remind` stays dormant; re-enabling it later must not double up. Known limits: one device only, a reminder can outlive a class cancelled while offline, and a reinstall loses scheduled reminders.
- [Schedule poster export](issues/61-schedule-poster-export.md) — _(staff web O3; client-only, one additive read field)_ One button renders the **active recurring templates** to a landscape 1600x1200 PNG (2x) on a `<canvas>` and downloads it. Templates, not a dated week: no booking data to strip, wall-clock times so the owner's browser zone cannot skew it, and no dates to go stale. Always light, no live clock, footer carries the 6-digit join code plus an "Updated <date>" stamp. No server route, dependency, or migration; `template.list` gains `instructorName`.
- [Schedule week grid](issues/53-schedule-week-grid.md) — _(staff web O2; presentation only, one additive read field)_ The week renders as a timetable on `md`+ (Mon-Sat columns, hour rows, classes placed by real time; Sunday shows only when it has a class); a colored left rail plus an 8% tint encodes gi (teal) vs no-gi (amber) via the new `--gi` / `--nogi` category tokens, brand violet marks only the now-line / today / pending, empty-hour runs collapse into a labelled band, and the grid uses a 24-hour clock. The phone keeps the day list and its full-size cancel button. `class.week` gains `instructorName`.
- [Internal referral attribution](issues/52-internal-referral-tracking.md) — _(O9; staff web + RLS domain)_ One permanent student→academy-member attribution, initial assignment by staff, owner-only correction/clear, and an append-only audit. `member_referral` + `member_referral_audit` are tenant-scoped in migration `0018`; self-referral and duplicate current rows are blocked in Postgres. Reporting reads existing owner-confirmed `payment_claim` rows retroactively, uses the academy calendar month, and groups money by currency. Owners/instructors see the referral ledger; only owners see history and correction actions. No commissions, discounts, codes, payouts, exports, contacts, or payment controls.
- [The referrals screen reads referrer-first](issues/56-referrer-first-referrals.md) — _(amends ADR 52's O9 layout)_ O9 shipped as a student ledger with a referrer picker on every row and five filters above it, which put a monthly action in forty places and asked the reader to operate a report. The screen now lists the people who bring students in, ranked, with their students as chips; **one dialog owns every write** (header button, an uncredited student, or an owner clicking a chip to correct); filters drop to search plus show-removed; plan and dues leave O9 for O4/O7. No API, schema, or permission change — the client groups `referral.dashboard` students by referrer and reuses `groupMoneyByCurrency` so totals match the rows on screen.
- [The student's first client is the web, not the app store](issues/57-student-onboarding-funnel.md) — _(amends ADR 42; join flow S2, student web S4/S5, settings O6)_ Registration on web already existed twice, and handing the student off to an app store afterwards would have added the most expensive step in the funnel (two magic links, one install, six app switches) to reach a store the project cannot publish to on iOS yet. A student who joined on web also landed on a permanent "You're almost in." page. So the phone browser becomes a first-class client for the first session: the invite link is also a **QR code** for the face-to-face moment, the magic-link mail hop moves to the **end** of the join form, and a joined student gets the **week schedule with book / cancel** on web, reusing `class.mine` and the `booking` router. The approval gate and the two-client split are unchanged; a pending member could already book (`provisional`). No migration, no new domain rule.
- [Every input is sanitized then bounded, in one place](issues/58-input-validation-and-sanitization.md) — _(amends the boundary rules in ADR 33)_ Every tRPC procedure already had a Zod schema, but the schemas measured length without looking at content: `z.string().trim()` keeps zero-width spaces, control characters and bidi overrides, and phone had no charset at all. `@matops/validators` now exports `lineText` / `blockText` / `NameSchema` / `PhoneSchema` / `EmailSchema` / `HttpUrlSchema` / `IdSchema`, each capping the raw string before it cleans it and bounding the cleaned value after. Three uncovered surfaces are closed with the same schemas: the **sign-in server actions** (a public endpoint that validated nothing, with an unchecked `callbackURL`), the join page's carried `?p=` profile, and the magic-link URL interpolated into an email `href`. Loose on format, strict on charset. No API, domain, or migration change. **Rate limiting stays out** and is Phase 5 work.
- [A join link prefills the form, it never joins on its own](issues/59-join-link-prefills-only.md) — _(amends ADR 57; join flow S2)_ The ADR 57 join link carried the profile in `?p=` and auto-fired `membership.join` on open. Nothing tied `?p=` to the magic-link verification meant to produce it, and both halves of the URL are public, so a crafted invite link sent to any signed-in user rewrote their **global** name and phone, made them pending in the attacker's academy, and could switch their active tenant — with no click. The carried profile is now a **prefill only**: the signed-in branch renders the normal join form with the values filled in, and joining takes one press. A server-side nonce was rejected as a table and a lifetime added to a screen that already has a form on it.
- [Backend review: a test seam for the API, one base-db door, and the fixes that fell out](issues/60-backend-review-fixes.md) _(amends ADR 33; adds a third test home)_ `packages/api` had no tests, and a full backend review found three critical bugs: the auth error hook logged the Better Auth context (which carries the **app secret**, so rotate it), a template timing edit hard-DELETEd classes that `class_participation` and `drop_in` reference with `ON DELETE no action` (so an owner could never move a booked template again), and every recipient of a class email went in one `to:` field. The seam now has **one** injection point, `ctx.baseDb`, and `withTenant` / `getMembership` / `getMemberById` / `getMemberIdForUser` / `listMembersOf` take a **required** `exec`. A default parameter is what let the old gap open with no compile error. Notifications moved to an `afterCommit` hook so sends no longer hold the tenant transaction open; the timing edit **cancels and revives** instead of deleting; emails go one per recipient. Migration `0019` indexes `member (organization_id, user_id)`; `0020` revokes matops_app's write access to the identity tables. Plus the smaller defects: `payments.myDues` was readable by a **pending** member (bank details), `deletePushToken` had no owner check, class notifications omitted the time zone, `template.update` reassigned the instructor to the editor, both reminder sweeps stamped before sending serially, and the drop-in upsert erased a returning visitor's class.

- [MVP product spec](issues/09-mvp-product-spec.md) — **DELIVERABLE:** [spec.md](spec.md). Student mobile (7 screens, ≤3-tap book) + owner/instructor web (6 screens), two core loops, approval gate, transactional capacity, flawless empty/error states, explicit not-in-v1.

- [Neon driver + serverless connection model](issues/21-neon-connection-model.md) — _(review wave)_ **Facts:** `neon-http` = no interactive tx (fine for atomic UPDATE); WebSocket/`pg` = full tx + row locks. Pooler (txn mode) breaks `SET`/`LISTEN-NOTIFY`/advisory locks; RLS via `SET LOCAL`/`set_config(...,true)` in a per-request tx. Recommended: **`pg` + Vercel Fluid compute on the `-pooler` endpoint**. LISTEN/NOTIFY needs a long-lived worker.
- [Better Auth Organization: pending-approval feasibility](issues/14-better-auth-approval-feasibility.md) — _(review wave)_ **Keep the plugin's `member` table + custom `status` field** (v1.3 `additionalFields`); `addMember` creates a pending member without an invitation. **Risk:** the plugin ignores status in all access checks — a pending member with a role passes everything. Mitigation: enforce `status==='active'` in the tenant middleware and/or **grant the role only at approval**.
- [API deployment shape](issues/15-api-deployment-shape.md) — _(review wave)_ **In-Next serverless for v1, `packages/api` kept extraction-ready.** Single Next app on Vercel (web + tRPC + cron), `pg` on Fluid compute + Neon pooler. Everything v1 needs runs serverless; DB-driven live updates (deferred) become a _separate small worker_ later, not an API rewrite. Corrects the "SSE on the same API" claim in 06/architecture §9.
- [Tenant isolation mechanism](issues/12-tenant-isolation-mechanism.md) — _(review wave)_ **Postgres RLS is the guarantee** (reverses "no RLS in v1"). Policy per tenant table `USING (academy_id = current_setting('app.academy_id'))`; non-BYPASSRLS role; per-request `SET LOCAL` in a transaction (works on Neon pooler). App queries stay plain and cannot leak. Better Auth tables keep plugin scoping; leak-test kept as regression net. Corrects architecture §5.
- [v1 notifications: push + email](issues/17-class-cancellation-notification.md) — _(review wave)_ **Push folded into v1.** Expo Push (mobile) + Resend email, via a thin `packages/notifications` helper — all serverless HTTPS, no WebSocket. v1 events: class cancelled (push+email), class reminder (cron), membership approved (push). **WebSocket/live-UI stays deferred** ([04](issues/04-realtime-strategy.md)): serverless publishes, a future worker subscribes.
- [Booking write atomicity](issues/13-booking-write-atomicity.md) — _(review wave)_ **Atomic conditional `UPDATE` claims capacity** (`WHERE booking_count < capacity`, row-lock serializes concurrent claims), + transition-detected participation upsert, inside the RLS transaction; failed claim rolls back. No `FOR UPDATE`. Re-book = same path (ON CONFLICT flips cancelled→booked); cancel decrements floored. Corrects architecture §7.
- [Instructor permissions + approval gate](issues/20-instructor-permissions-and-approval-gate.md) — _(review wave → pressure-test)_ **Instructors run the whole schedule once approved** (all classes+templates+attendance; owner-only for roster/settings/invites). **Approval is now uniform**: students _and_ coaches join pending/view-only; owner approval grants the role (closes leaked-instructor-link risk). Role granted only at approval (safe given Better Auth ignores status).
- [Class `completed` status](issues/19-class-completed-transition.md) — _(review wave)_ **Dropped.** `class.status` = `'scheduled' | 'cancelled'`; "past/done" is derived from `starts_at + duration < now()`, never stored. No sweep job needed. Schema draft updated.
