**Goal**

An organization can open a BJJ academy or a general space. Each branch has its own schedule, session templates, bookings, and attendance. An organization defines membership plans covering one or several named branches, such as BJJ, BJJ + Gym, or Gym + Sauna.

**Confirmed scope and proposed defaults**

Confirmed by the conversation:

- One organization owns several branches.
- A new branch can be `bjj_academy` or `general_space`.
- General spaces support schedules, templates, sessions, and bookings.
- A membership can cover one branch or a selected combination.
- Plans are created at organization level and available through entity member workflows.
- Assign membership from the member profile inside an entity. Members remain visible by entity.
- The owner needs a combined member directory and business overview across entities.
- Manual monthly payment status is now included by user decision. No payment processing or automatic collection.

Confirmed decisions from the owner:

| Decision             | Agreed behavior                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Assignment           | Organization owners only, from an entity member profile                                                            |
| Branch enrollment    | Automatically create missing active member records in covered entities; preserve existing suspensions              |
| Plan changes         | Apply coverage changes to existing assignments after showing affected members                                      |
| Membership period    | Calendar month, starting on the first; no rolling 30-day term                                                      |
| Mid-month enrollment | Seven days to pay from joining; normal first-of-month cycle starts the following month                             |
| Payment tracking     | Owner manually records whether the membership month is paid                                                        |
| Grace                | Seven days by default, configurable by the owner; warn members to pay                                              |
| Unpaid bookings      | Preserve access during grace; after grace block access and cancel future bookings without another valid membership |
| Reservations         | Shared scheduled sessions only; no private whole-space hire                                                        |
| Capacity             | Strict capacity for general spaces to prevent overbooking                                                          |

Unlimited visits and multiple concurrent memberships remain the simple proposed defaults. Preserve current BJJ capacity behavior; the strict-capacity decision concerns general spaces. One bookable space per general entity, with no overlapping sessions, remains the proposed resource model.

Public visitor booking for general spaces, private hire, arbitrary start times, equipment or room selection, waitlists, visit packs, payment processors, automatic collection, and separate per-branch allowances are outside this release. Existing BJJ public booking remains supported.

**Target design**

1. Extend the existing entity and schedule model.

   Use one shared implementation for recurring templates, scheduled occurrences, participation, and attendance. Keep existing table names in this release. Make instructor optional for general sessions, while preserving BJJ defaults. General sessions have no discipline or curriculum assignment. Add a bounded description field to templates and sessions. Copy template defaults into occurrences, as the existing code does.

   Keep recurring templates as the first release's template model. A separate library of unscheduled activity definitions is unnecessary. Staff can create a recurring template or a one-off session.

   Resolve shared identity and timezone directly from `entity`. Keep curriculum settings in `academy_profile`, which remains BJJ-only. General-space public booking stays unavailable, so its settings do not need moving yet. Add server-side type checks to BJJ-only procedures, including rank and curriculum. Hiding navigation is not an authorization check.

2. Create membership plans at organization level.

   The organization owner opens Memberships, creates a plan, names it, and selects the exact branches it covers. Examples: BJJ Only, BJJ + Gym, and Gym + Sauna. There is one shared plan record, not a copy in each branch. Coverage selects branch IDs, not branch types: BJJ Only can mean one specific academy rather than every BJJ academy.

   The organization owns one shared catalog, available to entity screens without copying plan rows. Recommend showing plans covering the current entity first in its assignment picker. Organization owners can view the full catalog. A plan being visible does not grant access to that entity.

   The primary flow is Entity → Members → Member profile → Assign membership. The organization Memberships screen defines plans and coverage; it is not the primary enrollment screen. Show the membership on the member profile in every covered entity.

   Only organization owners create, assign, change, or cancel memberships. They can assign from any entity member profile. Branch staff can view eligibility for their entity but cannot assign plans or change shared coverage.

   Assigning a plan to a person creates one ongoing membership with a calendar start month and status. Each month has its own manual paid/unpaid record. The system never collects money. A person can hold several assignments; access is the union of eligible assignments.

   Proposed records, named finally in the ADR:

   | Record               | Purpose                                                                                                         |
   | -------------------- | --------------------------------------------------------------------------------------------------------------- |
   | `access_plan`        | Organization, name, description, archive state                                                                  |
   | `access_plan_entity` | Links the plan to explicitly selected entities within the same organization                                     |
   | `access_assignment`  | Organization, user, plan, assigning entity, start month, active/suspended/cancelled status, assigning actor     |
   | `membership_month`   | Assignment, calendar month, paid/unpaid status, recorded-by user and timestamp; unique per assignment and month |
   | `membership_policy`  | Organization, owner-configured grace days (default seven), calendar timezone                                    |

   Store the assignment once against the existing user within the organization, even when created from an entity profile. The assigning entity records where the action happened; it does not limit coverage or own the shared assignment. Repeated assignment of the same active plan from another branch must show the existing membership rather than duplicate it.

   Use “Membership plan” and “Membership” in the interface. The internal `access_plan` name avoids confusing this structure with the existing billing `membership_plan` table. Add only calendar-month tracking and owner-recorded payment status. No bank integration, payment claims workflow, automatic charges, or revenue reporting. Price and payment amount recording are not required for the initial paid/unpaid tracker.

   Use composite foreign keys to prevent cross-organization references. Use organization row-level security, the database rules that restrict which organization's rows a request can read. Filter reads by person and role too: organization isolation alone does not protect one member from another.

   Apply live plan coverage with an affected-member preview before changes. Adding a new branch never adds it to any plan automatically. Archiving a plan stops new assignments; existing assignments retain coverage until ended. Do not allow editing archived plans. Keep an audit record of coverage changes and assignment changes.

3. Keep branch roles and approval separate.

   `entity_membership` continues to hold a person's role and status at one branch. An access assignment does not grant instructor or owner permissions. A branch suspension denies booking even when a valid assignment covers the branch.

   Owner assignment creates a missing active student membership in each covered branch. Keep existing roles and statuses. Never reactivate a suspended, archived, or removed membership automatically. Show the owner which branches still need an access decision.

   Adding coverage to a plan needs the same enrollment reconciliation for affected people. Removing coverage does not delete branch membership, attendance, or booking history. The access resolver denies new bookings where no other assignment grants coverage. Large updates need a repeatable reconciliation path; do not leave partial activation silently.

   Suspending an assignment affects all branches covered by that assignment. Suspending a branch membership affects only that branch. If another active assignment covers the branch, suspending the first assignment alone does not remove access.

4. Resolve booking eligibility in one place.

   Add a pure domain decision and a scoped database reader. Inputs include branch status, operational membership, session time, and applicable assignments. Return stable reasons such as `not-covered`, `pending-approval`, `suspended`, or `expired` for both clients.

   Require an active assignment covering the entity and an eligible calendar month. A paid month permits access. An unpaid month permits access during owner-configured grace and shows a warning with the exact deadline. After that deadline, block booking and admission. Missing monthly records mean unpaid, never paid by default.

   Default boundary proposal: with seven grace days, access remains available September 1-7 and stops September 8 at 00:00 in the membership calendar timezone. Grace belongs to the organization so one shared membership has the same deadline across entities. The calendar timezone remains to be confirmed.

   Mid-month enrollment is confirmed: give the new member seven days to pay from joining. Track that payment against the joining calendar month. The next membership month starts on the first, with the normal owner-configured monthly grace. For example, a September 15 join receives seven days to pay for September; October starts on October 1. This does not create a rolling monthly anniversary.

   Resolve eligibility both now and at session time. During grace, warn clearly about reservations after the deadline. The same resolver serves booking, admission, member lists, and owner overview. Another valid membership covering the entity preserves access even if this membership is unpaid.

   Warn in web and mobile membership and booking views from the first unpaid day. Show the month, payment status, deadline, and what happens after grace. Add deduplicated reminder notifications before expiry using existing notification delivery. Do not send one warning per covered entity. Final reminder cadence can be chosen during implementation.

   After grace, cancel future reservations that have no remaining valid coverage and release capacity once. Add a repeatable scheduled sweep with payment-state rechecks inside the cancellation transaction. Booking and admission checks enforce the deadline even if the sweep is delayed. Payment confirmation racing with cancellation must not cancel a now-eligible reservation.

   Owner payment confirmation is idempotent and marks a specific month paid across all covered entities. It restores eligibility but does not automatically restore cancelled reservations, since another person may hold the place. Preserve payment-status corrections in an audit record.

   Apply this resolver to member booking, owner booking on behalf of a member, and general-space check-in/walk-in admission. Staff administrative permission does not bypass capacity. Cancellation and viewing history remain available while access is blocked.

   Keep current BJJ billing working until an explicit per-entity activation. At activation, choose one authoritative payment gate for shared memberships. Do not apply legacy branch dues and the new monthly tracker together. Define the data mapping and preserve existing claims and history before switching any existing BJJ branch. This does not authorize a wholesale billing migration.

   Payment grace does not override a branch suspension. Whether coverage removal or explicit membership cancellation also gets grace remains an open distinction below.

5. Enforce general-space capacity atomically.

   Add an explicit session/template capacity policy, defaulting existing records to soft capacity. New general-space sessions use strict capacity. Copy the policy when materializing occurrences.

   Claim the place with a conditional database update inside the same transaction as participation. Reject a full session and roll back participation. Repeated requests must not consume another place. Cancellation releases a place exactly once. Reject capacity reductions below reserved places for strict sessions.

   Inventory every path that creates or confirms participation, including approval, staff booking, walk-ins, visitor promotion, and check-in. General-space pending members cannot create provisional reservations. Walk-ins must reserve a place before admission. Keep historical attendance corrections separate from admission so marking attendance does not reserve twice.

   Strict capacity limits reservations for a session. It does not model shared physical resources across overlapping sessions. Reject overlapping general-space sessions within one branch in this release, including recurrence generation and rescheduling. Use a transaction-safe overlap constraint or serialized branch schedule writes. Multiple simultaneous rooms require a later resource model.

6. Keep entity operations and organization oversight as separate views.

   Entity Members remains the daily member list: role, approval, applicable memberships, booking eligibility, and attendance for that entity. Show why the person appears, such as direct enrollment or access through a shared membership. Do not call someone a visitor merely because their plan includes the entity.

   Organization Members is an owner-only combined directory. Group existing entity memberships and assignments by user ID within the organization. Show one row per person with branch badges, memberships, access status, and recent attendance. Allow filtering by branch, plan, and status. Clicking a branch opens that entity's member profile. Do not create a second editable copy of the person's identity or deduplicate by display name.

   No new person table is needed for registered users. Shared identity for login-less visitors remains outside this release.

   Organization Overview summarizes business activity for a chosen date range:

   | Metric                    | Definition                                                                                                |
   | ------------------------- | --------------------------------------------------------------------------------------------------------- |
   | Unique enrolled members   | Distinct users with active student enrollment in at least one entity; exclude staff-only accounts         |
   | Members with valid access | Distinct users currently eligible in at least one activated entity; do not sum branch totals              |
   | Members who attended      | Distinct users with at least one recorded attendance in the selected period                               |
   | Attendance by branch      | Recorded visits at each branch; one person may contribute to several branches                             |
   | New members               | First student enrollment within this organization falls in the selected period                            |
   | Membership payment status | Paid, within grace, and blocked assignments for the selected month; count each shared assignment once     |
   | Session use               | Reserved places against available places, by branch and period; exclude unlimited sessions from the ratio |

   Example: Alex belongs to BJJ and gym and visited only BJJ. Count one person for the organization, one enrolled member in each branch, and attendance only at BJJ. Label branch totals as enrollments where they can count the same person twice.

   Use the existing organization-owner authorization and server-side entity-scoped aggregation. Never weaken entity row-level security to build the dashboard. Do not show revenue estimates from memberships because a paid/unpaid tracker does not establish collected amounts.

**Settled product details**

Decided 2026-09-03, recorded in ADR 126. Nothing here is open.

- **Membership calendar timezone.** One owner-selected organization timezone, on `membership_policy`, suggested from the default entity when the organization is created. Every deadline for a shared membership is computed in it, so the membership expires at one moment everywhere.
- **Grace applies to unpaid renewal only.** Removing an entity from a plan, cancelling a membership, and suspending an assignment or a branch membership all take effect immediately. Grace is a payment allowance, not a notice period.
- **Out of the first version.** Multiple rooms and simultaneous sessions in one general branch. Unlimited visits and several concurrent memberships stay as the defaults.

Manual paid/unpaid tracking was explicitly added by the owner after the earlier no-payment scope. This permits the minimum monthly status, grace, warnings, and cancellation behavior. It does not authorize online payments or the earlier full shared-billing design.

**Lessons learned**

- Treat membership structure and payment collection as separate scopes. Do not add billing, renewal, or financial migration work unless requested.
- Separate where a record is owned from where users manage it. A shared membership can be assigned from an entity member profile.
- When a later decision adds manual payment tracking, replace the earlier scope exclusion consistently without expanding it into payment processing.

## Rollback

Written by step 6.6 on 2026-09-04. The rule from the plan's rollout section: a
rollback stops NEW branch creation and membership editing, and keeps eligibility
enforcement, history and cancellation running for branches already activated.
Removing the checks would open a restricted branch to everybody, which is worse
than the problem any rollback is trying to fix.

**Level 1, stop it spreading.** Turn the flag off for the organization. New
general branches cannot be created; everything already there keeps working.

```sql
UPDATE "organization" SET general_branches_enabled = false WHERE id = '<org>';
```

**Level 2, stop the gate deciding at one branch.** Clear the activation and that
branch falls back to the legacy per-branch dues gate, which is what every
un-migrated academy already runs on. Memberships, months and history stay.

```sql
UPDATE "entity" SET membership_enforced_at = NULL WHERE id = '<entity>';
```

Do NOT clear this on a general branch that people are booking: it has no legacy
dues rows, so the legacy gate would admit everybody, which is the "accidentally
open a restricted branch" failure the rollout section warns about. For a general
branch, suspend the assignments or close the branch instead.

**Level 3, stop the background work.** Nothing is scheduled: `/api/cron/memberships`
is manually called, exactly like `/api/cron/materialize`. There is no cron entry
to remove, and not calling it is the whole rollback. Booking and admission
enforce the deadline themselves, so a sweep that never runs costs nobody a
wrongly kept place; it only leaves stale bookings in a list.

**What a rollback must NOT do.**

- Do not drop the tables or revert the migrations. All eight are additive or
  widen a constraint, they are applied append-only, and dropping them would take
  the payment history with them.
- Do not remove the eligibility checks. A branch already activated depends on
  them; without them it admits anybody who can reach it.
- Do not delete assignments to "clean up". Suspending one is reversible and
  visible; deleting is neither.

**Undoing the pilot data**, which is separate from a rollback and safe on dev:
`pnpm -F @matops/db seed down` removes the pilot organization, both general
branches and all six access tables' rows for it, children first. It is guarded
by `assertDevDatabase`, so it refuses to run anywhere but dev.
