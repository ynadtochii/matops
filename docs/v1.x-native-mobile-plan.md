## 0. What can proceed WITHOUT an Apple Developer account

The key fact: `getExpoPushTokenAsync` + remote delivery go through **Expo's** push
service, not APNs directly. So an Apple Developer account only matters for the
**iOS remote-delivery leg** and **installing on a physical iPhone**. Everything
else needs no Apple account. Also confirmed in `apps/expo/src/utils/push.ts`:
iOS **simulator** returns `null` immediately (`if (!Device.isDevice) return null`),
so iOS push is only ever testable on a real device — which itself needs the Apple
account for signing. Android has no such block.

### ✅ Doable + testable now — no Apple account

- **Steps 1–2 (config):** `eas init` + uncomment `extra.eas.projectId`; add
  `expo-notifications` to `plugins`. Free Expo account. Verified by
  `pnpm lint typecheck test`.
- **Full server + domain pipeline (already built):** message builders, `notify.ts`
  helpers, `runReminderSweep`, `getPushTargets`, `push_token` upsert, `pushToken`
  router — pure TS. Unit-test the sweep end-to-end with a fake `sendPush`. Worth
  doing regardless.
- **Android push — complete end-to-end:** Android uses **FCM** (free
  Google/Firebase account, no Apple). Create a Firebase project, upload the FCM v1
  service-account key to EAS, build an Android dev-client
  (`eas build -p android --profile development`, or local), install on an Android
  phone/emulator with Google Play. Register a real token, run the cron sweep, see a
  real push arrive + tap-route. This proves ~90% of the pipeline (transport, cron,
  message content, deep-link routing) with zero Apple involvement.
- **iOS Simulator local/simulated push (only if you have a local Mac + Xcode 14+):**
  `xcrun simctl push <device> com.matops.app payload.apns` exercises `push-sync.tsx`
  tap-routing + the foreground handler — but NOT token minting or the Expo→APNs
  delivery leg. Needs a simulator build with the notifications entitlement (the
  headless build env lacks Xcode, so this is local-Mac only).
- **Widget JS half:** the in-app snapshot writer (step 9) — `nextBookableClass` +
  formatters writing `widget-snapshot.json` — is plain JS, unit-testable now. The
  **Android** widget (`react-native-android-widget`, step 11) is testable on
  Android with no Apple account.

### ⛔ Blocked until we have an Apple Developer account

- iOS remote push on a real iPhone — needs an APNs key (paid account) + device
  signing.
- Installing any build on a physical iPhone — development signing needs the account.
- iOS WidgetKit target on device (step 10) — App Group entitlement + device signing.
- `aps-environment` entitlement in a real iOS build (iOS side of steps 3–4).

### Recommended no-Apple-account order

1. Steps 1–2 (config) + verify the server pipeline with tests — no devices.
2. Firebase/FCM + Android EAS build → test the full push loop on Android (proves
   the whole pipeline).
3. Snapshot writer + Android widget — testable on Android.
4. Leave iOS device/APNs/WidgetKit as a clearly-marked "needs Apple Developer
   account" fast-follow.

**Why nothing is delivered today — three concrete gaps, all in native/infra config:**

1. **No EAS project id.** `apps/expo/app.config.ts` has the `extra.eas.projectId`
   block **commented out**. `getPushToken()` (push.ts) explicitly returns `null`
   when `projectId()` is undefined, so a token is *never minted or registered*.
   This is the single hard blocker.
2. **No `expo-notifications` config plugin.** The `plugins` array in
   `app.config.ts` lists `expo-router`, `expo-secure-store`, `expo-web-browser`,
   `expo-splash-screen` — but **not** `expo-notifications`. Without it there's no
   iOS push entitlement/`aps-environment`, no Android notification
   channel/icon/color.
3. **No push credentials at the provider.** iOS needs an APNs key uploaded to EAS;
   Android needs an FCM v1 service account / `google-services.json`.
   `EXPO_ACCESS_TOKEN` in Vercel is optional (only for enhanced security) — the
   transport already degrades to a no-op when unset.

Everything else (permission prompt, foreground handler, deep-link tap routing to
`/class/[id]` and `/schedule`, sign-out unregister, idempotent server upsert) is
already wired and guarded to no-op safely on simulators.

### Relevant constraints (from CLAUDE.md / ADRs)

- No simulator/Xcode in the CI/build env → all device-only work is a deferred
  fast-follow; that's why these stalled.
- iOS native project is already prebuilt and committed
  (`apps/expo/ios/matops.xcodeproj`, `EXNotifications.podspec` present) — but a
  prebuilt native folder means adding config-plugin-driven native changes
  (notifications, widget target) requires a **re-prebuild or manual native edit**;
  the committed `ios/` can drift from `app.config.ts`.
- Cron cadence: class reminders want ~15 min; current `/api/cron/remind` runs
  **daily** (`30 3 * * *`). Sub-daily needs Vercel Pro. Dues reminders are fine
  daily.
- `CRON_SECRET` must be set in Vercel or the cron refuses to run in production.

## 2. Proposed design

Two tracks, sequenced. Track A (push activation) is low-code, high-value, and
unblocks the reminder pipeline already written. Track B (widget) is the native
fast-follow.

### Design rationale / key decisions

- **Activate, don't rebuild.** The correct move is configuration + credentials,
  not new abstractions. Resist adding a server-side "notification preferences"
  model — S7's decision (deliberate, see profile.tsx comment) is that "off" = no
  token registered = nothing sent. Keep it.
- **Fix the prebuilt-`ios/` drift risk.** Adding `expo-notifications` (and later
  the widget target) via config plugins is the managed path. Decide explicitly:
  either (a) delete the committed `ios/`/`android/` and treat them as CNG output
  (regenerate via `expo prebuild` / EAS), or (b) keep them checked in and apply
  native changes by hand + keep plugins in sync. **Recommend (a)** — the guide and
  Expo workflow both assume CNG; a committed `ios/` that predates the
  notifications plugin is a latent source of "works in config, missing in build."
- **Widget stays read-only + deep-link** (locked in ADR 27 / the guide). No auth
  or API in the widget process. App writes a tiny snapshot; widget renders +
  deep-links `matops://class/<id>`. Ship `class/<id>` first, upgrade to one-tap
  `book/<id>` later.
- **One selection function** (`nextBookableClass`) feeds F.1 card *and* widget
  snapshot — they can't diverge.
- **Cadence:** ship push on the existing daily cron (dues + best-effort class
  reminders); treat the ~15-min class-reminder cadence as a separate infra
  decision (Vercel Pro or external scheduler), not a blocker for turning push on.

## 3. API contracts / interfaces (all already exist — no changes needed)

```ts
// tRPC — packages/api/src/router/pushToken.ts   (BUILT)
pushToken.register(  { token: string; platform: "ios"|"android"; deviceId?: string } ) => { ok: true }
pushToken.unregister({ token: string } ) => { ok: true }

// transport — packages/notifications/src/expo-push.ts   (BUILT)
sendPush(tokens: string[], { title, body, data? }): Promise<{ sent: number; ok: boolean }>

// domain selection — packages/domain (schedule.ts)   (BUILT, reused by F.1 + widget)
nextBookableClass(classes, now): Class | null

// notify helpers — packages/api/src/notify.ts   (BUILT)
notifyClassCancelled / notifyClassChanged / notifyMembershipApproved / runReminderSweep
```

New surface required for Track B only (the widget snapshot — a file contract, not
an API):

```jsonc
// widget-snapshot.json  → App Group (iOS) / SharedPreferences (Android)
{ "academyName": string, "classId": string, "title": string,
  "whenLabel": string, "spotsLabel": string,
  "state": "bookable"|"booked"|"empty", "updatedAt": ISO8601 }
```

## 4. Data flow

**Push (per event):** app registers token on sign-in → `push_token` upsert (base
conn, idempotent on unique token) → domain/cron builds message →
`getPushTargets(userIds)` resolves tokens+emails cross-academy → `sendPush` chunks
(≤100) to Expo Push → APNs/FCM → device → tap → `push-sync` routes by `data.type`
(`class`→`/class/[id]`, `approved`→`/schedule`, `dues`→profile).

**Widget:** app fetches `class.mine` → `nextBookableClass(data, now)` → format
`whenLabel`/`spotsLabel` (same utils as F.1) → write snapshot to shared store →
`WidgetCenter.reloadAllTimelines()` (iOS) / `updateAppWidget` (Android) → widget
renders → **Book** fires `matops://class/<id>` → app opens `/class/[id]` →
existing `booking.book`.

## 5. Implementation plan

**Track A — turn push ON (mostly config; unblocks all Phase-4 notifications):**

1. Create/link the EAS project (`eas init`); set `extra.eas.projectId` in
   `apps/expo/app.config.ts` (uncomment the block).
2. Add `expo-notifications` to the `plugins` array (icon, color, Android channel).
3. Decide the prebuilt-native strategy: regenerate `ios/`+`android/` via CNG
   (recommended) or hand-patch entitlements. Ensure `aps-environment` + Android
   channel land in the build.
4. Upload push credentials to EAS: iOS APNs key; Android FCM v1 (service account /
   `google-services.json`).
5. EAS dev build on a **real device** (no simulator receives push); confirm token
   registers (`push_token` row appears) and a `sendPush` test arrives + taps route
   correctly.
6. Set Vercel env: `CRON_SECRET` (required), optionally `EXPO_ACCESS_TOKEN`,
   `RESEND_API_KEY`/`RESEND_FROM` for the email leg.
7. Verify the daily `/api/cron/remind` sweep delivers class + dues reminders
   end-to-end on device.
8. Update `docs/mobile-device-test.md` with the push checklist; flip roadmap
   cells; CHANGELOG line.

**Track A+ — cadence (separate infra call):** move class reminders to ~15-min cron
(Vercel Pro cron, or an external scheduler hitting the same protected route). Dues
stay daily. No code change — the sweep is already idempotent and bounded.

**Track B — widget (native fast-follow, per `docs/home-widget-implementation.md`):**

9. Add the in-app snapshot writer (on schedule fetch + app foreground/background),
   reusing `nextBookableClass` + F.1 formatters.
10. iOS: App Group `group.tech.matops.app` on both targets; WidgetKit
    `TimelineProvider` reading the snapshot; `widgetURL(matops://class/<id>)`; wire
    via `@bacons/apple-targets` config plugin.
11. Android: `react-native-android-widget` provider reading SharedPreferences;
    Book `PendingIntent` firing the deep link; `WorkManager` refresh.
12. EAS build + device verification; add widget checks to
    `docs/mobile-device-test.md`.

**Recommended sequence:** Track A (1–8) first — it's low-code and lights up the
entire already-built reminder system for the least effort; Track A+ if
class-reminder timeliness matters at launch; Track B last (largest native surface,
off the critical path).
