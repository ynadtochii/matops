# First release: one BJJ academy

## Goal

Release one simple, complete BJJ academy booking workflow on the web. Keep the organization and academy structure so the same business can add academies later. This plan records decisions and work still to do. It does not authorize deployment, database resets, or sending messages.

## Design authority

The current user decisions and this file define this release. Older specs, ADRs (including ADR 135), the project `CLAUDE.md`, roadmaps, and release plans describe earlier choices. The repo has a fresh baseline in `packages/db/migrations/`: `0000_baseline` to `0004_first_release_drops`. Use them to understand existing behavior, not as requirements to keep payment-based admission or extra features. Change active product docs when the code changes. Do not treat this plan as implemented.

## Decisions

1. Keep the existing organization, entity, person, entity membership, academy-scoped class data, entity URLs, and tenant authorization. An organization is the owner group; a typed `bjj_academy` entity is the place. Keep independent academy schedules, rosters, and join codes. Do not merge these records, split the app, rename the model, or build a general facility product. Changed 2026-09-27: the multi-academy web screens are gone (gym overview, People, the person page, Gym settings, the academy selector). The data model, entity URLs and tenant authorization stay, so a later release can add a second academy.
2. The pilot starts with one academy. An approved, active student can book without a plan, payment claim, or good payment standing. Pending, suspended, archived, and removed students cannot book. Keep booking-window, class-state, capacity, cancellation, and tenant checks. Billing stays outside Matops. "Strict scope" does not mean Stripe.
3. Deliver the weekly loop: create the academy, set its time zone and recurring classes, invite and approve a student, book and cancel on the web, handle changed or cancelled classes, finish attendance, and correct an error. Keep notice recovery and safe calendar extension.
4. Show the academy directly when there is one. Do not require owners to learn business versus branch navigation, general spaces, dashboards across academies, or payment setup before their first booking. Reveal academy switching and organization overview when more than one academy exists.
5. Hide independent optional features through existing clean gates. If hiding needs new flags, duplicate rules, fake empty states, or repeated backend/frontend exceptions, remove the blocked feature and its callers end to end. Keep privacy, security, export, recovery, and safe delete controls even if they do not fit the main navigation. Changed 2026-09-27: the optional features and their screens are removed, not hidden. Reception, public booking, referrals, curriculum and general spaces are gone with their procedures, tests and tables.
6. Inspect actual data and the exact database target before dropping tables, migrating data, or disabling a public link. Production is empty today (Decision 9); recheck before relying on it. On dev, preserve records only when a seed cannot rebuild them. Removing billing or general-space code must not remove future multi-academy BJJ support.
7. Change backend and frontend together. Update web, public and staff booking entry points, direct URLs, warnings, and empty states for every changed contract. Hiding a button does not change server authorization.
8. Payment admission is off for the pilot, not gone. A later release will turn it back on, through manual plan assignment or a payment provider. Keep the server seam: `entity.membershipEnforcedAt`, `packages/api/src/payments-gate.ts:bookingGate`, and `entity.setMembershipEnforced`. A null `membershipEnforcedAt` already means approval-only booking. New academies default to null. Clients hide payment UI by reading this one flag (`academy.current().membershipEnforced`), not a new flag. Payment UI that cannot be gated cleanly on the flag is removed from the web client; its server procedures stay if the later release needs them. Changed 2026-09-27: `entity.setMembershipEnforced` and its switch are removed. Turning payment on needs a later release or a direct database change. `bookingGate`, `entity.membershipEnforcedAt` and the payment code stay.
9. Production holds zero academies (confirmed by the user 2026-09-26). No backfill, data fill, or compatibility deploy is needed. Migrations may change the schema freely, but they stay structure only. Dev data is rebuilt with the seed. Recheck production is still empty before the first real invitation.
10. Web only. The Expo app is out of scope: do not change it, and do not check it on a device. It calls the same API, so server changes still reach it; record any Expo screen that breaks as a known issue, not a blocker.
11. The owner can override and correct everything in their academy. The owner can book and cancel for any student, and correct any attendance. S0 records the exact rules the owner path skips. Proposed default: the owner skips the booking window and the payment gate, but not tenant checks, deleted or cancelled classes, or the reason required for attendance older than 14 days. Instructors keep the current rules. Changed 2026-09-27: the owner "book past the window" server path is removed with `booking.bookFor`. Owner cancel (`booking.cancelFor`) and attendance correction stay.
12. Browser checks are skipped for this release (user decision, 2026-09-27). Wherever a step or release check asks for a browser walk, the evidence is lint, typecheck, focused tests the user runs, and server smokes through the real router against dev. What only a screen can show (layout, copy, which menu items render) is not verified by a person in this release.

Do not infer completion from older docs or a checked item elsewhere. At the end of each session, update `Current step` and `Progress log` in this file with changed paths, decisions, exercised checks and results, known risks, and the next concrete action. Check a step only when its completion conditions have evidence; leave external checks unchecked and record who or what is needed. Do not run tests without an explicit user request. Run lint and typecheck after code edits. For significant behavior changes, run a direct smoke scenario; static checks alone do not prove the flow. ### Owner override rules (Decision 11)

- Only `booking.bookFor` and the new `booking.cancelFor`, and only when `isOwner(ctx.membership)` (role `owner`). Managers and instructors keep the current rules.
- The owner skips: the booking window (`too-far-ahead`) and the payment gate. The booking is `confirmed`.
- The owner does not skip: tenant scope (`withScope`, `findBranchPerson`), deleted class (NOT_FOUND), cancelled class, a class that already started (`past`: attendance covers that), strict capacity (`claimSeat`; BJJ classes default to `soft`, so it never refuses there), and the student must still be an active member (a pending or suspended student is not bookable by anyone).
- Attendance: unchanged. The owner can correct any day; older than 14 days needs a reason.

### Visitor rule

Visitors on `/book/<code>` and at `/reception` never pass `bookingGate`, so the payment flag does not touch them. No approval and no plan: a visitor booking writes a `drop_in` lead and a `drop_in_visit`. Public booking stays off by default per branch (`academy_profile.public_booking_enabled`). Converting a visitor into a student stays a manual `dropin.promote`.
