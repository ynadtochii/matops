# Review plan: PR #4, the organization owns typed entities (v7.2)

**Target:** `origin/main...origin/dev`, 191 files, +31010 / -1379.
**Lenses:** architecture and security only. Nothing else.
**Reviewable churn after exclusions:** about 6700 lines across 140 files, split into 8 segments below.

Merging this PR deploys to production and applies migrations `0042`-`0047` against a database that
holds real academies. Treat it as a production change, not a refactor.

---

## 1. What is in scope

Two lenses, nothing else:

**Architecture.** Does the new tenant model hold together? Are boundaries in the right place, is
state owned once, does the code survive a second academy, a deploy, a rollback, and the next feature?
Coupling, duplicated truth, leaks between layers, dead paths left behind, and the cost of the
migration itself.

**Security.** Can one academy read or write another academy's rows? Can a client promote itself by
naming a different entity? Does a check fail open anywhere? Does data reach a screen or an API
response that should not have it?

### The invariants the PR claims

Every finding should be traceable to one of these being broken.

| # | Invariant |
|---|---|
| I1 | An **organization** holds only name, slug, logo. No place data. |
| I2 | An **entity** (`bjj_academy`) holds the place: name, time zone, country, address, map link, six-digit code. Per-academy settings live on `academy_profile`. |
| I3 | `entity_membership` is the only operational access record. Approve, suspend, archive, remove act on one entity. |
| I4 | The client names the entity in `x-matops-entity` on every request. The session never picks it. |
| I5 | A missing header is `BAD_REQUEST`, a foreign or unknown one is `FORBIDDEN`, **both before a transaction opens**. |
| I6 | `academy_id` and `app.academy_id` keep their names and hold an **entity** id. `app.organization_id` sits beside them. No BJJ table carries `organization_id`. |
| I7 | Creating a gym makes one organization and one default entity whose **id equals the organization id**, through one idempotent `provisionOrganization`. |
| I8 | Twelve `member_id` columns key on `entity_membership.id`, held by ten composite foreign keys. |
| I9 | `/overview` reads one entity at a time and combines on the server. It never reads across entities in one query. |
| I10 | The only writes allowed on the base (non-RLS) connection are the Better Auth identity tables and the two enumerated seam exceptions. |

## 4. How to review

### Protocol per segment

1. Pull only your slice:
   `git diff origin/main...origin/dev -- <paths for your segment>`
2. Read the **full current file** for anything you flag, not the hunk. A tenant bug is usually in
   what the diff did not touch.
3. For a security claim, name the concrete path: who calls it, with what header, what row comes back.
   "Could be unsafe" is not a finding.
4. Check the claim against the invariant table. Quote the invariant number.
5. If a test already pins the behaviour, say so and drop the finding to a note.

### Finding format

```
[SEV] <one-line claim>
file: packages/api/src/trpc.ts:312
invariant: I5
failure: <concrete inputs and state, then the wrong result>
evidence: <the lines, or the query, or the migration ordering>
fix: <the smallest change that closes it>
```

### Severity

- **S1 blocker.** Cross-tenant read or write, auth check that fails open, data loss, a migration that
  breaks production on deploy. Merge stops.
- **S2 serious.** Wrong behaviour under a real scenario (second academy, suspended member, rollback),
  or an architectural decision that will be expensive to unwind. Fix before pilot.
- **S3 note.** Debt, inconsistency, missing test on a stated invariant. Log it, do not block.

Rank findings most severe first. An empty segment result is a valid result. Do not pad.

### Rules

- No fabricated line numbers. Open the file.
- Do not propose refactors the PR did not ask for. The lens is "is this safe and sound", not "is this
  how I would build it".
- Do not run the test suite. Do not run migrations. Read-only, plus `psql` reads if a segment says so.

### S1. Migrations and deploy safety — highest risk

**Files**
```
packages/db/migrations/0042_entity_foundation.sql
packages/db/migrations/0043_entity_rls.sql
packages/db/migrations/0044_invite_names_the_entity.sql
packages/db/migrations/0045_bjj_tables_name_the_entity.sql
packages/db/migrations/0046_rows_name_their_membership.sql
packages/db/migrations/0047_the_organization_stops_being_an_academy.sql
packages/db/migrations/meta/_journal.json
packages/db/src/seed/wipe-academies.sql
apps/nextjs/package.json (vercel-build), packages/db/src/env-guard.ts (context, unchanged)
```
~130 lines of SQL. Small file, largest blast radius.

**Questions**

1. **The rolling deploy window.** A migration lands while the OLD deployment is still serving, for
   the length of a build (CLAUDE.md states this rule). `0047` drops nine columns from `organization`
   plus `member.status` and `member.invited_role`. Production code currently reads those columns.
   What happens to live requests between the migration commit and the promotion of the new build?
   Is `0047` safe to run in this PR at all, or does it belong in a later deploy? This is the single
   most likely S1 in the whole PR.
2. **`0046` against real rows.** CLAUDE.md records that dev was **wiped and reseeded** between `0045`
   and `0046`, because `0046` cannot apply to rows whose `member_id` still names a Better Auth
   member. Production has real academies and was never wiped. Does `0046` apply cleanly to production
   rows, or does it fail the foreign key and block the deploy? Is there a backfill, and if so, where
   does it live?
3. **Structure-only rule.** Migrations carry no `UPDATE` / `INSERT` / backfill (CLAUDE.md, "Phase 0
   gotchas"). Do `0042`-`0047` obey it? If a backfill is needed for correctness and is missing, that
   is a finding either way: either the migration breaks the rule, or the data is left wrong.
4. **Locks.** `0045` adds a foreign key `academy_id -> entity.id` on 18 tables; `0046` adds ten
   composite foreign keys. Are these validated in place, and what does that lock and for how long on
   a live table? Is `NOT VALID` plus a later `VALIDATE` warranted?
5. **RLS completeness on the new tables.** `0043` enables RLS and adds policies for `entity`,
   `entity_membership`, `academy_profile`. Are the four `matops_app` grants present, from `0001`'s
   `ALTER DEFAULT PRIVILEGES` or explicitly? Is `FORCE ROW LEVEL SECURITY` needed or deliberately
   absent? Compare against how every prior tenant table was set up.
6. **The organization-scoped policies.** `entity` and `entity_membership` match on
   `app.organization_id` only, not on the entity. Confirm this cannot expose a sibling academy's
   product data through a join, and that an organization transaction (entity GUC unset) reads exactly
   the rows it should.
7. **Journal `when` stamps.** `_journal.json` gained six entries. Per CLAUDE.md, `drizzle-kit`
   silently skips an entry not newer than the last applied row and still reports success. Are the six
   `when` values strictly increasing and past `0041`?
8. **Rollback.** If the deploy fails after `0047`, what is the path back? `0047` is destructive and
   drops data (`public_api_key`, `public_api_origins`, `country`, `address`). Is that data copied to
   `entity` / `academy_profile` first, and where?

**Optional evidence.** Read-only queries against the **dev** branch are allowed, using
`.claude/skills/debug/scripts/sql.sh`. Never touch production.

### S2. The tenant seam — the security core

**Files**
```
packages/api/src/trpc.ts                    (+213 / -62)
packages/db/src/tenant.ts                   (+34 / -15)
apps/nextjs/src/app/api/trpc/[trpc]/route.ts
apps/nextjs/src/trpc/server.tsx
apps/nextjs/src/trpc/react.tsx
packages/auth/src/index.ts                  (+12 / -62)
```

**Questions**

1. **Header trust.** `x-matops-entity` is attacker-controlled on every request. Walk
   `resolveEntity()` line by line. Is there any path where an entity id reaches `withScope` before
   `getEntityInOrganization` and `getEntityMembership` have both answered? (I5)
2. **The synthetic owner membership.** When an organization owner has no `entity_membership`,
   `resolveEntity` builds `{ ...orgMembership, role: "owner", status: "active" }`. Two things to
   chase: (a) is `isActiveMember(orgMembership) && isOwner(orgMembership)` the only gate, and is it
   evaluated against the *organization* membership as intended; (b) that object spreads
   `orgMembership`, which carries a Better Auth `member` id. If any resolver writes `member_id` from
   `ctx.membership`, it writes a Better Auth member id into a column whose composite foreign key now
   points at `entity_membership` (I8). Grep every write of `member_id` and check which id it takes.
3. **Fails closed before the transaction.** Confirm no `withScope` opens before authorization, on
   every tier: `enrolledProcedure`, `memberProcedure`, `staffProcedure`, `ownerProcedure`,
   `organizationMemberProcedure`, `organizationOwnerProcedure`, `identityProcedure`,
   `organizationOwnerIdentityProcedure`.
4. **The identity procedures bypass RLS by design.** They hand the resolver a base connection and an
   explicit `ctx.withScope`. Enumerate every procedure built on them and every write they perform.
   Does any of them write a tenant table on the base connection? (I10)
5. **GUC hygiene under pooling.** `withScope` sets role and both GUCs with `set_config(..., true)`.
   Confirm transaction-local in every branch, including the organization-only branch, and that a
   thrown resolver cannot leave a connection with the role or GUC still set on Neon's transaction
   pooler.
6. **The organization-only transaction.** `withScope` omits `app.academy_id` for organization scope,
   so entity policies match nothing. Check no organization-scoped resolver reads a tenant table and
   silently gets zero rows where it expected data (a fail-closed bug that reads as an empty screen).
7. **RSC and caching.** `apps/nextjs/src/trpc/server.tsx` and `react.tsx` now carry the entity per
   request. The app runs Cache Components (ADR 91) and a server prefetch on every route (ADR 88). Can
   a cached or deduped server render serve entity A's data into entity B's page, or one user's data
   to another? Check what the cache key includes.
8. **Client cache across a switch.** The selector switches by link, not mutation. Does the TanStack
   Query cache carry entity A's rows into entity B's screens on a soft navigation?
9. **What `packages/auth` lost.** 62 lines removed. Confirm nothing that was an authorization check
   moved into a place where it is now advisory or skipped.

### S3. Entity, membership and provisioning data layer

**Files**
```
packages/db/src/entity-schema.ts            (+170)
```

**Questions**

1. **`provisionOrganization` idempotency.** It claims to be idempotent and to make the default
   entity's id equal the organization id (I7). What happens on a concurrent double call, a retry
   after a partial failure, or a second sign-in racing the first? Is there a unique constraint doing
   the work, or only application logic?
2. **The id equality decision.** `entity.id === organization.id` for the default entity. Architectural
   lens: what breaks later because of it? List the places that now cannot tell the two apart, and
   whether any authorization check accidentally passes because the ids match.
3. **`membership.ts`, 421 new lines.** Approve, suspend, archive, remove, and the last-owner rule now
   act on one entity. Can the last owner of an organization lose access to every entity? Can a
   suspended member at academy A act at academy B? Does removal at one academy leak into the other?
4. **`member_id` sourcing (I8).** Every insert into the twelve tables carrying `member_id`. Which id
   does each one write? A single caller still writing a Better Auth member id is an S1 data
   corruption path.
5. **Erase and delete.** `erase.ts` gained 76 lines. Does permanent erase now cover `entity`,
   `entity_membership`, `academy_profile`? Does deleting one academy leave orphans, and does it
   correctly close one mat rather than the whole gym (the PR body claims this was fixed)?
6. **Six-digit code uniqueness.** The code moved from `organization` to `entity` and `0047` dropped
   `organization_public_code_unique`. Is uniqueness still enforced at the database level, and over
   what scope? A collision means one gym's join QR opens another gym.
7. **Invites.** `0044` repoints `academy_invite` at `entity`. Can an invite issued for academy A
   admit someone to academy B? What happens to invites that existed before the migration?

## 6. Cross-cutting checks

Assign these to one reviewer over the whole diff, not per segment.

1. **The deferred rename.** `academy_id` holds an entity id in 818 places across 131 files (ADR 124
   out-list). Where does that ambiguity actually bite: any place a reader could pass an organization
   id where an entity id is expected and get a silent wrong answer rather than an error. The
   `ctx.academyId = entity.id` alias in `trpc.ts` is the first thing to check.
2. **Error messages.** `publicErrorMessage` only masks `INTERNAL_SERVER_ERROR` in production. Do the
   new `FORBIDDEN` and `BAD_REQUEST` messages tell an attacker anything, for example whether an
   entity id exists?
3. **Logs.** `timingMiddleware` logs every path. Does anything new log an entity id, a member id, or
   a header value that should not reach the console?
4. **Dead code.** Three components deleted, twelve files moved. Grep for anything still importing the
   old shape, and for columns dropped by `0047` still read anywhere in the tree.
5. **Stated but untested invariants.** For I1 to I10, name which have a test and which do not. Do not
   review the tests, just report coverage of the invariant.
