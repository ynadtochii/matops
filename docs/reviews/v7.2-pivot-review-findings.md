## Segment 1 — Migrations and deploy safety

Files read in full: `0042`-`0047`, `0001_tenant_rls.sql`, `0003_grant_app_role.sql`,
`meta/_journal.json`, `packages/db/scripts/deploy-migrate.mjs`,
`apps/nextjs/package.json`, `packages/db/src/provision.ts`, `packages/auth/src/index.ts`,
`packages/api/src/router/academy.ts` (create), `docs/beta-launch-plan.md` §1.1-1.3.

### The premise that decides this segment

**Production is empty.** Confirmed by the repository owner on 2026-09-02: the production Neon branch
holds no organizations and no rows; the branch with the old test data (Alma beta, the fakes) is the
dev one. That is the state `docs/organization-entity-pivot.md` was written for ("Production is empty
and dev is rebuilt with `pnpm db:seed`. No data is preserved", Decision 16), and it still holds.

This review first ran against the opposite premise, because `CLAUDE.md` says the production branch
"holds only real academies", `docs/beta-launch-plan.md` §3.4 says the Alma beta demo lives in the
production database, and the review plan opens by stating the migrations run "against a database
that holds real academies". **On an empty database every one of those blockers is void.** They are
recorded below as checked-and-not-applicable rather than deleted, because the same six migrations
become unsafe the moment the first real gym signs up, and because the next reader deserves to know
the question was asked.

**Void on an empty production database:**

- `0045`/`0046` add 28 foreign keys to `entity` / `entity_membership`, which no migration or script
  ever fills. With zero rows in the eighteen BJJ tables there is nothing to validate, so they apply
  cleanly. (With rows, they cannot: CLAUDE.md records dev being wiped between `0045` and `0046` for
  exactly this reason.)
- `0047` drops nine `organization` columns plus `member.status` and `member.invited_role`. Nothing
  is lost because nothing is stored, and the build-window outage it would cause needs a live request
  to hurt.
- `0042` turns `member_by_org_user` into a unique index. No rows, no duplicates, no failure.
- No organization exists that predates the deploy, so the missing repair path for one does not fire.

**The first gym to sign up does so on the new code**, so `provisionOrganization` runs for it and it
gets its entity, profile, owner membership and curriculum track from the start.

### Findings

```
[S3] 0047 still belongs in its own deploy, and this is the last cheap moment to
     move it
file: packages/db/migrations/0047_the_organization_stops_being_an_academy.sql
failure: `deploy-migrate.mjs` runs inside `vercel-build`, minutes before the new build is
  promoted, so `0047` lands while the OLD deployment is still serving. That deployment's
  `getMembership` selects `member.status` (`git show origin/main:packages/db/src/membership.ts:38`)
  on the path of every authenticated request, and its academy screens read
  `organization.public_code`, `time_zone`, `address` and the two public-booking columns.
  On an empty database nobody is making those requests, so the cost today is zero. Two things
  still argue for splitting it out:
  (a) it breaks the rule this repo wrote down for itself — `docs/beta-launch-plan.md:216-220`,
      "add columns and tables freely, drop one only in a later deploy, after the code that used
      it is gone" — and a rule that gets an exception the first time it is tested is not a rule;
  (b) it makes this deploy a one-way door. There are no down migrations anywhere in the repo, so
      once `0047` runs, redeploying the previous build puts the old code on a schema it cannot
      read a single authenticated request against. `0042`-`0046` are all additive and roll back
      for free.
fix: move `0047` to the next deploy. Nothing in the new code needs those columns gone.
  If it ships as-is, that is a defensible call on an empty database — make it deliberately, and
  do not let it become the precedent for the next contract migration.
```

```
[S3] An organization whose provisioning dies half way cannot be repaired by any
     user action
file: packages/db/src/provision.ts:142 (`provisionOrganization`)
      packages/auth/src/index.ts:105, packages/api/src/router/academy.ts:303 (the two callers)
invariant: I7
failure: the pivot plan promises "Make incomplete provisioning recoverable by retrying missing
  steps", and `provisionOrganization` delivers the retry: every insert is an
  `onConflictDoNothing`, so a second run makes only what is missing. But both call sites sit in
  the CREATE path. `afterCreateOrganization` runs inside Better Auth's create, and
  `academy.create` calls `createOrganization` FIRST and only then re-runs the provisioner — so
  it repairs the organization it just made, never an older one. If the hook throws after Better
  Auth has written the `organization` row and the user's request dies before `academy.create`'s
  belt-and-braces call, that organization has no entity, and the owner's only route back is
  "Start a gym", which makes a second organization. On an empty production database this is a
  first-week risk rather than a live one, and it is the same gap that would have stranded every
  existing gym had production not been empty.
fix: call `provisionOrganization` from the post-login gate when the session's active organization
  has no default entity. It is idempotent by design and already runs on the base connection, so
  it is a few lines in `resolveOrganization`'s caller rather than in the hot path.
```

```
[S3] 28 foreign keys are added and validated in place, with no NOT VALID + VALIDATE split
```

```
[S3] entity_membership RLS matches the organization only, so within an entity
     transaction a member of academy A can read academy B's membership rows
file: packages/db/migrations/0043_entity_rls.sql:14-17
invariant: I3, I6
failure: the policy is `organization_id = current_setting('app.organization_id', true)`. Inside an

  into the routers. Segments 3 and 4 checked every reader and found the `where` clauses correct
  today (`requireMember` compares `academyId`, `writeMembership` filters on `entity_id`).

  that these two tables are organization-wide and every read of them must carry its own entity
```

### What this segment confirms and what it could not

- **Confirms:** the structure-only rule is obeyed exactly — `0042`-`0047` contain no `INSERT`,
  `UPDATE` or backfill. Journal `when` stamps are strictly increasing, one day apart, and run ahead
  of the real clock as CLAUDE.md requires (`0041` 2026-09-08 → `0047` 2026-09-14), so
  `drizzle-kit migrate` cannot silently skip the wave, and `deploy-migrate.mjs` asserts the applied
  count against the journal afterwards. RLS is enabled with one policy each on all three new tables;
  the four `matops_app` grants come from `0001`'s `ALTER DEFAULT PRIVILEGES`, which covers tables
  created later by the same migration role. `FORCE ROW LEVEL SECURITY` is absent on the new tables
  exactly as it is absent on all 20 existing ones — correct, because the app never runs as the table
  owner, it `SET LOCAL ROLE matops_app`.
- **Could not confirm:** nothing. The one open question — whether production holds rows — was
  answered by the owner rather than by a query, since the plan forbids touching production and no
  credentials for it are on this machine.
- **Doc fix worth making with this PR:** `CLAUDE.md` ("the production branch, which was emptied and
  rebuilt from `0000` and holds only real academies") reads as though real gyms are live on it, and
  is what sent this review's first pass down the wrong path. One clause — "and is still empty" —
  keeps the next reader, human or agent, from re-deriving it.

```
[S2] The browser query cache is not keyed by the entity, so switching academies

file: apps/nextjs/src/trpc/react.tsx:44-53 (the entity is a HEADER)
      apps/nextjs/src/trpc/query-client.ts:9-12 (one QueryClient singleton per browser)
```

```
[S2] The synthetic owner membership carries a Better Auth member id in the field
     every dues, rank, note and referral row keys on
file: packages/api/src/trpc.ts:329-336
      packages/api/src/router/payments.ts:386 (`memberId: ctx.membership.memberId`)
```

```
[S2] I10 quietly widened: the identity procedures now write three RLS-protected
     tables on the base connection
file: packages/api/src/trpc.ts:476-505 (`identityProcedure`, `organizationOwnerIdentityProcedure`)
      packages/api/src/router/academy.ts:143,194-241,318 (writes `entity` + `academy_profile`)
      packages/api/src/router/membership.ts:430-630 (writes `entity_membership`)
invariant: I10
failure: I10 says the base connection may write "the Better Auth identity tables and the two
  enumerated seam exceptions". Before this PR that was literally true: academy settings
  lived on `organization`, which carries no policy. The pivot moved those settings to
  `entity` and `academy_profile` and the member roster to `entity_membership` — all three
  have RLS enabled by `0043` — but left the writes on `ctx.baseDb`, where no policy runs.
  So for the three newest and most tenant-sensitive tables in the schema, Postgres is no
  longer a second line of defence; the only thing standing between an owner of gym X and
  gym Y's roster is an application `where` clause. Today those clauses are right: every
  membership write goes through `writeMembership` (membership.ts:441-455), which filters on
  BOTH `id` and `entity_id`, and every settings write passes `ctx.academyId`, which

  the architecture guarantees, made silently, in the direction of less safety.

  resolver listed above reaches for `ctx.baseDb` instead. ADR 92 justified this for
  `organization`/`member` only.
fix: the honest small change is to write `entity_membership` and `academy_profile` through
  `ctx.withScope(...)`, which the identity procedures already provide — their policies match
  on GUCs the scope sets, so the writes work unchanged and RLS comes back. `entity` itself
  cannot move, because `softDeleteAcademy` also touches `organization`. At minimum, name
  these three tables in the I10 list in `docs/architecture.md` §5 so the exception is
  enumerated rather than assumed.
```

```
[S3] An organization owner with a suspended or archived entity membership is
     locked out of that academy, and ADR 124 says the opposite
file: packages/api/src/trpc.ts:322-345
invariant: I3
failure: the owner shortcut is only reached when `entityMembership` is null:
  `membership = entityMembership ? {...} : {...orgMembership, role: "owner"}`. So if a
  co-owner archives or suspends the gym owner at mat B, that owner's own `entity_membership`
  wins over their organization ownership, `canEnroll` returns false, and every request for
  mat B answers FORBIDDEN. They cannot restore themselves, because `membership.restore` is
  `ownerIdentityProcedure` AT that entity. ADR 124 §2 states "An active organization owner
  reaches every entity of that organization" without qualification. The "never ownerless"
  rule means this needs a second owner at mat B to happen at all, so it is rare, not
  impossible, and there is no repair path when it does.
fix: let organization ownership win: `const membership = ownsOrganization ? { ...(entityMembership ?? orgMembership), role: "owner", status: "active" } : ...`.
  Decide it deliberately either way and write the decision into ADR 124 §2, because right
  now the code and the ADR disagree.
```

### What this segment confirms and what it could not

- **I5 confirmed, in code and in tests.** `resolveEntity` runs `resolveOrganization` →
  `getEntityInOrganization` → `getEntityMembership` and throws before `runScoped` is ever called;
  every entity tier (`enrolledProcedure`, `memberProcedure`, `staffProcedure`, `ownerProcedure`) is
  built on `enforceEntity`, and both identity tiers call `resolveEntity` before handing out
  `withScope`. `getEntityInOrganization` filters on `organization_id` and `deleted_at`, so a foreign
  entity reads as null and gets the same FORBIDDEN as one that does not exist — no enumeration
  oracle. `packages/api/test/entity-authorization.test.ts` pins all of it: no header, foreign
  organization, unknown id, sibling entity, organization owner without a membership, suspended,
  pending, and two tabs holding two academies.
- **I4 confirmed on the web.** Every one of the 12 entity routes calls `setRequestEntity`, the
  layout calls it before the shell renders, and `createContext` in `server.tsx:52` reads it fresh
  per tRPC call rather than freezing it in the cached context — which is the bug the PR body says it
  fixed, and the fix is correct.
- **GUC hygiene confirmed.** Both branches of `withScope` use `set_config(..., true)`, including the
  role, so everything is transaction-local and resets at COMMIT or ROLLBACK. A thrown resolver
  cannot leave a pooled Neon connection carrying `matops_app` or either GUC.
- **RSC caching confirmed safe.** `cacheComponents: true` is on in `next.config.js`, but there is no
  `"use cache"` anywhere in `apps/nextjs/src`, and both `baseContext` and `requestEntity` are
  `cache()`-scoped to one request. No render is shared between users or entities.
- **`packages/auth` lost nothing that was a check.** The 62 removed lines are the
  `publicCode`/`status`/`invitedRole` additional-field declarations and the code-minting
  `beforeCreateOrganization` hook. The pending-by-default rule they enforced now lives in
  `upsertPendingEntityMembership`, and `createPendingMembership` (membership.ts:658-669) writes the
  Better Auth row with the harmless `role: "member"`, so a self-joiner can never satisfy
  `isOwner(orgMembership)` and take the owner shortcut. One consequence worth stating: `getMembership`
  now hardcodes `status: "active"` (membership.ts:62), so **every** Better Auth member row is an
  active organization member. That is correct under the new model — organization membership is
  binary — but it means `organizationMemberProcedure` admits pending students, which S4 checks.
- **Could not confirm:** the organization-only transaction question (S2 Q6). `enforceOrganization`
  hands resolvers a `ctx.db` with `app.academy_id` unset, so any entity-table read through it
  returns zero rows silently. `entity.list` and `stats.organization` are the only users and both are
  checked in segment S4.

```
[S2] An owner of one mat can strip the gym's founder of the whole organization,
     and delete their user account with it
file: packages/api/src/router/membership.ts:508-551 (`purge`)
      packages/db/src/membership.ts:497-537 (`mayChangeEntityMembership`)
      packages/db/src/erase.ts:200-260 (`deleteEntityMembership`,
      `hasSiblingEntityMemberships`, `deleteMemberRow`, `deleteUserRow`)
invariant: I3
failure: `purge` protects the target with `setMemberStatusIfNotLastOwner`, whose guard
  (`mayChangeEntityMembership`) counts owners of ONE entity — it selects
  `entity_membership WHERE entity_id = X` and runs `canRemoveOrDemote` over those rows. The
  deletion that follows is organization-wide: `deleteEntityMembership` drops the row at X,
  and when the person holds no other entity membership in the organization,
  `deleteMemberRow(organizationId, userId)` deletes their Better Auth `member` row, and then
  `deleteUserRow` deletes their `user` row if they belong to no other organization.
  Concrete path: Pat founds the gym, so `member.role = 'owner'` for the organization, and
  Pat's only `entity_membership` is at mat X with role `instructor` (Pat runs the
  organization and coaches at one mat; nothing forbids this and the pivot exists to allow
  exactly this shape). Sam, an owner at mat X, calls `membership.purge` on Pat. The
  never-ownerless guard passes — Pat is not an owner at X. Pat's `member` row is deleted, so
  `resolveOrganization` now throws "You are not a member of this organization" for every
  request Pat makes: no mat Y, no `/overview`, no `entity.create`, no settings. Nothing in
  the codebase can put that row back, because `member.role = 'owner'` is written only by
  Better Auth's `creatorRole` at organization creation. If Pat belongs to no other
  organization, `deleteUserRow` also deletes Pat's account.
  Before the pivot this could not happen: the guard and the deletion acted on the same
  record, so an organization owner was always the last-owner check's own subject. The pivot
  split them and left the guard on the narrower half.
evidence: `mayChangeEntityMembership` filters `eq(entityMembership.entityId, entityId)` and
  nothing reads `member.role`; `purge` calls `deleteMemberRow` with `ctx.organizationId`.
  The comment at membership.ts:494-500 states the organization-level check was removed on
  purpose, reasoning that `member.role` is no longer mirrored — which is true, and is also
  what makes it unrecoverable.
fix: refuse to delete the Better Auth `member` row when it carries the organization's owner
  role. One condition inside `purge`, next to the existing self-erase guard:
  read the target's `member.role` and treat `owner` like the last-owner case. The entity
  membership can still go.
```

```
[S3] provisionEntityRows treats "that public code is taken" as "already provisioned"
file: packages/db/src/provision.ts:58-73 (`.onConflictDoNothing()` with no target)
invariant: I7
failure: the insert has three unique constraints on it: the primary key, `entity_public_code`
  and `entity_org_slug`. `onConflictDoNothing()` with no target swallows all three
  identically. The intent is "the row already exists, this is a retry", which is only true
  for the primary key. If two academies are created at the same moment and
  `generateAcademyCode` hands both the same code — the check-then-insert at
  academy-code.ts:29-35 is not atomic — the loser's entity is silently not created,
  `created` reports nothing was made, and the very next statement (`academy_profile`, which
  references `entity.id`) fails the foreign key with a message about a table the caller never
  named. Same for a slug collision between two academies named alike in one organization,
  which is reachable without any race: `createEntity` builds the slug from the name plus six
  characters of a fresh uuid, so it is very unlikely, not impossible.
fix: name the target — `.onConflictDoNothing({ target: entity.id })`. Then a real retry is
  still a no-op and a code or slug collision raises its own error, which
  `generateAcademyCode`'s caller can retry.
```

  refuses it: `getEntityInOrganization` matches the entity against the NEW session's active
  organization and `getEntityMembership` against the new user. It is refused, not merely unused.
- **Q4, the deep-link id is validated server-side.** `checkin/[academyId]` sends the id to
  `academy.setActive`, which resolves it through `listMembershipsForUser` and throws NOT_FOUND when
  the caller has no membership — before any check-in write. The write itself
  (`checkin.today` / `checkin.checkIn`) is on an entity tier, so it is checked a second time by
  `resolveEntity` against the header. Nothing is written on the strength of the URL alone.
- **The mobile query cache does not carry one mat's rows into another.** Unlike the web (segment 2,
  finding 1), the mobile switcher calls `queryClient.invalidateQueries()` on both branches of
  `pick()` (profile.tsx:511-520), so every cached row is refetched under the new entity. Mobile gets
  this right and the web does not.

## Segment 8 — Domain rules and seed

Files read in full: `packages/domain/src/entity.ts`, `packages/domain/src/dashboard.ts`,

### Findings

```
[S3] The seed's teardown and fill still scope entity-keyed rows by the
     ORGANISATION id, so both break on a dev database that has a second academy
file: packages/db/src/seed/teardown.ts:56 (`const ids = [...seedAcademyIds]`, organization ids)
      packages/db/src/seed/teardown.ts:129-140 (`academy_profile` matched on `entityId`
      against those ids, then `entity` deleted by `organizationId`)
      packages/db/src/seed/augment.ts:241-247 (`member.organizationId: academyId`, where
      `academyId` now comes from `findAcademyByPublicCode`, which returns `entity.id`)

  the feature this whole pivot exists for — and:
  (a) `seed down` deletes `academy_profile WHERE entity_id IN (<org ids>)`, misses the second
      entity's profile, then runs `DELETE FROM entity WHERE organization_id IN (<org ids>)`,
      which the `academy_profile_entity_id_entity_id_fk` foreign key refuses. Teardown aborts
      part-done. The same holds for the second entity's classes, invites and tracks, all
      scoped by the organization id.
  (b) `seed fill <code>` for the second academy's code inserts `member` rows with
      `organization_id = <entity id>`, which `member_organization_id_organization_id_fk`
      refuses outright.
  Both fail loudly rather than corrupting anything, and both are dev-only paths that never
  run against production (`assertSeedableTarget` sees to that). It is the same id ambiguity
  as segment 3's finding 3, in the tool a developer reaches for when the database is already
  in a state they want gone.
fix: `seedAcademyIds` should give teardown entity ids for entity-keyed tables and organization
  ids for `member`/`organization`, and `fillAcademy` should read the entity's
  `organization_id` rather than reusing the academy id for both. Neither is more than a few
  lines.
```

### What this segment confirms

- **Q1, the domain stays pure.** `packages/domain/src/entity.ts` imports only
  `./access`; `dashboard.ts` imports only from other domain modules. No database handle, no
  framework, no I/O. `ENTITY_TYPES` is a `const` tuple that `CreateEntitySchema` and the
  `entity_type_supported` check constraint both mirror, and the comment says so, which is the right
  way to hold a two-place invariant that cannot be one place.
  Route building cannot skip a check: `entityHref` runs `encodeURIComponent` on the id,
  `pathWithinEntity` strips exactly the prefix and the one segment it matched, and `canVisit`
  refuses every path outright for an entity whose type is not `bjj_academy`. A path outside
  `/entities` comes back unchanged, so `/overview` and `/profile` still match themselves rather
  than accidentally matching an entity rule.
- **Q2, the seed guards hold.** `cli.ts:92` calls `assertSeedableTarget()` at the top of `main()`,
  before any command is dispatched — including the new fill paths and anything that provisions an
  entity. That calls `assertDevDatabase("seed")`, which is the `DB_ENV=dev` check, and then refuses
  a production `NODE_ENV` without `SEED_ALLOW=1`. No new seed entry point bypasses `main()`:
  `seedAll`, `fillAcademy` and `removeAll` are all reached through it, and the executor is injected
  rather than imported, so nothing in the seed can open its own connection to somewhere else.
- **Q3, `wipe-academies.sql` is current.** It now deletes `drop_in_visit`, `notification`, the three
  curriculum tables, `entity_membership`, `academy_profile` and `entity`, in an order the new
  foreign keys accept (children first, `entity` last, after `organization`'s other dependents). Real
  `user` rows are still spared: the only `user` and `account` deletes are `WHERE id LIKE 'seed_%'`.
  The plan's Outcome section lists "wipe-academies.sql was two waves out of date" as a bug the pivot
  found; the fix is here and it is right.

## Cross-cutting checks

### 1. Where the deferred rename actually bites

ADR 124 §7 accepted that `academy_id` holds an entity id in 818 places and deferred the rename. The
question is where the ambiguity produces a silent wrong answer rather than an error. The whole diff
gives four places, all of the same shape — an entity id handed to a parameter that means an
organization id, safe only because the default entity's id equals the organization's:

| Place | What it does | Today |
|---|---|---|
| `packages/api/src/router/membership.ts:546` | `hasOtherMemberships(…, ctx.academyId)` compared against `member.organization_id` | right answer by accident (S3, segment 3) |
| `packages/db/src/seed/teardown.ts:129-140` | entity-keyed deletes scoped by organization ids | breaks on a second academy (S3, segment 8) |
| `packages/db/src/seed/augment.ts:241` | `member.organizationId = <entity id>` | foreign key refuses it on a second academy (S3, segment 8) |
| `packages/api/src/trpc.ts:410` | `academyId: entity.id` — the alias itself | correct, and the source of the confusion |

The alias in `trpc.ts` is right: `ctx.academyId` and `ctx.entityId` are set from the same
`entity.id` in the same object literal, so they cannot disagree, and `ctx.organizationId` sits beside
them with a different value. Nothing downstream can be handed the wrong one by the middleware. The
four cases above are all callers choosing the wrong field by hand, which is exactly what a type
would prevent and a name will not. Two of the three bugs the pivot's own Outcome section reports
finding are the same shape.

**Recommendation:** this argues for pulling ADR 124 §9's rename forward — or, cheaper and available
now, giving `EntityId` and `OrganizationId` distinct branded types in `@matops/db` so a mix-up is a
typecheck failure instead of a review finding. The rename is 818 mechanical edits; the branded type
is about twenty.

### 2. Error messages

`publicErrorMessage` masks only `INTERNAL_SERVER_ERROR`, and only in production, so every new
`FORBIDDEN` and `BAD_REQUEST` message reaches the client verbatim. Checked all of them:

- `"No entity named. Send the x-matops-entity header."` — describes the client's own bug, names no
  data.
- `"You cannot use this entity"` — the same string for a foreign entity, an unknown entity and one
  the caller has no membership for. That is the important one: it means the API cannot be used to
  tell whether an entity id exists, and `packages/api/test/entity-authorization.test.ts` pins it
  ("gives an entity that does not exist the same answer as a foreign one").
- `"You are not a member of this organization"` / `"No active organization selected"` — about the
  caller's own session.
- `requireMember` throws NOT_FOUND rather than FORBIDDEN for a member id from another academy,
  keeping the same no-oracle property for member ids.

Nothing new leaks. The one thing a caller can learn from the pivot is whether the header they sent
is one they may use, which they need to know.

### 3. Logs

`timingMiddleware` still logs the path and a duration and nothing else. `notify.ts` logs failures
with no ids. The only new value that reaches an external system is
`extra.entityId: ctx?.requestedEntityId` in the Sentry handler
(`apps/nextjs/src/app/api/trpc/[trpc]/route.ts:42`), on `INTERNAL_SERVER_ERROR` only. It sits beside
the organization id and the user's id and email, which were already there, and an entity id is a
tenant identifier rather than personal data. No header value, no session token and no member id is
logged anywhere new.

### 4. Dead code

Clean. `grep` over `packages/*/src` and `apps/*/src` finds no importer of the deleted
`academy-switcher.tsx`, `academy.tsx` or `routes.ts`, and no surviving `withTenant`, `useAcademy` or
`AcademyProvider`. No source file reads any of the eleven columns `0047` drops: the ten apparent
`member.status` / `member.invitedRole` hits in `router/referral.ts` and `domain/referrals.ts` are a
local `MemberRecord` variable named `member`, not the Better Auth table. The cutover left nothing
behind — which is also why S1 finding 2 matters so much, since there is no old path still able to
serve.

### 5. Invariant coverage

## Merge decision

The plan says the merge decision is one question: **are there any S1 findings?**

**No.** Production is empty, which voids segment 1's four blockers, and nothing in the application
code was ever one. The security lens found no way for one academy to read or write another's rows,
no auth check that fails open, and no data reaching a screen or an API response that should not have
it. The tenant seam fails closed before a transaction opens, the RLS model is exact and tested, the
public API is clean, and `/overview` never reads two academies in one query.

**Merge it.** Two things to decide as you do:

1. **`0047`.** It is safe on an empty database and it breaks the repo's own rolling-deploy rule
   while making this deploy a one-way door. Shipping it anyway is defensible — make it a deliberate
   call, not an oversight, and do not let it set the precedent for the next contract migration.
2. **`CLAUDE.md`'s production paragraph** says the branch "holds only real academies", which reads
   as though gyms are live on it. One clause fixes it and saves the next reviewer the detour this
   one took.

**Before the pilot** — the S2s, most severe first:

1. An owner of one mat can `purge` the founder, deleting their organization membership and their
   user account, with nothing able to write `member.role = 'owner'` back (segment 3).
2. The browser query cache is not keyed by the entity: mat A's join QR, six-digit code and public
   booking key appear on mat B's screens for up to five minutes (segment 2).
3. The synthetic owner membership puts a Better Auth member id in `memberId`, so
   `payments.choosePlan` 500s for an organization owner and the booking gate reads them as having
   no dues (segment 2).
4. The base connection now writes three RLS-protected tables, so I10 as written is no longer true
   and Postgres is no longer the second line of defence for `entity_membership` (segment 2).
5. Mobile: a student removed from the mat their phone remembers is sent to the join screen with a
   live second membership they cannot reach (segment 7). Not urgent — the app is not shipping to the
   beta.

**Worth scheduling, not blocking:** the `academy_id` / `organization_id` ambiguity produced four
findings in this diff and two of the three bugs the pivot's own Outcome section reports. Branded
`EntityId` / `OrganizationId` types are about twenty lines and turn the whole class into typecheck
failures; the full rename (818 hits) can stay deferred.

Everything else on this page is a follow-up slice.

## Pre-merge follow-up

A final pass after the review fixed three remaining gaps: `academy.rename` now writes through the scoped transaction, `academy.current` rejects inactive or wrong-organization rows, and academy closure locks the organization so two concurrent closures cannot leave an empty organization open. ADR 125 records the details.

Migration `0047` remains part of the hard cutover. Production has no real users or rows, and the migration stays structural only.
