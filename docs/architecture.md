# matops — Architecture Design Doc (v1)

_The design of record for **matops** (the from-scratch rebuild of the old app **MAT**). A build team starts here. Pairs with the product [spec.md](./spec.md); every decision below is a resolved wayfinder ticket (links go to the rationale)._

> **Naming:** **matops** = this new project (`/Users/kuna/projects/matops`). **MAT** = the old reference app (`/Users/kuna/projects/mat`); "the old app" always means MAT.

> **✅ Folds in the critical-review wave (tickets 12–21).** The three original over-claims are corrected here: tenant isolation is now **Postgres RLS** (§5), booking is an **atomic conditional `UPDATE`** (§7), and future live updates use a **separate always-on worker**, not SSE on the serverless API (§7/§8). Also folded in: push+email notifications (§7), the `pg`+Fluid+pooler connection (§9), dropped `completed` status, lazy+cron materialization, instructor/approval rules, and the multi-academy switcher.
>
> **➕ Low-friction student wave (tickets 22–27) — product detail lives in [spec.md](./spec.md); captured here at reference level.** Technical shape (to be detailed when we move past conceptual): a new **`enrolledProcedure`** tier lets pending members read + provisionally book/check-in (role still only at approval); `class_participation` gains **`booking_tier`** so only _confirmed_ (approved-member) bookings count capacity; a **`drop_in`** table + a public per-gym check-in/lead endpoint (an enumerated public entry point); a **QR check-in** endpoint; and **magic-link** auth. See the stack table's "Student low-friction" row and the schema draft.

## 0. As-built status (Phases 0–4 + every wave through v3.0 — read this first)

Sections 1–11 are the **conceptual design of record** (the "why", written before code). This section is the **reality on disk** through Phases 0–4 and every product wave to **v3.2**. Where they differ, this section wins for "what exists today"; the sections below still hold for intent. Slice-by-slice detail: [../CHANGELOG.md](../CHANGELOG.md); live plan + status matrix: [roadmap.md](roadmap.md); how we build + keep docs true: [delivery.md](delivery.md).

**Built and green** (`pnpm lint` 15/15 · `pnpm typecheck` 17/17 · `next build`; five test suites, see "Testing" below): the create-t3-turbo monorepo, the DB layer on **Neon**, the RLS tenant seam (**verified live on Neon**, not only PGlite), Better Auth (org + magic-link + optional Google), and the tRPC procedure tiers. On top of that: **Phase 1** identity (onboarding, invite links, self-join → pending → approval, member list, multi-academy switcher, 6-digit code join); **Phase 2** scheduling (templates, DST-aware materialization, one-off classes, edit/cancel propagation, schedule reads); **Phase 3** booking & attendance (book/cancel, provisional tier, staff attendance + mark-all-present, QR check-in, public drop-in); **Phase 4** notifications (Expo Push + Resend transport, event sends, the class + dues reminder sweep — engine built, but **not scheduled in v1**, ADR 46); the **mobile pass**; and the waves **v1.1 → v3.2** (UX, stats, payments, rank & notes, PWA, mobile design + IA, referrals, mobile waves, the student web funnel, the two review passes, coach workload, the Settings split, invite roles, the web Profile, the academy time zone / address / delete, the in-app QR scan, the pinned map link, and the student web at parity).

**Migration state on Neon:** `0000`–`0022` are **applied** (23 rows in `drizzle.__drizzle_migrations`, checked 2026-08-22). `0021` adds `time_zone` / `address` / `deleted_at` to `organization` (all nullable, ADR 68); `0022` adds the nullable `map_url` to the same table (ADR 71). `0023` adds `notification` + `notification_pref` (notification center, ADR 77), **applied 2026-08-22** — 24 rows in `drizzle.__drizzle_migrations`, both tables RLS-enabled with their isolation policies live. `0024` adds the nullable `sent_by` to `notification` (who posted an announcement, ADR 77 follow-up), **applied 2026-08-23** — 25 rows in `drizzle.__drizzle_migrations`.

**Not built yet:** universal/App links (a Phase-5 launch-infra task; the app uses a custom scheme), **a sub-daily scheduler** (ADR [75](issues/75-daily-cron-on-github-actions.md) added a **daily** GitHub Actions cron, 09:00 Lisbon, for dues reminders alone; Vercel Cron stays removed, ADR 46, and the class horizon is filled by hand (ADR [79](issues/79-manual-schedule-rebuild.md)). The **class** reminder sweep is deliberately off — mobile schedules those **on the device**, ADR 54, and a web-only student gets none), **booking-count reconciliation**, and the **R.2 native home-screen widget** (scaffolded + guided, native build deferred). Rate limiting is **built for the pilot** (ADR [76](issues/76-pilot-blockers.md)) but is in-process and per-instance, so a shared store is still Phase-5 work; the Expo app still reports no errors to Sentry. Two carried operational items: **rotate `AUTH_SECRET`** (ADR 60) and the mobile **Google browser→app session hand-off** still does not land (ADR 35).

**v4.1 as-built (archive and permanent erase; ADR [84](issues/84-archive-and-erase.md)):**

The single `membership.remove` action becomes two with different weight, and three defects behind it are fixed: the dues cron kept reminding people who had left (`claimDueDuesReminders` joined `member` and never filtered its status), archiving never cancelled upcoming bookings so `class.booking_count` stayed inflated forever, and `restore` refused anything not `suspended`.

- **`archived` is a status value, not a column.** `member.status` is plain `text` with no enum, so it costs no migration, and `canEnroll` is a whitelist (`pending` / `active`) so the new value is denied access by default. `removed` narrows to mean only "an applicant the owner declined". `isArchived` / `isOnRoster` in `packages/domain/src/access.ts` replace three separate `!== "removed"` filters in the member list, the growth counts and the referrals screen, so they cannot drift apart.
- **`membership.archive`** reuses `setStatusOrRejectLastOwner` for the locked never-ownerless check, then cancels the member's `booked` rows on **future scheduled** classes and decrements `booking_count` only for the `confirmed` ones. `class_participation` is unique on (class_id, student_id), so a flat -1 per affected class is exact. Past rows are untouched: they carry attendance on the same row as the booking.
- **`packages/db/src/erase.ts`** holds `eraseMemberData` plus the identity helpers. **No domain table has a foreign key to `member` or `user`**, so nothing cascades and all nine tables are named explicitly, in the order `clearAcademy` (`seed/augment.ts`) already uses. `recomputeBookingCounts` moved out of the seed module into this one, so no production path imports from `seed/`.
- **`membership.purge`** archives first (both for the ownerless guard and because the tenant transaction and the base connection cannot commit as one, so an archived member is the recoverable state), erases the RLS-scoped rows on `ctx.db`, drops the `member` row on `ctx.baseDb`, and drops the `user` row **only when no other membership survives**. An owner may wipe what their own gym holds, never another gym's records, and cannot erase themselves.
- **The two "append-only" tables were never append-only.** `member_referral_audit` (`0018`) and `notification` (`0023`) both read as though DELETE was withheld, but migration `0001` sets `ALTER DEFAULT PRIVILEGES ... GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO matops_app`, so every table created after it starts with all four and a later narrower `GRANT` takes nothing away. Append-only there was a convention in the comments, not a permission. Migration `0026` makes the grant explicit and **changes nothing**; `packages/db/test/erase-grants.test.ts` is the check that matters. Real enforcement would need an explicit `REVOKE` plus a carve-out for the erase.
- **`ConfirmDialog` (`packages/ui`) gains optional `confirmPhrase` and controlled `open`**, so the type-the-name gate in front of a permanent delete is a reusable prop rather than a bespoke dialog.

**v4.0 as-built (API latency; ADR [81](issues/81-api-latency.md)):**

A round-trip pass, not a rewrite. No migration, no new dependency, no screen changed. One statement to Neon costs 45 ms and a dashboard load sent about forty of them.

- **The dev-only sleep is deleted** from the timing middleware in `packages/api/src/trpc.ts` (inherited create-t3-turbo boilerplate, a random 100-500 ms per procedure). The `[TRPC] <path> took <n>ms` log stays: it is the measuring tool.
- **`session: { cookieCache: { enabled: true, maxAge: 5 * 60 } }`** in `packages/auth/src/index.ts`. Better Auth signs the session + user rows into the cookie, so an authed request costs zero identity queries instead of two. **A revoked session stays valid for up to five minutes.** Role / status changes are not affected (`getMembership` reads the `member` row live on every tenant call); academy switching is not affected because `/organization/set-active` calls `setSessionCookie` and `nextCookies()` copies it onto the tRPC response.
- **`"regions": ["fra1"]`** in `apps/nextjs/vercel.json`, which until now held only a `$schema` key — so functions defaulted to `iad1` while the database sits in `eu-central-1`. **Inferred, not measured**; confirm on the next deploy.
- **`withTenant` sets both values in one round trip.** `SET LOCAL ROLE x` is defined as `SET LOCAL role = x`, so the role is a plain GUC: `SELECT set_config('app.academy_id', $1, true), set_config('role', $2, true)`. Both are bound parameters now, so the seam has no interpolated identifier left. `packages/db/test/tenant.test.ts` is the first test that exercises the real `withTenant` — every RLS test mirrors it by hand.
- **The `(app)` layout prefetches `academy.current` + `academy.memberships`** and wraps the shell in `HydrateClient`. `prefetch()` existed in `apps/nextjs/src/trpc/server.tsx` with no call site anywhere, so all data was fetched after hydration. The queries dehydrate while still pending, so nothing blocks the HTML, and `AppShell` is unchanged.
- **Pool: `max: 20`, `keepAlive`, `idleTimeoutMillis: 60_000`** in `packages/db/src/client.ts`. Ten concurrent tenant transactions sat exactly on the `pg` default of 10. **Each Vercel instance holds its own pool**, so this multiplies across a scale-out against Neon's pooled endpoint limit.
- **Not done, on purpose:** one transaction per HTTP batch. Ten procedures in a batch open ten transactions and pay the 179 ms setup ten times; sharing one is the largest win left and changes the tenant seam (§5, ADR [12](issues/12-tenant-isolation-mechanism.md)) and the `baseDb` injection point (ADR [60](issues/60-backend-review-fixes.md)).

**v3.9 as-built (Manual schedule rebuild; ADR [79](issues/79-manual-schedule-rebuild.md)):**

The owner owns the horizon. No migration, no new dependency.

- **Six months, not six weeks.** `MATERIALIZATION_HORIZON_DAYS` 42 → **180** in `packages/domain/src/schedule.ts`. Every caller threads it as a default, so lazy-on-save and the rebuild share one number and a template save fills half a year at once.
- **`staleClassIds(existing, wanted)`** in `packages/domain/src/materialize.ts` — a pure set difference on `(templateId, startsAt)` that skips `templateId === null`. This is the whole "what gets deleted" rule, and it is unit-tested with no IO.
- **`planRebuild` / `rebuildSchedule`** in `packages/db/src/materialize.ts` run on the caller's tenant transaction, so RLS scopes every statement and the deletes roll back together on failure. Order: participations, then `drop_in.class_id → NULL`, then the class, because **no FK carries `ON DELETE`** and a blanket `CASCADE` would let any future class delete take bookings silently. Then `generated_until = NULL` on every active template before re-materializing, or a template already at the horizon would create nothing and leave the hole the delete made. `onConflictDoNothing`, not `reviveCancelled`, so a deliberately cancelled class stays cancelled.
- **Never touched:** classes with `starts_at <= now` (attendance shares the participation row with the booking), one-offs (`template_id IS NULL`), and cancelled instants the templates still want.
- **`template.rebuildPreview` + `template.rebuild`** on `ownerProcedure`. The preview exists so the confirm dialog names the count before the owner commits, the pattern `notification.audienceCounts` uses. The UI is a `RebuildSchedule` block at the foot of `apps/nextjs/src/app/_components/templates.tsx`, behind a `ConfirmDialog` — one step below the typed-phrase gate on deleting the academy, because templates and history both survive.
- **`BOOKING_WINDOW_DAYS = 7`** and a fourth `NotBookableReason`, `"too-far-ahead"`, in `packages/domain/src/booking.ts`; `packages/api/src/router/booking.ts` grew the third message arm. Measured from `now`, not midnight, so the guard is never stricter than the seven-day list both clients already render. **No client change** — this closes the `/class/<id>` deep link.
- **The sweep stays, unscheduled.** `.github/workflows/cron.yml` drops the materialize call (the dues step is untouched); `/api/cron/materialize`, `runMaterializationSweep` and its tests all remain a live, authenticated, cross-academy seam.

**v3.8 as-built (Fan-out, horizon, and seat seams; ADR [78](issues/78-notification-and-horizon-seams.md)):**

An architecture pass over the v3.6 / v3.7 wave. No migration, no new dependency, nothing a member can see.

- **One notification fan-out.** `deliver(items: PersonalDelivery[])` in `packages/api/src/notify.ts` is the only path; `each(userIds, msg)` expands one message across a list for the five callers that want that, and `deliverEach` is gone. The two had drifted inside one wave (one `sendPush` call for a whole class versus one per person; `sentBy` honoured by one reader of a shared type and not the other).
- **`sendPush` takes addressed messages**: `BatchPush[]` (one token, one text each), chunked at Expo's 100. Any mix of same-message and per-person sends now costs `ceil(tokens / 100)` calls. Its only caller was `notify.ts`.
- **The horizon belongs to the cron.** ~~`.github/workflows/cron.yml` curls `/api/cron/materialize` daily.~~ **Superseded by ADR [79](issues/79-manual-schedule-rebuild.md):** the horizon is manual now. What stands from this wave: `healHorizon` is gone and both week reads are plain reads again, `runMaterializationSweep` takes an optional `exec`, and `packages/db/test/materialize-sweep.test.ts` gives it its first tests.
- **`canDecideSeat(actor, member)`** in `packages/domain/src/membership.ts` replaces the router's `requireOwnerForCoachSeat` body: an instructor clears the student queue, the coach queue stays the owner's. Tested next to `canApprove` and `wouldLeaveOwnerless` instead of needing a router harness.
- **Two moves for the test surface:** `notificationKindLabel(kind)` is exported from `@matops/domain` (`NOTIFICATION_KIND_LABEL` is private now) and replaces the identical fallback wrapper both clients had copied; `clientIp(headers)` moved out of the `rateLimited` middleware into `packages/api/src/rate-limit.ts`, where the limiter's tests are.

**v3.7 as-built (The notification center; ADR [77](issues/77-notification-center.md)):**

Migration `0023` adds one academy-scoped table inside the tenant seam, with the standard `academy_id` isolation policy. The migration grants `SELECT, INSERT, UPDATE` to `matops_app`; `DELETE` arrives anyway from the `ALTER DEFAULT PRIVILEGES` in `0001`, so what keeps a notification undeletable is the absence of a procedure that deletes one, not the grant.

- **`notification`** — one row per RECIPIENT per event (`kind`, `title`, `body`, `link`, `sent_by`, `created_at`, `read_at`), indexed on `(academy_id, user_id, created_at)`, which serves both the feed and the unread count. Fan-out on write, not an announcement table plus read receipts.
- **`packages/db/src/notification.ts`** holds `insertNotifications` on the **base connection**, because their callers run outside the seam: `deliver()` is handed to `ctx.afterCommit` (ADR [60](issues/60-backend-review-fixes.md)) and both cron sweeps run cross-academy. Reads go the other way, through `ctx.db` under the seam.
- **`deliver()` in `packages/api/src/notify.ts` writes the inbox row first**, in its own `try`, ahead of the push. All five existing kinds gained an inbox entry with no new call sites; `DueDuesReminder` grew an `academyId` (already on `member_dues`) so the dues sweep can address the row.
- **Nothing a gym sends goes out by email** _(v3.8)_. matops has no mail layouts, so a notice would leave as bare text from a domain nobody recognises. `deliver()` writes the inbox row and pushes, and that is the whole delivery. Gone with it: `sendEmailBatch` and `BatchEmail` in `packages/notifications`, the `email` field on `Delivery`, `emailsFailed` on `runReminderSweep`, the `email` builders in `@matops/domain`, the `notification_pref` table with its router, and the tick box on the compose form. `sendEmail` stays for the sign-in magic link, its only caller (`packages/auth`). The dues claim still stamps the period **before** the send, so a dropped push is lost until the next period; `/api/cron/remind` returns 200 either way, because `curl --retry` would re-run the sweep, find every row already claimed, and report a clean tick.
- **`packages/api/src/router/notification.ts`** — `list` (50, no cursor), `unreadCount`, `markAllRead` on `memberProcedure`, all narrowed to `ctx.session.user.id` on top of the academy policy; `announce` and `audienceCounts` on `staffProcedure` (owner or instructor), both resolving the roster through the pure `announcementRecipients`. `announce` stamps `sent_by` with the caller's display name, copied at send time so a rename or a departure does not rewrite the history; system messages leave it null.
- **Web:** `(app)/notifications` with `_components/notifications-screen.tsx` (feed grouped by day, owner compose box), and a nav item with the unread badge in `app-shell.tsx`. No route-access entry: the feed belongs to every member.
- **Not touched:** the scheduler (ADR [75](issues/75-daily-cron-on-github-actions.md)'s daily dues tick is what it was, and now leaves a copy behind), the phone app, and the parked live-UI seam — the badge polls.

**v3.6 as-built (Pilot blockers; ADR [76](issues/76-pilot-blockers.md)):**

Five gaps between the code and `docs/pilot-plan.md`, whose defining constraint is that nobody from matops is in the room. **No migration, no schema change, no new dependency.**

- **The schedule read heals its own horizon.** ~~`healHorizon(db, to)` in `packages/api/src/router/class.ts`, awaited by `class.week` and `class.mine` before they read.~~ **Superseded by ADR [78](issues/78-notification-and-horizon-seams.md):** the read was doing unbounded writes, so `healHorizon` is deleted and the daily GitHub Actions tick curls `/api/cron/materialize`. See the v3.8 section.
- **Rate limiting on the two public surfaces.** `packages/api/src/rate-limit.ts` is a fixed-window counter in a `Map` (~25 lines, no dependency), driving a `rateLimited(max, windowMs)` tRPC middleware keyed on procedure path + the first `x-forwarded-for` entry: `dropIn.submit` 5/10 min, `dropIn.academyInfo` + `invite.resolve` 30/min. Better Auth gets its own `rateLimit` block (60/min, `/sign-in/magic-link` 5 per 5 min, `/magic-link/verify` 20/min), production-only by its own default. **Both are per process** — Fluid compute scale-out and cold starts leak, and the documented upgrade is a `rate_limit` table.
- **Member approval is the staff tier.** `membership.approve` / `reject` / `members` / `memberHistory` moved from `ownerProcedure` to `staffProcedure`; `rank.*` and `note.*` were already staff and only unreachable because `/members` was owner-gated. `membership.members` returns **`dues: null`** for a non-owner (the field was already nullable and both consumers already branched, so this is one line and no type change — the same shape `stats.gym` uses for `newMembers`). `remove` / `suspend` / `restore` / `staff` / `promote` / `setRole` / `dropIn.list` / `invite.*` stay owner-only: an instructor with `setRole` could mint instructors and demote every owner but the last. `packages/auth/src/permissions.ts` is **untouched and still decorative** — nothing in the repo calls `hasPermission`, and `instructor` and `student` are the same role object there. On the web, `/members` moved to `isStaff` in the ADR 74 access table, and the four owner-only blocks inside it (Invites, the leads tab, Export CSV, suspend/restore/remove + the role picker) grew their own `isOwner` check, since the route table is no longer their guard.
- **Sentry is capped for the free plan.** `tracesSampleRate: 0` and `enableLogs: false` in all three configs, `replaysSessionSampleRate: 0` with `replaysOnErrorSampleRate: 1.0`, and `ignoreErrors` for extension noise and aborted fetches. `sampleRate` stays 1.0. The plan is 5,000 errors and 50 replays a month, with **one seat** and **30-day retention** — both reasons to open Sentry daily rather than weekly.
- **A public privacy page and two feedback seams.** `apps/nextjs/src/app/privacy/page.tsx` is a plain server component outside `(app)`, so it is public by existing (there is no middleware and no shared public layout). It ships with `[ENTITY]` / `[ADDRESS]` / `[CONTACT EMAIL]` **visible**, because a half-true notice is worse than an obviously unfinished one. Linked from the drop-in consent line and the join form, in a **sibling** element rather than inside the `<label>`, since a link inside a label toggles the checkbox. A `FeedbackLink` (`mailto:` prefilled with academy, role and screen) sits in the sidebar footer and on Profile, because the footer is desktop-only. The dashboard's "All clear." block is replaced by a **three-step checklist** when an owner has no active members and no classes this week.

**v3.0 as-built (In-app QR scan; ADR [70](issues/70-in-app-qr-scanner.md)):**

The student app gains a fourth tab, **Scan** (`apps/expo/src/app/(tabs)/scan.tsx`), and its first native camera dependency, **`expo-camera`**. The scanner is the operating system's own sheet (`CameraView.launchScanner()` → `DataScannerViewController` on iOS 16+, the Google code scanner on Android), so the app ships no camera preview or overlay; `CameraView.isModernBarcodeScannerAvailable` gates the phones that cannot present one back to the old camera-app flow. The config plugin adds `NSCameraUsageDescription` and `android.permission.CAMERA`, asked on the first tap of the tab. **No back-end, RLS, or migration change:** the poster still encodes `https://…/checkin/<academyId>`, the public drop-in page and its `matops://` deep link still work, and the scan routes into the existing `checkin/[academyId]` screen over the unchanged `checkin.today` / `checkin.checkIn`. The only new logic is the pure `parseCheckInLink` in `@matops/domain`. Because `apps/expo/ios` and `android` are generated (CNG), the dev client must be rebuilt, and the flow is **not verifiable in a Simulator**.

**v3.3 as-built (Web shell seams; ADR [74](issues/74-web-shell-seams.md)):**

A refactor of the web client only: no procedure, no schema, no migration, and no user-visible screen changed except one. **`AppShell` puts the resolved academy in a React context** (`_components/academy.tsx`), so the thirteen screens that each ran `academy.current` and re-wrote its loading / failed / none branches now call `useAcademy()` and get a non-null membership. The shell already refused to render a child until that value existed, so those branches were dead code that still had to be read. **Book and cancel became one hook** (`_components/use-booking.ts`), the web twin of `apps/expo/src/components/book-control.tsx`: three screens had copied the mutation pair, and two of them invalidated different query paths, so one list could stay stale after the other updated. **`routes.ts` holds the access table** the sidebar and the shell both read, so a page a role cannot use is not offered and does not render if the URL is typed: the shell shows `NoAccessState` instead of a screen of refused queries. The tRPC tier is still the guard. **The formatters moved out of the screens** into `~/lib/format.ts` (the mirror of `apps/expo/src/utils/format.ts`), which re-exports the shared `@matops/domain` rules and adds the web's own day and date shapes: 24 `Intl.DateTimeFormat` instances across 14 files became 12 named ones in a single place (the schedule poster keeps its own, pinned to `en-GB` because it is drawn into an image). Two more rules moved down to `@matops/domain` with tests, because both clients had a copy: `dayKey` / `groupByDay` (the local-day bucketing behind three schedule screens) and `PAYMENT_STATUS_LABEL` (the words "Paid" / "Due soon" / "Overdue", which the web and the phone spelled out separately). Verified by typecheck 17/17, lint 15/15, `next build`, and `pnpm test` 456 green.

**v3.2 as-built (The student web reaches parity; ADR [73](issues/73-student-web-parity.md)):**

The student web goes from one screen to the app's four jobs minus Scan, **inside the owner's own `AppShell`** — no new procedure, no new pure rule, no migration. New routes `(app)/training` (S6, `booking.mine` + `stats.me` divided by the pure `splitMyClasses` / `nextClass`) and `(app)/class/[id]` (S5, `class.get` + `class.attendees`, the first dynamic segment under `(app)/`); `(app)/payments` branches on `isOwner` and serves `MyDues` (`payments.myDues` + `payments.claim`) to everyone else; `/profile` gains **My rank** (`rank.mine`, `formatRank`) and the academy address with the ADR 71 `academyMapUrl` link. The shell adds four `!isStaff` nav items, which is all it took: both nav blocks were already wrapped in `items.length > 1` and a student qualified for exactly one, so the sidebar and the bottom tab bar were built and switched off. The rest of the chrome (pending banner, avatar link, theme toggle, sign out) already rendered for a student and is unchanged. The **S11 overdue strip** renders in the shell under the pending banner, gated on `!isStaff && isActiveMember` because `payments.myDues` is a `memberProcedure`, which refuses a **suspended** member as well as a pending one. One shared read changed: the switcher moved from `academy.listMine` (filtered by `isWebLensMembership`, so a student-only user always got an empty list) to `academy.memberships`, the list the ADR 49 post-login gate already offers, so an owner who also trains elsewhere now sees that gym too. Owner and instructor screens are untouched. Verified by typecheck 17/17, lint 15/15, and `next build` (the first since v2.4), with `/training` and `/class/[id]` in the route table; the screens themselves want a browser pass, which is the `pilot-plan.md` dry run.

**v3.1 as-built (A pinned map link for the academy; ADR [71](issues/71-academy-map-link.md)):**

Migration `0022` adds one nullable column, `organization.map_url`, written on the same base connection as the other `organization` settings. `academyMapUrl(address, mapUrl)` in `@matops/domain` returns the pinned link when there is one and falls back to the Google search URL built from the address. `MapUrlSchema` in `@matops/validators` narrows `HttpUrlSchema` to a fixed list of map hosts (`maps.google.com`, `maps.app.goo.gl`, `maps.apple.com`, `openstreetmap.org`, `osm.org`, `waze.com`, and `google.com` only under `/maps`), because the value is rendered as an `href` for every member. The host comes from `new URL()`: a browser treats a backslash in the authority as a path separator, so a regex host group reads the wrong host. The package tsconfig adds the `dom` lib for the `URL` type, as `@matops/ui` already does. The web Settings card gains the input plus a live **Check the pin ↗** preview built from the same helper, and the mobile Profile opens the pinned link directly or falls back to `maps://` / `geo:` so the tap reaches the phone's own map app.

**v2.9 as-built (Academy time zone, address, and delete; ADR [68](issues/68-academy-time-zone-address-and-delete.md)):**

Migration `0021` adds three nullable columns to `organization`, alongside `public_code`: `time_zone`, `address`, `deleted_at`. Writes to them run on the **base connection**, because `0020` revoked `UPDATE` on `organization` from `matops_app`; the reads inside a tenant resolver take `ctx.db`, per ADR 66.

**The academy zone is now stored rather than inferred.** It had never existed: each `class_template` carried its own zone, defaulted client-side from `Intl.DateTimeFormat().resolvedOptions().timeZone` into a free-text input, and `academyTimeZone()` picked the most-used template zone with a `"UTC"` fallback — so a typo mis-timed a whole template's materialization, two coaches in two zones split the schedule with no warning, and a gym with no templates drew its week and month boundaries in UTC. `academyTimeZone(tx)` became `academyTimeZone(ctx)` (it needs `academyId` to pin the RLS-less `organization` row) and reads the setting first, the template query second, UTC last. Changing the setting **never re-times existing templates** — that would run the ADR 60 cancel-and-re-materialize path against classes students have booked; `driftingTemplateZones` names the strays on Settings and the template form offers a one-click move instead.

**`ownerIdentityProcedure`** is a new tier for the two writes that touch the `organization` row: `protectedProcedure` plus the membership and owner checks (now shared with `enforceTenant` via `resolveActiveMembership`), and **no tenant transaction**. `0020` revoked `matops_app`'s `UPDATE` on `organization`, so the write must use the base connection, and doing that from inside `withTenant` holds two pool connections (ADR 66) — on single-connection PGlite it deadlocks outright. The table has no RLS policy, so the transaction was never buying anything. `academy.settings` reads RLS-scoped `class_template` and stays an `ownerProcedure`. `getAcademyCode` / `findAcademyByCode` / `getAcademyPublic` gained the `exec` parameter they were missing.

**Soft delete is filtered at seven academy-resolution paths**, all in `packages/db`: `getMembership`, `listMembershipsForUser`, `findAcademyByCode`, `getAcademyCode`, `resolveInviteToken`, `getAcademyPublic`, and both cron claim queries. `getMembership` is the load-bearing one — it inner-joins `organization`, so a deleted academy fails **every** tenant procedure at the middleware regardless of what the session still holds. No session cleanup is needed: `academy.current` returns null and `AppShell` already renders the post-login gate for that case. The pure rules (`isValidTimeZone`, `timeZoneOptions`, `resolveAcademyTimeZone`, `driftingTemplateZones`, `academyMapUrl`, `deleteAcademyPhrase`, `matchesDeleteAcademyPhrase`) live in `packages/domain/src/academy-settings.ts`; the seam has router tests in `packages/api/test/academy-settings.test.ts`.

**Concrete facts that refine the conceptual sections below:**

- **DB driver / connection (refines §9):** a `pg` (node-postgres) `Pool` in `packages/db/src/client.ts`, using the Neon **`-pooler`** string in `POSTGRES_URL` (`sslmode=verify-full`). `drizzle.config.ts` strips `-pooler` so **migrations** run on the direct endpoint.
- **RLS mechanism (refines §5), as implemented:** `withTenant(academyId, fn)` in `packages/db/src/tenant.ts` opens a transaction and runs **`SET LOCAL ROLE matops_app`** + `set_config('app.academy_id', <id>, true)`, then the resolver's queries. `matops_app` is a NOLOGIN, non-BYPASSRLS role (migration `0001`); migration `0003` does `GRANT matops_app TO current_user` so the (non-superuser) connection role can `SET ROLE` to it — **required on managed Postgres like Neon**; PGlite (superuser) doesn't need it. `academy_id` is **text**, no `::uuid`. The RLS example + regression table is `tenant_probe`.
- **Procedure tiers (refines §4), as implemented** in `packages/api/src/trpc.ts`: `publicProcedure` · `protectedProcedure` (authed, kept from template) · **`enrolledProcedure`** (any member incl. pending — this is the one that opens the tenant tx) · `memberProcedure` (active) · `staffProcedure` (owner|instructor) · `ownerProcedure`. The `enforceTenant` middleware reads `session.activeOrganizationId`, loads membership via `getMembership`, checks the pure **`canEnroll`** predicate (only `pending`/`active` may enter the enrolled tier — `suspended`/`removed` keep a row but are refused, ADR **33**), then wraps the resolver in `withTenant`. Role/status checks are pure predicates in `@matops/domain` (`canEnroll`/`isActiveMember`/`isStaff`/`isOwner`), unit-tested. **Fail-closed context (ADR 33, amended by ADR 60):** the only handle that may touch a **tenant** table is the RLS-scoped `ctx.db` injected by `enforceTenant`, so a non-tenant resolver that reaches for it fails at typecheck; a lint rule (`packages/api/eslint.config.ts`) blocks the raw owner `@matops/db/client` in `packages/api/src/router/**`. The context also carries **`ctx.baseDb`**, the base (non-RLS) connection. It exists for two jobs (ADR [66](issues/66-identity-reads-run-on-the-tenant-transaction.md)): lookups that run **before** the transaction opens (`getMembership` in the middleware, `academy.setActive`), and identity **writes**, which migration `0020` denies `matops_app`. Identity **reads** inside a tenant resolver run on `ctx.db` like any other read: those tables carry no RLS policy and `matops_app` keeps SELECT, so the rows are the same either way, while reaching for the base connection would check out a SECOND pool connection and hold both for the length of the request. The read helpers take `DbReader = DbExec | TenantTx` so the call site picks. It is the single injection point the router tests replace with PGlite; every base-connection helper (`withTenant`, `getMembership`, `getMemberById`, `getMemberIdForUser`, `listMembersOf`) takes `exec` as a **required** parameter, so a missed call site is a build failure rather than a silent fall back to the production pool. Migration `0020` revokes `matops_app`'s write access to those identity tables and all access to `session`/`account`/`verification`/`invitation`/`academy_invite`. **`requireMember(ctx, memberId)`** (`packages/api/src/members.ts`) is the one guard scoping a member id to the caller's academy. **`ctx.afterCommit(task)`** defers push/email sends until the tenant transaction has committed, so a network call never holds a pooled connection open.
- **`@matops/api` and `@matops/auth` are consumed from SOURCE** (no `.d.ts` emit): the `AppRouter` type embeds the whole Better Auth `Auth` type, too large to serialize (TS7056). Their `exports.types` point at `src` and their tsconfig extends `base.json` (noEmit). Do not revert.
- **Migrations (refines §10):** versioned SQL in `packages/db/migrations`, applied with `pnpm -F @matops/db migrate` (**not** `push` — the RLS role/policy are hand-written in `0001`/`0003`). `drizzle-kit check` runs in CI. The set is `0000`–`0020`: `0000` core tables + `_health`, `0001` RLS role/policy/probe, `0002` Better Auth org tables, `0003` role grant, `0004` `academy_invite` + `member.invited_role`, `0005`/`0006` `class_template` + its RLS, `0007`/`0008` `class` + its RLS, `0009` drop the scaffold `post` table, `0010` `organization.public_code`, `0011`–`0013` the booking / attendance / drop-in schema, `0014` push tokens (outside the tenant seam), `0015`/`0016` payments, `0017` rank + notes, `0018` referrals, `0019` the `member (organization_id, user_id)` index, `0020` identity-table grants. **Applied on Neon through `0018`; `0019`/`0020` are not applied yet.** A **lint guardrail** (ADR 33) blocks the raw owner `db` in routers so the tenant seam can't be bypassed by accident.
- **Auth (refines §6):** magic-link (`sendMagicLink` logs the URL in dev — Resend is Phase 4) + Organization plugin; roles owner/instructor/student in the client-safe `@matops/auth/permissions`; `member.status` defaults `pending`. Discord OAuth was removed. **Social login (slice 1.8, ADR 35):** `socialProviders.google` is added **conditionally** — `initAuth` takes optional `googleClientId`/`googleClientSecret` (from optional `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` env), and registers the Google provider only when both are set (else magic-link only, so dev/CI/tests are unaffected). A social user has no academy membership → same pending/approve join gate as magic-link. **Account linking** (`account.accountLinking.trustedProviders = ["google"]`) unifies a Google sign-in with an existing same-email user (one identity per email). **As-built status:** **web works** (server-side verified); **mobile's server side works** (callback creates the user + `google` account + session, redirects to `matops:///` with the cookie) but the **browser→app session hand-off is not yet landing** — an open item, same class as the earlier mobile magic-link cookie issue (ADR 35 "As-built status"). Web: a new owner **Payments** screen (O7 — claims to confirm, member-dues assignment, plans) with a nav item + waiting-claims badge, and a **bank-details** field on Settings (O6). Mobile: an S9 **Membership dues** card on Profile — status + amount + next-due, a requisites card with **copy** buttons (`expo-clipboard`) for the bank details + reference code, and an **"I paid"** button that raises the claim (shows "waiting to confirm" while a claim is open). Verified live on Neon (claim under RLS, double-submit blocked by the partial unique index, confirm rolls the due date — rolled-back tx); **mobile device check pending** (no simulator in env; needs a dev-client rebuild for `expo-clipboard`). **R.1 (dues reminders)** then extended the Phase-4 notify engine: a pure `buildDuesReminderMessage` (push + email, due-soon vs. overdue wording), a `dues_reminder_period` column on `member_dues` (migration `0016` — the "YYYY-MM" of the last reminder, so exactly **one reminder per billing period**, resetting automatically when a confirm rolls `next_due_at` into a new month), and a base-connection `claimDueDuesReminders` sweep (an atomic `UPDATE … RETURNING` that claims each due-soon/overdue member not yet reminded this period — concurrency-safe like the class sweep). It rides `runReminderSweep`, so the existing `/api/cron/remind` route now does both sweeps. _(ADR 46 removed all `vercel.json` crons; ADR [75](issues/75-daily-cron-on-github-actions.md) then put this sweep on a **daily GitHub Actions** tick, so dues reminders fire automatically. ## 1. Principles (the spine)

Four constraints drove every choice; when in doubt, re-derive from these:

1. **Minimal vendor lock** — portable/ejectable core: standard Postgres, open auth, no proprietary reactive engine. (Convex + Clerk deliberately rejected.)
2. **Simple now, expandable without a major refactor** — MVP is small; the _seams_ for later domains are placed now (§8).
3. **Solo builder, move fast, DX-first** — fewest moving parts; shared types; no codegen pipelines.
4. **Agentic-coding first** — a maximally conventional, well-documented stack agents know cold → the **create-t3-turbo** pattern.

We also carry forward three _patterns_ (not code) from the old app: **domain partitioning**, a **pure policy layer**, and a **structural tenancy seam**.

**Dependency direction:** `apps/*` → `packages/*`; packages never import apps. `db`, `validators`, `domain` are platform-agnostic leaves. **`packages/domain` must stay framework-free** so the server _and_ both clients import the same policy functions — this is the re-derived "pure policy layer" and the key testability seam.

## 4. Request lifecycle (the core path)

```
Client (web in-process | Expo over HTTPS)
  → tRPC procedure
    → auth middleware     : Better Auth validates session → ctx.user
    → tenant middleware   : read active academy (Better Auth activeOrganizationId) →
                            load the member row → assert status='active' + role →
                            open a tx and set_config('app.academy_id', id, true)  (ctx.tx)
    → procedure resolver  : calls packages/domain (pure) for decisions;
                            all reads/writes go through ctx.tx — Postgres RLS
                            filters every row to app.academy_id
      → Drizzle (pg) → Postgres (Neon, non-BYPASSRLS role)
```

The **procedure tiers**: `protectedProcedure` (authed) → `memberProcedure` (authed + active membership, opens the RLS tx) → `staffProcedure` (owner **or** instructor) → `ownerProcedure`. Because RLS filters in the database, resolvers can run plain Drizzle queries and still cannot read another academy's rows.

## 5. Tenancy — Postgres RLS (the load-bearing idea)

- **Shared DB, `academyId` on every tenant row, academyId-leading indexes.**
- **Postgres RLS is the guarantee.** Every tenant table has RLS enabled + a policy `USING (academy_id = current_setting('app.academy_id'))` (and a matching `WITH CHECK` for writes). Note `academy_id` is **`text`** (it holds Better Auth's `organization.id`, a random string, not a UUID) — the policy compares text to text, no cast. The app connects with a **non-`BYPASSRLS` role**. The tenant middleware opens a per-request transaction and runs `select set_config('app.academy_id', <id>, true)` (transaction-local) — the local scope matches the Neon pooler's checkout boundary, so the setting never leaks to a reused connection ([21]).
- **Why RLS, not an app-side `scopedDb` wrapper:** auto-injecting `where academy_id` into every select/join/update/delete is easy to get wrong (a missed join or raw query leaks). With RLS the middleware sets **one variable** and Postgres does the filtering — app queries stay plain Drizzle and **cannot** leak, even from a buggy query. This is the true by-construction property (the earlier "no RLS, scopedDb" plan was reversed by the review).
- **Deletion test:** remove the middleware and requests lose their `app.academy_id` → RLS returns _nothing_ (fails closed), not another academy's rows. Structural, not disciplinary.
- **Guardrails:** a lint rule forbids resolvers opening a connection outside the tenant helper; the CI **cross-tenant leak test** (foreign `academy_id` → assert empty) stays as a regression net on the policies.
- **Identity via Better Auth:** `organization` = academy (`academyId === organization.id`), `member` = membership (role + `status` pending/active), `invitation` = invite link. **These tables keep the plugin's own scoping — do not force RLS on them.** Global/cross-tenant tables (e.g. a future games catalog) get no academy policy and are reached by a trusted **service role** (an enumerated, server-only exception — used by system jobs, never request handlers).
- **Active academy** comes from Better Auth's `activeOrganizationId`; switching academy = `setActive()` → the next request's `app.academy_id` changes ([18]).

## 6. Auth flows (web + mobile)

- **Web:** Better Auth cookie session; server components/route handlers read it; tRPC middleware validates.
- **Mobile:** `@better-auth/expo` persists the session in `expo-secure-store` (Keychain/Keystore), auto-attaches it to tRPC calls; refresh validated server-side. **As built (mobile pass):** passwordless **magic link** (email only) — the client rewrites the relative `callbackURL` into the app's `matops://` deep link, so opening the verified link bounces back into the app and the auth gate routes onward. The server `trustedOrigins` must list the app scheme (`["matops://"]`) — the expo plugin only appends the session cookie to the verify-redirect when its location starts with a trusted origin (Expo Go's `exp://` is auto-added in dev). Custom-scheme deep links require a **dev build**, not Expo Go. The client mirrors the server's `user.phone` additional field with the `inferAdditionalFields` plugin (explicit schema) so it stays typed without importing the heavy `Auth` type.
- **Authorization** is _ours_: authN + org/role come from Better Auth; resource-level rules live in the tenant/role tRPC procedures.
- **Approval + the status trap ([14]):** Better Auth's access checks are **role-based and ignore our `status` field** — a `pending` member who holds a role would pass every check. So we **grant the role only at approval**: a student joining via the student link lands `pending` with **no role** (harmless); the owner approves → role assigned + `status='active'`. Instructors join active via the instructor link. Defense-in-depth: `memberProcedure` also rejects `status !== 'active'`. Pin the Better Auth version + an integration test (`additionalFields` inference bugs).
- **Contract discipline (mobile version skew):** store apps linger on old builds → tRPC procedures are **additive-only** (never change/remove a shape a shipped app calls). This is the one operational rule the internal-tRPC choice demands; enforce it in review.

## 7. Scheduling engine

- **Materialize lazily on save ([16]; cron removed in v1 — ADR 46):** creating/editing a `class_template` materializes its `class` rows out to the rolling **~6-week horizon** **immediately** (in-request), so schedules appear at once and stay filled for a multi-week pilot. Idempotent via `UNIQUE(templateId, startsAt)` + cursor `template.generatedUntil`. The **bounded daily cron** that re-extended the horizon cross-academy stays removed (ADR 46, 78, 79). Nothing fills the horizon automatically: a template save fills **six months** (ADR 79) and the owner's **Rebuild schedule** button regenerates the lot. The schedule read does **not** materialize. Time math (local `startsAtMinutes` + IANA tz → UTC instant, DST-aware) lives in `packages/domain`.
- **One-off classes:** `templateId` nullable → special classes cost nothing extra.
- **Class status is `scheduled | cancelled` only ([19]).** "Past/done" is **derived** from `starts_at + duration < now()` — no stored `completed`, no sweep job.
- **Booking = idempotent upsert + atomic count claim ([13], [22]) — as built (slice 3.1):** inside the request's RLS transaction (`ctx.db`), the `booking` router (`book`/`cancel` on `enrolledProcedure`) first upserts the `class_participation` row — `INSERT … ON CONFLICT (class_id, student_id) DO UPDATE SET booking_status='booked', … WHERE booking_status <> 'booked' RETURNING id` — so `UNIQUE(class_id, student_id)` prevents double-book, a returned row marks a real transition (new **or** re-book flipping `cancelled → booked`), and no row means already-booked (idempotent, count untouched). Then, **only on a real transition of a `confirmed` booking**, an **atomic `UPDATE class SET booking_count = booking_count + 1`** — v1 **drops the `booking_count < capacity` guard** (soft cap, never blocked, §4); the row lock still serializes concurrent claims (no `SELECT … FOR UPDATE`). **Two tiers ([22]):** `confirmed` (approved member) counts; `provisional` (pending member) is recorded + tagged "pending approval" but never moves the count. Cancel mirrors it (floored `GREATEST(count−1,0)`, confirmed-only). Both statements share the one request tx, so they commit/roll back together. This is why **no real-time is needed** for correctness — only display freshness, handled by polling.
- **Attendance = the second axis of `class_participation` ([08]) — as built (slice 3.3):** the same row carries `attendance_status` (`unmarked|present|absent`) orthogonal to booking, plus a `none` booking value for walk-ins (attended without booking — never counted). The `attendance` router is **staff-only** (owner + instructor see names): `list` (booked + walk-ins + drop-ins, with header counts via pure `attendanceCounts`), `mark`, and `addWalkIn`. Marking is gated to the **14-day backfill window** (`canMarkAttendance`, spec O5). Members `visitCount` ("attended N×") is a present-count grouped by student.
- **QR check-in = book + attend ([24]) — as built (slice 3.4):** the `checkin` router (`enrolledProcedure`) reuses the booking write **and** sets `attendance='present'` in one RLS tx — present even if full, idempotent, pending → provisional. `resolveCheckInClass` (pure) picks the current/next class **server-side** so the Expo app needs no domain dep. v1 has no camera: the app uses the active academy; the physical QR carries no-app visitors to the drop-in form.
- **Public drop-in = the one tenant-seam exception ([25], [12]) — as built (slice 3.5):** the `dropIn.submit`/`academyInfo` procedures are **`publicProcedure`** (unauthenticated). Having no session, they can't use `withTenant`; instead they call `@matops/db` helpers that write on the **trusted base connection** (table owner, bypasses RLS — we never `FORCE` it), each pinned to a validated `academy_id`. The `drop_in` table dedupes by `UNIQUE(academy_id, phone)` (repeat visit → `visit_count++`), carries its own contact + implied `present` attendance (a drop-in has no `user.id`), and has the standard RLS policy for **owner reads**. Consent is required (`z.literal(true)` + `canSubmitDropIn`).
- **Notifications ([17], [34]):** class-cancelled → push + email to booked students; class time/instructor change → push + email; membership-approved → push; class reminder → push. **Built in Phase 4** (as-built §0), but **nothing schedules the sweep** (ADR 46); the mobile reminder is a local notification the phone books at booking time (ADR 54). Three concerns, three layers (ADR 34): transport (`packages/notifications`, no DB dep, never throws), message text (pure builders in `packages/domain`), recipient resolution + orchestration (`packages/api/src/notify.ts`, base connection). No open connection, no comms domain.
- Full data model + invariants: [08] and [assets/schema-draft.ts](./assets/schema-draft.ts).

## 8. Expansion seams — how deferred domains plug in without a refactor

The whole "expandable" constraint lives here. Each deferred domain is **additive**: a new `packages/db/schema/<domain>.ts`, a new tRPC router mounted on the root, optionally new `packages/domain/<domain>` pure logic — no change to the tenancy seam, the request path, or existing tables.

| Deferred domain                          | Plug-point                                                                                                                                                                                                            | Why it's additive                                                                                                            |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Billing / memberships / payments**     | new tables (`membership_type`, `subscription`, `payment`) all carrying `academyId`; a `billing` router; a **payment-gate** step composed _before_ the booking resolver                                                | booking already funnels through one tenant procedure — insert a gate; nothing existing changes                               |
| **Curriculum / games**                   | `games` as a **global, cross-tenant** table (no `academyId`) reached via an explicit `globalProcedure` escape hatch (mirrors the seam's allowlist idea); academy curriculum tables are tenant-scoped and reference it | the seam already anticipates a small enumerated global set                                                                   |
| **Comms (announcements + in-app DMs)**   | `comms` schema + router. _(Transactional push/email already exist in v1 via `packages/notifications`; this adds the in-app messaging surface.)_                                                                       | no coupling to scheduling beyond reading class/booking ids                                                                   |
| **Belts / rank**                         | per-discipline `belt` + `belt_history` tables, tenant-scoped; a `curriculum`/`identity` router                                                                                                                        | pure additive; attendance recency signal already exists                                                                      |
| **Live in-app updates (WebSocket/SSE)**  | a **separate always-on worker** (Fly/Railway) holds the connections and listens to Postgres `LISTEN/NOTIFY`; mutations publish events to it; clients subscribe. _Cannot_ live on the serverless API ([15])            | "serverless publishes, a worker subscribes." v1 polling upgrades in place; the main API doesn't move (kept extraction-ready) |
| **Tiers / entitlements**                 | a single `getEntitlements(academy)` resolver + a gate; frontend hides nav                                                                                                                                             | one gate, not per-feature tier reads (old app's proven shape)                                                                |
| **Cross-academy views / hard isolation** | aggregated "all my gyms" screens are additive reads over existing memberships; harder physical isolation = promote a tenant to its own schema/DB                                                                      | RLS is already the v1 guarantee (§5); these are further steps, not the baseline                                              |

**Rule of expansion:** a new domain adds a schema file + a router + (maybe) pure logic. If adding one forces edits to the tenancy layer or existing tables, that's the signal the boundary is wrong — fix the boundary, not the caller.

## 9. Deployment topology

```
Vercel ────── apps/nextjs (web + tRPC API + /api/cron/* seams)           [Fluid compute]
Neon ──────── Postgres (single shared DB; Better Auth + domain tables)
                connect: pg driver → Neon "-pooler" endpoint, non-BYPASSRLS role
EAS ───────── Expo builds / OTA / store submission
GitHub Actions ── daily cron (ADR 75): curls /api/cron/remind (dues reminders) at
                    09:00 Lisbon with the CRON_SECRET bearer token. The class horizon
                    is the owner's button, not a cron (ADR 79). NOT the host's
                    scheduler — Vercel Cron stays removed (ADR 46), nothing is
                    host-locked. Daily, because on Neon Free each ping buys ≥5 min
                    of compute.
Expo Push ── phone notifications   |   Resend ── email       (both: outbound HTTPS)
```

**Escape hatches (nothing is a one-way door):** Next containerizes off Vercel (Docker → Fly/Railway/self); Postgres migrates by dump/restore; the tRPC routers (pure) extract onto `@hono/trpc-server` if a standalone API is ever wanted; **future live-UI adds a separate always-on worker** without moving the API; EAS is build tooling, not data lock.

## 10. Cross-cutting engineering

- **Migrations:** `drizzle-kit generate` (versioned SQL) in CI, applied on deploy; `push` in local dev only.
- **Validation & errors:** Zod at the tRPC boundary; typed error codes (re-derive the old app's `DomainError` set: `NOT_FOUND`, `FORBIDDEN`, `CLASS_FULL`, `BOOKING_NOT_ALLOWED`, …) surfaced as tRPC errors clients map to human toasts.
- **Testing:** unit-test `packages/domain` (pure → trivial); integration-test tRPC procedures against a test Postgres; **cross-tenant leak suite** in CI (asserts the RLS policies deny a foreign `academy_id`); a Better Auth `additionalFields`/approval integration test ([14]). This is why the pure/boundary split matters — the hard logic is testable without the framework.
- **Guardrails:** lint rule forbidding resolvers from opening a db connection outside the tenant helper (so `app.academy_id` is always set); `packages/domain` may not import React/Next/Expo/tRPC.
- **Observability (thin v1):** platform logs (Vercel/Neon) + an append-only `audit_log` table for owner-facing "what happened" — a documented next step, not built day 1.
- **Error tracking as-built (ADR [72](issues/72-sentry-error-tracking.md)):** `@sentry/nextjs` on the **web only**. `src/instrumentation.ts` loads the server or edge config by `NEXT_RUNTIME` and exports `onRequestError`, so a throw inside a tRPC procedure is reported with its request. `src/instrumentation-client.ts` covers the browser and App Router navigations; `src/app/global-error.tsx` catches a crash that escapes the root layout. `next.config.js` is wrapped in `withSentryConfig` for source-map upload, which needs `SENTRY_AUTH_TOKEN` set in Vercel (the local copy lives in the gitignored `apps/nextjs/.env.sentry-build-plugin`). The DSN is hardcoded on purpose: it is public, and a required env var would fail the build when unset. Tracing samples every request while the pilot is small. The Expo app reports nothing.
