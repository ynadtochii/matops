# Gym-owned Stripe payments: first integration

**Status: design only, not implemented. Updated 2026-09-29.** Start with optional, academy-wide drop-in payment. An owner can switch between all free and all paid drop-ins. Free mode keeps the current form and booking flow. Paid mode offers future classes starting at least 45 minutes from now; the owner chose **pay first, then book**. Failed or abandoned payment creates no visit. Stripe hosts account setup, Checkout, receipts, refunds and disputes. MatOps does not collect card details or issue refunds. Student membership payments remain off.

## Owner and gym account

- An owner connects an **existing independent Stripe account** or signs up for a **new account** through Stripe Connect OAuth. Link one account to the gym. Keep owner authorization, short-lived one-use OAuth state, live/test mode and unique gym/account mapping on the server. Read `charges_enabled` and capability status before offering paid Checkout. A Stripe return URL alone does not prove readiness. Stripe handles account setup; MatOps shows whether payments are ready. [Connect OAuth](https://docs.stripe.com/connect/oauth-reference)
- The owner chooses **Free** (no Stripe connection needed) or **Paid** (one configured positive academy drop-in price and currency; Stripe must be ready). Keep the price saved when switching to Free; Paid cannot be selected without a valid price and ready connection. All drop-in requests use the active academy mode, independent of the student membership payment gate. In paid mode the gym is the seller and manages money, receipts, refunds and disputes in its own Stripe Dashboard. MatOps takes no application fee. Use **direct charges** on the gym's account; the Stripe-hosted Checkout page uses its branding. [Direct charges and hosted Checkout](https://docs.stripe.com/connect/direct-charges.md?platform=web&ui=stripe-hosted)
- Revocation stops new Checkout Sessions. Keep the mapping for sessions already open so their payment events can still be handled. Do not switch a gym's account while a session is open; wait until it is paid, failed or expired. An owner can disable new paid sales without losing a record of old purchases.

## Visitor flow

1. Keep `/drop-in/<token>` and its email/phone lookup, required answers, agreement and class choice. Free mode keeps the current three-local-day class list, including an in-progress class. Paid mode shows only future classes that start at least 45 minutes from the time of the request; do not offer paid check-in to a class already in progress. Show the final gym price before payment. `dropIn.classes` already queries current rows and filters out cancelled, deleted and out-of-window classes, but the browser treats that result as fresh for 30 seconds. For a paid flow, refetch on return to the form and before opening Checkout; never use the cached list as payment eligibility. The server resolves the token and checks the live class state, paid cutoff, price, currency and connected account again when creating an attempt. Never accept these values from the browser. A visible class can still become unavailable during Checkout. If Stripe is unavailable in paid mode, say payment is unavailable; do not silently book for free.
2. Validate the form and class, then save a **payment attempt**, not a `drop_in_visit`. Save only the gym and academy IDs, lead/class IDs, quoted amount and currency, account ID, Checkout Session ID and payment state. The existing lead already stores contact and health answers; this integration adds no copy of those answers. Do not send contact details, health answers or agreement text in Stripe metadata. Stripe may collect payer details on its own hosted page; MatOps never sees or stores card data.
3. Create one guest Stripe-hosted Checkout Session in `payment` mode, with cards only, a single fixed-price item, **30-minute expiry** and no application fee. Redirect the visitor to Stripe's URL. Use the attempt ID as the idempotency key and reuse an open session for repeated taps. Persist the attempt first; retry session creation with the same key if the server stops before recording the session ID. Do not create a second open session for the same lead and class. [Checkout Sessions](https://docs.stripe.com/api/checkout/sessions/create)
4. Returning from Stripe means only that Checkout closed. Show **Checking payment**, **Booked**, **Payment not completed**, or **Paid, gym action needed**, based on server status. A signed-out visitor gets an unguessable purchase token for this status page; it returns no contact or health answers. Closing the browser, a declined card or an expired session creates no booking. A visitor may retry with a new session only after the previous one is known to have failed or expired. A booked or attended visit, including one created in free mode, must not be charged again.

## Payment event and booking

- Verify the Connect webhook signature on the raw body. Match its live/test mode, connected account, Checkout Session ID, amount and currency against the saved attempt. For cards, act only when the session has `payment_status = paid`. A browser redirect is **not** payment proof. Handle repeat or delayed webhooks without creating a second visit. The return page may retrieve the session through Stripe's API and run the **same** idempotent confirmation path to reduce wait time; webhooks remain required when the browser never returns. [Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted)
- On confirmed payment, use the existing guarded `drop_in_visit` write once, against the current class row. If the class remains scheduled, not deleted, and has not ended, book the selected future class, then mark the attempt fulfilled in the same database transaction. If a webhook arrives after class start but before class end, keep the original future-class booking choice. Do not repeat the three-day window or 45-minute cutoff after a successful charge; both were checked before Checkout. Pending, failed and abandoned attempts never enter the roster or booking count. The schedule rebuild and attendance-review queries treat every visit row as real, so an unpaid placeholder visit is not safe.
- When staff cancel a class, its next live drop-in query stops offering it. After cancellation commits, try to expire open Checkout Sessions for that class; Stripe API failure must not undo the cancellation. Expiration cannot stop a payment already completing. If a paid attempt arrives after cancellation, deletion or the class ending, **record it as paid, gym action needed** and tell the visitor to contact the gym. Show the owner the affected class, amount and Stripe payment reference in the existing action queue so a missed browser return cannot hide it. The owner handles a refund or another resolution **in Stripe**; MatOps never issues a refund or claims the purchase was booked. Refetching the class list cannot eliminate this race because Stripe and the schedule database do not share one transaction. Retry transient database and webhook failures before treating a charge as needing manual action. [Expire an open session](https://docs.stripe.com/api/checkout/sessions/expire)
- If the owner refunds a fulfilled purchase in Stripe, a signed Connect event updates its payment badge to refunded; it does not erase attendance or automatically change a booking. Staff use the existing class controls if cancellation is needed. Duplicate or out-of-order events must not overwrite a newer paid/refunded state. An owner can check a stuck purchase against its stored Stripe Session on the connected account. No scheduled job or in-app refund interface is needed in this release.

## Data boundary and implementation scope

Add one gym-to-Stripe account mapping, an academy-wide Free/Paid mode with an optional saved price/currency, and a payment-attempt record with unique provider IDs and an unguessable public status token. New academies start Free. Free mode uses no price for new bookings even if a previous price is saved; Paid requires a positive price and a ready Stripe connection. The attempt points at an existing lead and class. Keep a unique active attempt per lead/class; keep the existing one-visit-per-lead/class constraint. Store Stripe IDs, amount, currency and status, not card, bank or new visitor profile fields. Existing `drop_in` leads already contain email, phone and possibly health answers; promising that MatOps stores **no personal information** would be false. No new Stripe Customer record, card vault, product catalogue, payment dashboard, refund procedure, template/class payment column or Expo payment UI.

Keep the current free `dropIn.submit` path. The paid path reuses its validation and guarded visit write, but creates the visit only after verified payment. Owner-only connection and price procedures belong in the existing API. Only OAuth callback and Connect webhook need new route handlers. Scope public status reads to the purchase token and all writes to the resolved gym/academy. Structure-only migrations and focused DB/API tests accompany implementation. Update `docs/spec.md`, `docs/architecture.md`, an ADR, `docs/roadmap.md` and `CHANGELOG.md` with the actual behavior when built.

## Acceptance before launch

- In Stripe test mode, connect an existing independent account and a new account, finish setup, and test revocation. Verify platform and gym merchant countries are eligible. Free mode must work without Stripe; paid mode must refuse new Checkout when Stripe is not ready.
- Prove a free in-progress check-in, a free future booking and a paid future booking starting at least 45 minutes away. Paid mode must not offer in-progress or near-start classes. Try declined, abandoned, expired and repeated sessions; none may create an unpaid visit. Try duplicate webhooks, a missed return, class start during Checkout and a retry after server failure; paid fulfillment happens once.
- Turn paid mode off for a promotion and on afterward without losing its configured price. New requests follow the current mode, but earlier free or paid bookings keep their original status and quote. Expire open paid sessions after the switch. A session paid despite the switch uses its locked quote; if a free visit already exists for that lead and class, do not book twice and show the charge as **paid, gym action needed** for resolution in Stripe. Cancel a class while the public form is open: the refreshed list must remove it, and a stale selection must be refused before Checkout. Cancel again with Checkout open: attempt to expire the session. Prove any payment that completes despite cancellation is visible to both visitor and owner for manual Stripe resolution. Test a Stripe Dashboard refund and confirm MatOps updates the badge. No live cards or production deployment for design verification.

## Outside this first integration

Student membership payments, paid in-progress drop-in check-in, subscriptions, saved cards, SEPA and MB WAY, per-template/per-class pricing, MatOps-initiated refunds, MatOps billing gyms, automated reconciliation and a second payment provider. An academy-wide free promotion is based on when a visitor books, not the date of the class; date-specific free weeks need later class-level pricing. The withdrawn 2026-09-24 payment plan is not an implementation checklist.
