# Changelog

One line per shipped slice (see `docs/delivery.md` §4). Newest first.

## The app names its mat too (pivot wave 6)

- **The student app is back up, and a student can now train at two mats of one gym.** The academy they picked lives in secure-store and is read inside the tRPC link's `headers()`, per request, so switching mat never rebuilds the client. **`academy.setActive` is no longer how you change academy**: picking a mat is a local write plus a cache invalidation. The mutation survives for one job, because the session still holds the _organization_ — a mat belonging to a different gym still needs it, and the pick calls it only when the organization actually differs. Three flows had to remember the pick or the next request would name nothing: joining by code, joining by invite link, and the QR check-in deep link, where the poster names the academy and the app follows it. Sign-out clears the stored academy for the same reason it clears the query cache, and a fresh install picks the first academy the student belongs to. **One real bug fixed on the way**: `joinPending` set the active organization only when the session had none, so a student who already trained somewhere and joined a _second_ gym kept the first organization active and every request naming their new academy would have been refused. It now follows them to the gym they just joined. The rest of the wave was already true, which is what doing the schema first buys: join codes and invite tokens have resolved `entity` since Wave 2, the public booking key and six-digit code since Wave 3, the QR poster's URL since Wave 4, and `push_token` never carried an academy at all. New: 7 contract tests over **two mats of one organization**, the case every earlier public test missed by using two separate organizations — each key sees only its own classes, each mat has its own code and time zone, and `academy.current` follows the header between them. **1146 tests, all passing** (up from 1139), `next build` green, `pnpm typecheck` 17/17. Static gates only, per the plan: the device test is the human's.

## An owner can see both mats at once (pivot wave 5)

- **`/overview` gives an owner the totals across every academy they run, without weakening entity isolation by a single row.** `stats.organization` checks the owner **before** enumerating anything, so a non-owner never learns a sibling mat exists, then reads each academy inside its own `withScope({ organizationId, entityId })` transaction and combines the rows with a pure function. There is no organization-wide query and no relaxed policy: two mats cost two transactions, which is slower than one big read and is the point, because the alternative is a mode where one query can see two academies. The per-academy reader reuses `academyTimeZone`, `rosterOf` and the confirmed-revenue reader the entity's own dashboard already uses, so no figure has a second implementation to drift from. `EntitySummary` carries `memberUserIds` rather than a count, because **a person who trains at two mats has to count once**: in the test fixture that is 5 seats and 3 people. Money is grouped by currency through the same helper the referral ledger uses and never summed across them, and each academy keeps its own time zone. The screen shows the totals, a **Waiting on you** list ordered by how much is queued, and one card per mat; a non-owner sees the plain list and nothing more. No metrics projection: the plan parks that until a measurement asks for one. One thing the build taught us: a server component that prefetches must read request data first, or Cache Components refuses the build the moment the procedure reaches for the clock. **1139 tests, all passing** (up from 1125), `next build` green, `pnpm typecheck` 17/17. Mobile is still down until Wave 6.

## The URL names the academy (pivot wave 4)

- **Every owner and student screen moved under `/entities/[entityId]`**, and the session stopped choosing which academy you are looking at. A URL that names its mat is what makes two browser tabs show two academies, a reload keep the one you were on, and a link you paste to a coach open the right place. `academy.setActive` is no longer how you switch; a link is, so `AcademyGate` and `AcademySwitcher` are gone. Above the entity sit `/overview`, which lists the academies you may open and is reachable without choosing one, and a `/profile` that only forwards. The browser sends `x-matops-entity` from `window.location.pathname`; a server render cannot read that header and has no pathname, so the entity layout writes the id into a `cache()`-scoped holder that the RSC tRPC context reads. **No middleware.** `AcademyProvider` became **`EntityProvider`** across 23 files, with a new `OrganizationProvider` beside it holding the places you may open and whether you may add one; `entity.list` answers both in one read. `ROUTE_ACCESS` and `canVisit` moved into `packages/domain`, where they are finally tested: `canVisit` reads the path after the entity segment and refuses **every** screen for a place that is not a BJJ academy, so there is no second list to keep in step. The selector is a set of links with an owner-only **Add academy** that offers only `bjj_academy`. One real bug on the way: `createContext` in `server.tsx` was cached per request, so the entity was frozen at the first tRPC call — which happens in the organization layout, before any entity is known — and every screen under the entity would have server-rendered against no entity at all. The session read stays cached; the entity is read per operation. A stated deviation from the plan: `/profile` shows the academy name, address, role, join date and belt, all facts about one mat, so the screen lives under the entity and the old path redirects. **1125 tests, all passing** (up from 1110), `next build` green, `pnpm typecheck` 17/17. The web client works again; **mobile is still down until Wave 6 sends the header**.

## Every row belongs to one mat (pivot wave 3)

- **The whole BJJ product moved onto the entity.** `member_id` stops meaning a Better Auth `member.id` and means `entity_membership.id`: the readers, the writers, both seeds and the api fixture all moved, and migration `0046` adds **ten composite foreign keys**, `(academy_id, member_id) -> entity_membership(entity_id, id)`, which is what stops a dues row at one mat naming a membership at another. The four tenant tiers keep their names and are now built on `enforceEntity`, so all 145 procedures in 21 routers run at the entity named in `x-matops-entity`; `enforceTenant` and `resolveActiveMembership` are gone, and nothing picks a place from the session any more. **No product query reads academy settings from `organization`**: the public booking API, `getAcademySettings`, `academyContext`, the drop-in form, the code lookup, the class-reminder cron and the switcher lens all read `entity` and `academy_profile`, so **a gym with two mats publishes two booking links with two keys** and shows two academies in the switcher. Two bugs fell out of the new keys. A permanent erase left the erased person's id in **other students' referral history**, which was a dangling string before and is now refused outright; it clears both referrer columns. And `wipe-academies.sql` was two waves out of date and would have failed on the first `DELETE FROM "organization"`. Policies and indexes needed no rewrite, because `academy_id` and `app.academy_id` kept their names and changed meaning; `rls-coverage.test.ts` now proves the point, asserting that **every table carrying `academy_id` has a foreign key into `entity`** and that the one row joining two parents still carries the organization match. New in `rls.test.ts`: three tests over **two entities of one organization**, the first proof that a shared owner does not mean shared data. Dev was wiped, migrated to **47 rows** and reseeded. **1110 tests, all passing** (up from 1097), `pnpm typecheck` 17/17, five packages lint clean. **Both clients are down until Wave 4 and Wave 6 send the header**, which is what a hard cutover costs: every tenant tier now refuses a request that names no entity. `dev` is not mergeable until Wave 7.

## A membership belongs to one mat (pivot wave 2)

- **`entity_membership` becomes the operational access record.** Migration `0044` repoints `academy_invite` at `entity`, so a link names one academy rather than the whole gym, and `resolveInviteToken` returns the organization above it. `findAcademyByCode` reads `entity` too, because **a gym's second academy has a six-digit code no organization row carries** and the mobile code search would have found nothing for it. A join now writes two rows for two jobs: the Better Auth `member` row records that the person belongs to the organization and is **reused untouched when it is already active**, so opening a link to a second mat cannot reset the first membership to pending, and the `entity_membership` row is the pending one carrying the invited role. Approval, rejection, suspension, restore, archive, removal, promote and setRole all moved onto that row, and the never-ownerless guard now runs **twice**: once over the mat's memberships and once over the organization's, because writing the Better Auth mirror means demoting yourself at one mat also strips the organization role that was your only way into the other. Erase got the same treatment: purging someone from one mat takes their membership of that mat, **keeps the organization membership that is their way into the other**, and keeps their sign-in account. Two bugs fixed on the way: `softDeleteAcademy` set `organization.deleted_at` and left every entity live, so a closed gym stayed findable by its code; and the api test fixture built no entities, which is now the real provisioner. `member.role` and `member.status` stay as a **mirror** until Wave 7 drops them, because both clients still use the academy tiers. **1097 tests, all passing** (up from 1078), `pnpm typecheck` 17/17, five packages lint clean. Nothing user-visible changed.

## The organization gets its first entity (pivot wave 1)

- **The foundation, behind the old model rather than replacing it yet.** Migration `0042` adds `entity`, `academy_profile` and `entity_membership`, and `0043` gives them RLS: `entity` and `entity_membership` match on the new **`app.organization_id`**, `academy_profile` matches on `app.academy_id`, which now holds an **entity** id and keeps its Postgres name. `withTenant` becomes **`withScope({ organizationId, entityId? })`**, still one round trip; omitting the entity leaves `app.academy_id` unset so an organization transaction cannot read entity rows by accident, and an empty entity id is refused rather than treated as absent. **No foreign key cascades**, and `entity_membership(organization_id, entity_id)` keys into `entity(organization_id, id)`, which is what stops a membership reaching a sibling organization's entity. Six new procedure tiers read the entity from the **`x-matops-entity`** header instead of the session, so two browser tabs can show two places: a missing header is a `BAD_REQUEST`, and a foreign entity, an unknown one and a soft-deleted one all answer `FORBIDDEN` with the same message, so the header cannot enumerate other people's gyms. An active organization owner reaches every entity; everyone else needs a live `entity_membership`. **`provisionOrganization` is idempotent**: it makes the default entity (the organization's own id and public code, so printed QR posters still resolve), the academy profile, the owner membership and the curriculum track, runs from both the Better Auth hook and `academy.create`, and repairs an organization whose setup died half way. Owner-only **`entity.create`** adds a second academy with its own id, slug, public code, curriculum and membership rows. Caught on the way: `generateAcademyCode` checked only `organization.public_code`, so a second academy could have been minted a code another gym already held. **1078 tests, all passing** (up from 1040), `pnpm typecheck` 17/17, five packages lint clean. Nothing user-visible changed yet: the web and mobile clients still send no header and still use the academy tiers.

## The organization will own typed entities (pivot wave 0)

- **Docs only, no code and no schema.** An owner opening a second location cannot run both from one login, because the Better Auth organization is also the academy: the tenant, the settings, the public code, the member scope and the session's active context are one row. ADR [124](docs/issues/124-the-organization-owns-typed-entities.md) fixes the replacement before any schema is written. The **organization** becomes the owner group, a typed **entity** becomes the place (only `bjj_academy` in this pivot), and **`entity_membership`** becomes the operational access record, so one person can own one mat and train at the other. Every request names its entity in the **`x-matops-entity`** header instead of the session, which is what makes two browser tabs and a shareable URL possible; a missing header is a `BAD_REQUEST` and a foreign one a `FORBIDDEN`, both before a transaction opens. **RLS stays exact:** `academy_id` and `app.academy_id` keep their names and hold an entity id, `app.organization_id` joins them, and no mode reads every entity at once. The inventories were read off the dev database, not guessed: **21** tables carry `academy_id` (`notification_pref` is dead and gets dropped, `academy_invite` has no policy on purpose), only **14** foreign keys exist in the whole schema, **12** `member_id` columns across 7 tables move to `entity_membership.id` and **10** columns keep pointing at `user.id`. The matrix decides that **no BJJ table gains an `organization_id`**, because the `academy_id -> entity.id` key already proves one organization per row. `docs/architecture.md` and ADR [18](docs/issues/18-multi-academy-ux.md) now say plainly which model is current and which is the target, and `CLAUDE.md`'s claim of 27 failing tests was stale: the suite is **1040 tests, all passing**. The plan is [organization-entity-pivot.md](docs/organization-entity-pivot.md) and the run file is [organization-entity-pivot-epic.md](docs/organization-entity-pivot-epic.md).

## The web app fits a phone

- **No control was big enough to hit.** `webSize` in `packages/ui/src/button.tsx` had a 44px floor for `size="sm"` and nothing else, and even that never ran: `buttonClass` gated it on `size && webSize[size]`, and `size` is `undefined` whenever a caller takes the default. Every size now carries `min-h-11` up to `sm:`, `Input` and `Select` are `h-11 sm:h-9`, and `DropdownMenuItem` gets the same floor. An icon that sits inside a line of text keeps its drawn size and grows only its hit box, through `TAP` in `primitives.tsx` and `ICON_BTN` on the curriculum screen.
- **`Select` zoomed iOS Safari on focus.** `Input` and `Textarea` both carry `text-base md:text-sm`, the rule that stops a phone zooming into a focused field. `Select` was `text-sm` at every width, so a form's select jumped the page while its inputs sat still.
- **Seven tabs shared a phone's width.** An owner's bottom bar gave each tab 53px at 390px and 45px at 320px. Past `MAX_TABS = 5` the tail moves into a **More** menu and the hidden items' badges are summed onto that tab, so a waiting payment claim still shows. The mobile header drops its theme toggle and sign-out, which the Profile screen the avatar opens already holds, and the four controls left are 44px instead of 32px.
- **Three skeleton bars were wider than the phone.** `w-96` is 384px inside a 327px column, so the page scrolled sideways while it loaded. Dialogs use `dvh` rather than `vh`, tighten to `p-4` on a phone, and keep the title clear of the close button; tab strips scroll instead of clipping their tail; the schedule header and the one-off class form wrap.
- Verified with Playwright against a signed-in owner at 390px and 320px across every app route and the four public pages: no sideways scroll, no control under 40px, no text field under 16px. ADR [123](docs/issues/123-the-web-app-fits-a-phone.md).

## The lead phone keeps its country code, and a cancelled visit stays off the register

- **`normalizePhone` no longer throws the `+` away.** `drop_in.phone` is both the dedupe key behind `UNIQUE(academy_id, phone)` and the number the owner dials back, and stripping the plus served the first at the cost of the second: `351912345678` does not say whether `351` is a country or an area. It now strips the formatting only, so two spellings of one number still collapse, a number typed with no country code is still left alone, and `canSubmitDropIn` counts digits directly so its floor did not move. Amends ADR 119, which had said storage was untouched. The hand-run fill for rows written before this is `packages/db/scripts/2026-08-31-lead-phone-plus.sql`, which prefixes only a row whose digits start with the academy's own dial code and guesses at nothing else.
- **`attendance.markVisitor` refuses a cancelled visit.** It matched on `(visit_id, class_id)` alone, while `attendance.list` and every class count filter cancelled bookings out, so a cancelled visit could be marked present and then be invisible on the register it counted toward. Spec §O5 already says a cancelled visitor booking leaves the register entirely. One `ne()` in the where clause, the guard every sibling query already had. Not reachable from the UI, which never draws a cancelled visit.

## The booking page groups by day and opens on three of them

- **A flat list of every class in seven days is a wall.** Sharing the beginner classes turned the picker into fifteen rows a stranger had to read before they could choose. It now groups by day, names Today and Tomorrow, and opens on the next three days that have a class, with the rest behind a **Show the rest of the week** link.
- **Picking a class collapses the list to that class.** Even grouped, eight rows two lines tall pushed the form off the bottom of the screen, so somebody who had just chosen a class saw no reason to scroll and no sign there was anything left to do. The picker now folds to the chosen class with a **Change** button, and each row is one line (time, title, length) instead of two, so the choice and the form fit together.

One optional parameter in `packages/domain/src/format.ts` rather than a second copy of the rule in the page.

## The beginner-friendly classes are on the trial page

- **A stranger asking about a trial should land on a class they can walk into.** `packages/db/scripts/2026-08-31-share-beginner-and-all-levels.sql` shares the Beginner and All-levels templates and their future classes for academy `990001`, and leaves both Inter-Advanced templates private. Scoped by academy code rather than by title alone, so a second academy with a class called "Beginner" cannot be caught by a re-run, and it only ever sets the flag on, so nothing it does not name can be switched off by running it. **Run against Neon 2026-08-31:** 6 templates flipped, 311 future classes; the trial page now lists 15 classes in the next week.

## Ticking "Share this class publicly" now reaches the classes

- **The tick saved on the template and never reached a class.** An owner ticked it on an existing template, saw it stay ticked, and `/book/<code>` still said no classes were open. `templateContentChanged` in `packages/domain/src/class-edit.ts` decides whether a template edit rewrites its future classes, and `publicBookable` was missing from its field list, so an edit that changed only that flag returned `"none"` and the in-place update never ran. The flag reached a class only when one was generated, which for a live academy had already happened for the next 180 days. One field added to the list; the in-place update already copied it.
- **A one-time fill for the rows already stranded.** `packages/db/scripts/2026-08-31-sync-public-bookable.sql` syncs future, non-cancelled, template-owned classes to their template's flag. Safe to run twice, and one-off classes are left alone because they carry their own flag. **Run against Neon 2026-08-31:** 77 rows across three templates, all ticked on the template and private on the class; the re-check reported zero.

## The link is two taps away, from every screen

- **A Share control in the shell, for all staff, on every screen.** Someone messages the gym asking about a trial and whoever is holding the phone wants to paste a link and get back to the mat. The trial link lived four steps deep in owner-only Settings, so the instructor who reads the gym's messages had no path to it, and the join link was on a third screen, so the wrong one got sent. All three now sit side by side in one dialog — the booking page, the wall check-in form and the join link — each saying who it is for, with Copy, Share and QR. ADR [122](docs/issues/122-the-link-is-two-taps-away.md).
- **It copies the links, it does not move them.** Settings keeps the public booking setup, and Members keeps the invite card and the printable check-in poster, because that is where an owner configures them, with the key and the allowlist beside them. The dialog is the place you reach with someone waiting for a reply.
- **`academy.shareLinks`, staff, three fields.** The master switch, the code the URL is built from, and whether a class is actually open for booking. It is deliberately not the owner-only `publicApi` query, which carries the publishable key an instructor has no use for and should not hold. It runs only when the dialog opens, so the shell boot path is untouched.
- **The two silent gates now speak.** Public booking off, or no class shared this week, and staff could copy a perfectly formed URL that led nowhere. The row says which one it is; an owner gets a one-tap "Turn on public booking", an instructor is told who can fix it and never shown a button the server would refuse. The shared-class check reads the same seven-day window the visitor's page asks for, through the same query, so the answer cannot drift from what the visitor sees.
- **`invite.list` drops to staff, minting stays owner-only.** `/members` is a staff route rendering an owner-only query, so an instructor opening it got an error card where the invite belonged. Reading a link grants nothing — an owner still approves every join — and `InviteLinkCard` now hides Create and Rotate from a non-owner.

## The policy comes to the form, and the mat has a warning on it

- **The privacy link opens a dialog instead of another page.** It was an `href`, so a stranger who wanted to know what the gym stores before ticking the box left a form holding their name, phone, email and class pick, and got it back only if the back button behaved. The form now stays mounted underneath: nothing is remembered or restored, because nothing is unmounted. ADR [121](docs/issues/121-the-policy-comes-to-the-form.md).
- **One copy of the words.** `policy-text.tsx` holds the prose with no page chrome, so `/privacy` and the dialog render the same component. Two copies of legal text drift the first time one is edited.
- **A second tick, for the risk.** Grappling is full contact, and someone booking their first session was told the gym would contact them and nothing else. A required checkbox now says so, with the notice a click away, naming the academy rather than matops because the liability limit is the gym's. It says plainly that it is not the waiver, which is still signed at the desk.
- **The tick gates, it does not record, and that is the decision.** No column, no field on the public booking schema, no migration. The gym already relies on the waiver signed at the desk, and a tick on a stranger's phone would be a weaker copy of a document that exists on paper, so storing it would only invite someone to treat it as the stronger one.
- **The privacy page says less.** It listed the companies running parts of matops by name, along with the database, hosting, email and error-reporting vendors. Someone deciding whether to leave a phone number does not need our stack, and a vendor list goes stale the first time one is swapped. What is left is the two facts a reader needs: the data is stored in the EU, and whoever handles it does so on our instructions. The rest of the page was cut to the same standard.

## A form never goes dead

- **A submit button is disabled only while its request is in flight, never for validation.** A visitor typed something that was not a phone number and hit a dead end: `toE164` cannot represent it, so the form held an empty string while the box still showed the text, and `canSubmit` quietly killed the button. A disabled button states no reason, and because submit never fired the browser's own check on the invalid email never ran either. The same three conditions held on the public `/book/<code>` page. ADR [120](docs/issues/120-a-form-never-goes-dead.md).
- **The phone field stops eating input.** Characters a phone number cannot contain are dropped as they are typed, so the visible value and the value the form holds can no longer disagree. That is the root fix and it covers all six forms sharing the field.
- **Errors land on the field, in words a stranger can act on.** Each form parses the exact payload it is about to send with the same schema the procedure uses, so client and server cannot disagree about what is valid. One message per field through the existing `FieldError`, `aria-invalid` on the control, focus to the first bad one, and the message clears as soon as that field is edited. A refused drop-in also refetches the class list, so a class that closed while the form sat open stops being offered.

## One way to ask for a phone and an email

- **Every form asks for a phone the same way.** A country picker beside the number, opening on the academy's own country, so the common case is that nobody touches it. What reaches the server is one format, `+351912345678`, instead of six spellings of the same number. ADR [119](docs/issues/119-one-way-to-ask-for-a-phone-and-an-email.md).
- **Email completes the domain after the `@`.** Type `sam@g` and `sam@gmail.com` is offered. It is a native browser suggestion list, so it works with the keyboard and on a phone, and there is nothing to dismiss.
- **One component each, eleven fields replaced.** The profile edit, both steps of the invite join, the code join, the walk-in row on the roster, the wall-QR drop-in, the public booking page, sign-in and the promote dialog all use the same two.
- **No phone library.** Per-country length rules would cost 75-145 kB against a bundle floor that is already the biggest thing on the frontend budget. The country is picked, not guessed, which is most of the value. One gap is named rather than papered over: a leading zero is dropped from the international form, right nearly everywhere and wrong for an Italian landline.
- **Migrations are structure only from here on.** Tables, columns, indexes, constraints, policies and grants. A fill for existing rows is a hand-run script in `packages/db/scripts/`, because a migration runs everywhere and forever while a fill is usually right once, on one database. `0041` adds the column and nothing else.
- **The academy sets its country in Settings.** A time zone is a good guess and nothing more: zones cross borders and our map does not cover every one. Set it once and every phone field on every screen opens there. Until you do, the guess still applies and the setting says so.
- **Numbers already saved are left alone.** Backfilling would mean guessing a country for each one, wrong for any member with a foreign number. New writes are consistent and the existing match keeps bridging both.
- **Mobile keeps its four fields for now**, so the schema still takes a number with no country code. That branch goes when the Expo fields are rebuilt.

## The owner makes the account

- **An owner turns a lead into a member, and the person just signs in.** Before this the owner copied the academy-wide link, sent it themselves, and the lead then typed an email, waited for a magic link, retyped the name and phone the gym already had, and waited again to be approved. "Make them a member" on the lead does all of it: the dialog shows the email back, writes the account, and the person signs in with that address whenever they like. ADR [118](docs/issues/118-the-owner-makes-the-account.md).
- **Nothing is sent, so the dialog says to tell them yourself.** Resend still carries the sign-in magic link and nothing else.
- **Two gates, and one of them is not fixable.** A front-desk visitor never agreed to be contacted, so the action is not offered on them at all. A lead with no email is offered it and the dialog asks for one, which is also the first way to store an email an owner was given by voice.
- **A new address is active at once; an address that already has an account lands pending.** That second person is real, maybe at another gym, and never asked to join this one, so they keep their say on the requests tab. Their name and phone are left alone.
- **Approving and promoting now share one path**, so a promoted member cannot land on dues differently from an approved one.
- **The wall-QR drop-in form now requires an email.** It was optional, and a lead without one can only be reached through a channel matops never sees. The public booking API already required it, so the front desk is now the last path that writes a lead with no email, for the same reason it writes one with no consent: staff are recording a person, not asking them anything. Rows already saved keep whatever they have, and the owner can fill one in.
- **The lead tabs carry a count on New only.** A badge on every stage read as data rather than as a queue.

## The visitor picks the class

- **The drop-in form asks which class, instead of the server guessing.** It attached a class only when exactly one was running, so two mats going at once left the lead attached to nothing, losing the one fact the gym wanted. The form now offers the classes on now (picking one marks them present) and the ones coming up (picking one books them, so staff can mark them absent later), plus "I'm just visiting". One class on is pre-selected, so the common case is still one tap. ADR [117](docs/issues/117-the-visitor-picks-the-class.md).
- **A walk-in between classes can book the evening session from the wall poster.** That is the public booking API's job, done for the person already standing in the gym rather than only for the gym's website.
- **The pick is re-checked on the server.** `classId` rides an unauthenticated write, so the submit re-resolves the lists and refuses an id not on them: a class that ended while the form sat open, one the owner cancelled, and another gym's class are all the same refusal. No new write path: `createDropIn` and `bookVisitor` are the helpers the front desk and the public API already use.

## Rate limiting and the cost ceiling

- **Every public tRPC procedure carries a cap now.** The limit used to be opt-in at each call site, so `system.health` and `auth.getSession` had none. `publicProcedure` includes a 120-a-minute per-address brake, and because `t` is private to `trpc.ts` that is the only door onto the unauthed surface, a new public procedure cannot ship without one. The three procedures with a tighter cap of their own are unchanged. ADR [116](docs/issues/116-rate-limiting-and-the-cost-ceiling.md).
- **The edge, not the code, is what caps the bill.** Every limiter we can write runs inside the serverless function, so a 429 we return is one we paid for. A Vercel WAF rule blocks before the invocation and costs nothing. Written up with the numbers, plan limits and the batching gotcha; the rule itself is an operational step and is **not applied yet**.
- **One suspected cost does not exist.** An unauthenticated flooder cannot make `getSession` query Neon: Better Auth checks the cookie signature in-process and returns before touching an adapter. The lazy-session refactor this would have justified is recorded as unnecessary rather than left pending.

## The public booking API and the drop-in lead path

- **A visitor's classes are their own rows.** `drop_in_visit`, one row per lead per class, with the same booking and attendance axes a member's row has. This fixes a live bug: a visitor recorded on Monday and again on Wednesday used to disappear from Monday's register, because a lead held a single class pointer that the second visit overwrote. Migration `0037`. ADR [115](docs/issues/115-public-booking-api-and-the-lead-path.md).
- **A booked visitor can be marked absent.** Before this a visitor was present by construction, so someone who booked online and never turned up could not be recorded as a no-show. Spec: O5.
- **Every stage move on a lead is an explicit tap**, and all of them live in one `⋯` menu beside the row, the same shape the member row uses. Copying the join link and marking someone invited are two separate items: an owner copies a link to look at it, or sends it through a channel matops never sees, so a copy is evidence of nothing.
- **A lead is a stage plus what the person did.** `new` / `contacted` / `invited` / `joined`, with `ghosted` as a side exit that deletes nothing, beside a derived activity line ("trained 2 times, last 12 Aug"). Filter chips and four funnel numbers on the Drop-in leads tab, and each lead records where it came from. Migration `0038`. Spec: O4.
- **The dashboard queue gains "Trained, not joined" and loses the 7-day window.** Both lead items now reach zero, because a stage is the handled flag the queue never had. Spec: O1.
- **Joining links the lead automatically**, matched on the last nine digits of the phone, so a country code written on one form and not the other still matches. Manual "mark as joined" stays for the rest, and it is a link to a member.
- **Share one class publicly**, off by default, on the recurring template and on a one-off. The flag is copied onto each class as it is generated, so unsharing one date leaves the template alone. Migration `0039`. Spec: O3.
- **Public booking, one switch in Settings.** It mints the academy's publishable API key, turns on the shared link at `/book/<code>` with a printable QR, and takes an optional list of websites allowed to call the API. Off by default. Migration `0040`. Spec: O6.
- **A small public REST API per academy**: read the shared schedule, book a visitor, cancel. The key names the academy, so no path carries an academy id. Capacity never blocks a booking and never appears in a response. An unshared class answers "not found", never "forbidden". Integrator page: [docs/public-api.md](docs/public-api.md).
- **A public booking always makes a lead**, never an account and never a member. Booking closes 60 minutes before the class starts. Cancelling takes the person off the register and keeps the lead.
- **The API's limits are product rules, not a cost ceiling.** Six buckets on the in-process brake (per key, per address, per phone, per academy), each carrying `Retry-After`. The bill is a separate layer, ADR [116](docs/issues/116-rate-limiting-and-the-cost-ceiling.md).
- **The visits table has three readers and a test that says so**: the roster, the leads screen and the public API. No statistics query may join it, so drop-ins still count in no member statistic, attendance rate or coach workload.

## The class card, and the poster's home

The curriculum theme loses its violet slab for a brand hairline. No API or domain change.

The roster list and row classes moved to `primitives.tsx` so the shape and its skeleton cannot drift.

It still draws the active **templates**, and now reads that list itself (the route already prefetches it) instead of taking it as a prop. Spec: O3.

## A note on one run of a block

- **Every run of a block takes its own note.** The block's notes say what it covers, everywhere it appears. **This run** says what these two weeks are doing about it, with this group. Writing one changes no other run and does not touch the block. ADR [113](docs/issues/113-a-note-on-one-run.md).
- **It shows up on the class**, under the theme, labelled This run.
- **You can still write it after the weeks have passed.** It is the one thing a finished stretch lets you change apart from the block's name, so it is where "what we actually covered" goes.
- **Students never see it**, the same as your block notes.
- Taking a block off the plan takes its run note with it, and Undo puts both back.

## Two blocks on the same weeks

- **A stretch of weeks can teach more than one block.** Standing and Pinning run together over the same fortnight instead of one after the other. ADR [112](docs/issues/112-several-blocks-on-one-stretch.md).

- **Taking one block off a stretch moves nothing.** The dates belong to the stretch. The last block leaves by taking the whole stretch off the plan.
- **A class shows every theme running that week**, above the roster and on the class page, in the app too.
- **Deleting a track no longer refuses when classes follow it.** Those classes go back to the default track, and the confirm says how many. Rename and delete now sit in a menu on the track's own chip, behind a three-dot button.

## One gym, several curriculums

## The block you are teaching now is yours to change

- **The block running this week has the same buttons as every other one.** Shorten it, lengthen it, move it up or down the plan, rename it or take it off. Before, it could only be made longer. ADR [109](docs/issues/109-the-running-block-is-editable.md).

## The plan runs Monday to Sunday

- **Every week on the curriculum timeline starts on Monday**, and so does every block. The rows now line up with the week numbers beside them, and with the week grid on the This week tab. ADR [108](docs/issues/108-the-week-starts-on-monday.md).

- **Every button on the screen answers the keyboard** with a visible focus ring, and presses in like the rest of the app. The arrows, the stepper and the grips are drawn icons now rather than typed characters, so they match the weight of the text beside them.
- **A block that has already run looks like a record**, a soft filled row instead of a dashed outline, which everywhere else in the app means something is missing or cancelled.
- **Today's date sits on the now-line**, and an empty plan says what to do instead of leaving you a page of blank weeks.

## Your blocks go in folders

- **Blocks are filed under categories now**, so a library that has grown to sixty of them is still readable. You see a short list of category names with counts, and open the one you want. ADR [107](docs/issues/107-block-categories.md).

## The plan is a blank year you fill in

- **The timeline is always there now**, even with nothing on it: a run of weeks with the week number and month down the side, so you can see where a block would go before you have any. ADR [106](docs/issues/106-the-timeline-is-a-run-of-weeks.md).
- **Drag a block's bottom edge to make it longer or shorter.** The blocks below move as you pull, and nothing is saved until you let go.
- **Drag a block's grip to move it up or down the plan**, and the blocks in between shuffle out of the way while you drag.
- **Dragging works with a finger now.** The old version only answered a mouse.
- **Blocks on the plan show their notes**, so a row tells you what the block covers instead of just naming it. A one-week block leaves them out, since there is no room.
- **Every block has an edit button**, on the plan and in your library, and both open the same block. Blocks that already ran can be renamed too, even though their dates are fixed.
- **The buttons all still work**, and the resize handle takes the arrow keys, so nothing here needs a pointer.

## Blocks are yours to keep, and you drag them onto the plan

- **Curriculum has two halves now: your blocks, and the plan.** A block is a theme your gym teaches, with notes and a usual length. It stays in your library, and you can put it on the plan as often as you like. ADR [105](docs/issues/105-a-block-library-and-a-drop-target-timeline.md).
- **Drag a block onto the plan**, and a violet line shows where it will land. Drag one already on the plan to move it. Everything after it slides down.
- **On a phone, or with a keyboard, press Add to plan** and use the arrows. A drag does not work on touch, so the buttons are the whole feature there, not a fallback.
- **Nothing can be dropped onto a part of the plan that has already started.**
- **Taking a block off the plan no longer asks first**, because you can put it straight back with Undo. Deleting a block from your library still asks, and it refuses while the block is on the plan.
- **Renaming a block renames it everywhere it appears**, so a better name fixes the whole plan at once.
- **The same theme can run for different lengths each time.** The library holds how long it usually runs; the plan holds how long it runs this time.

## Your gym's plan is a timeline you can shove

- **Schedule has a Curriculum tab.** Write the themes your gym works through, one block at a time, and see them as a column where a block's height is how long it lasts. ADR [104](docs/issues/104-curriculum-blocks-as-a-timeline.md).
- **Ran long on closed guard? Press +1 week.** Every block after it moves with it. You used to have no way to plan this at all, and the alternative was re-dating a dozen rows by hand, which is why gym plans rot.
- **Ran long? Press + on the block you are on now.** It uses the same stepper as every other block, with the − switched off, because a block that has started can be extended but never shortened.
- **Blocks that already ran do not move.** They read as a record, with no controls, because the plan should never contradict the register.
- **Every change says what it did and can be undone in one press.** "Passing now runs 3 weeks. 6 blocks after it moved. The plan now ends Dec 21", with an Undo beside it.
- **Length is set in weeks, never "a month"**, because a month is four weeks or five and the dates would drift.
- **Owners and instructors both write it.** Students do not see it yet.
- **Not yet:** the theme does not appear on tonight's class screen, and there is no place to log what you actually taught. Both are the next slice.

- **Deleting a class template, rebuilding the schedule, and cancelling a class are covered.** These are the three actions that can clear a gym's calendar.

- **Booking a class, or marking a register, now updates the gym's numbers straight away.** They used to keep showing the old figures for up to two minutes: the insights, the "who's drifting" list, and a student's own training stats. ADR [98](docs/issues/98-fewer-round-trips-and-one-invalidation-rule.md).

## The reminders get a safety net

- **The class and dues reminders are tested for the first time.** They are the one part of the system that runs on its own, with nobody watching. A broken screen gets reported the same day. A broken reminder is silent: the gym just stops hearing from us. ADR [97](docs/issues/97-the-notification-path-gets-a-test.md).
- **A gym that has closed, a cancelled class, and a member who has left are all now proven to be left alone.** Each was already handled in the code and none of it was checked.
- **If the push service is down, the message still reaches the inbox.** That was already true by design, and now a test says so.
- **Both scheduled endpoints share one door check.** They had a copy each, so the two could drift apart while both looked right.

## One definition per rule

- **Checking in to a class you did not attend is no longer possible.** The scan mutation was allowing any class from the last two weeks, while the app itself only ever offered the one happening now. Attendance feeds the gym's stats and its "who's drifting" list, so the numbers were open to being wrong. ADR [96](docs/issues/96-one-definition-per-rule.md).
- **A long class that is still running now shows up when you scan.** The lookup only reached three hours back, so a seminar that started this morning was invisible to the scanner while its own check-in window was still open.
- **A map link can no longer hide invisible characters.** It is the one field the gym shows every member as a tappable link, and it was the one field skipping the cleaning step every other text field gets.
- **Two reminder rules with passing tests were never actually used.** They are gone, and the code that really sends reminders is now on the list to be tested.

- **A class further out than a week no longer shows a Book button that fails.** Both apps checked "is it cancelled" and "has it started" themselves and neither knew about the one-week booking limit, so opening a direct link to a class three weeks out offered a button the server then refused. Both ask the same rule now. ADR [95](docs/issues/95-what-belongs-in-domain.md).

- **The dashboard's eight rules can now be tested without rendering the page**, including the one that decides whether the day block shows today or rolls forward to tomorrow. It has seven branches and had no test.
- **Money is formatted one way.** There were three: one on the web, one in the app, and a third inside the dues reminder students actually receive.

## One copy of each query

- **The grace period an owner sets and the rule that enforces it read one number now.** The Payments screen and the booking gate each carried their own default. They agree today, so nothing was broken yet; the next edit to the shared constant would have moved one and not the other, with nothing failing. ADR [94](docs/issues/94-one-copy-of-each-query.md).
- **Cancelling a class is finally tested.** Nothing checked that the booked students actually hear about it. They do, and now a test says so.
- **Switching to an academy you do not belong to answers the same as switching to one that does not exist.** Before, the two answers differed, which told a caller that an academy id was real.
- **Thirteen copies of the roster read, four of the payment settings, five of "this class, not deleted" and two byte-identical booking counters became one each.** No new layer and no behaviour change: the same queries, written once. 617 tests pass.

## The safety pass before the pilot

- **A mutation that fails halfway no longer leaves the first half behind.** The tenant transaction was committing even when the resolver threw, because tRPC reports a failed resolver by returning it rather than raising it. Every two-step mutation was exposed. ADR [13](docs/issues/13-booking-write-atomicity.md) had promised this rollback since session 10.
- **A database error stops talking to the user.** An unhandled server error reached the client carrying Postgres's own words, which name the table, the column and the constraint. In production it now says one plain sentence. Separately, "I paid" was reporting a dropped connection or a permission error as "a payment for this period is already awaiting confirmation", and now only says that when it is true.
- **Faster reminders, dues sweeps and academy switching**, and four screens that would have slowed down for a long-running gym now stop at a fixed number of rows. Migration `0027` adds four indexes, three of them for the nightly sweeps that read across every academy. It is written and still needs applying.
- **Adding a tenant table without row level security is now a failing test**, not something you find out later. ADR [93](docs/issues/93-safety-pass-before-the-pilot.md).

## Identity writes stop fighting the tenant transaction

- **Approving, archiving, restoring or erasing a member, handing out an invite link, and signing in a walk-in each hold one database connection instead of two.** All thirteen ran inside the tenant transaction and then wrote an identity table on the base connection, which the pool quietly absorbed by handing out a second connection and the test database could not absorb at all: 27 tests failed on timeouts and the three suites took eleven minutes. They now run on identity procedures that open no transaction and ask for one only around the part that needs it, keeping each mutation's own ordering. Reaching for the base connection inside a tenant procedure is now a compile error. `pnpm test` is 589 passing in 19 seconds.

## The QR poster pages start drawing before the server wakes up

- **The two pages a new student lands on from a printed QR code now come straight from the cache, not from a server that has to start up first.** Scanning a gym's poster or opening a join link should show something immediately, on gym wifi, on a cold phone. Those pages hold no gym data, so there was nothing worth waiting for.

## The page arrives while the gym data is still loading

- **The web app now draws the page around your data before the data is there.** Until now the server waited for every number on a screen before it sent anything, so the browser sat on a blank page for about seven tenths of a second and then got everything at once. It now sends the page straight away, with the same placeholder shapes you already saw, and each panel fills in as its own answer comes back. The dashboard's heading reaches you in about a tenth of a second instead of seven tenths, and the page is not one byte bigger.

- **Every screen in the web app now loads its data on the server and sends it with the page, instead of the browser asking for it after the page has drawn.** The dashboard used to make eight requests after it appeared; now it makes none. The page costs about 12 kB more to download and saves roughly two thirds of a second of waiting.

The server and your browser would have picked slightly different weeks, and the page would have fetched everything twice. Date ranges are now worked out one agreed way, while what you actually see is still your own local days.

## One place decides how stale a screen may be

- **How long cached data stays fresh is now one table, and both the web app and the phone app read it.** Each client had the same 30 second rule copied into it separately, and two screens overrode it by hand. 30 seconds is right for a class roster someone else can change while you watch it, and pointless for the plan list or your gym's name, which only change when a staff member edits them. Reference data now holds for five minutes, stats for two, the two little counters in the sidebar for one, and everything else keeps 30 seconds.

## Session replay stops riding along on every page

- **The error-recording tool was being downloaded on every screen, including the privacy page, even though it only ever records when something breaks.** It now loads a moment after the page does, which takes 123 kB off every single route and keeps the recording.

## The frontend has numbers now

- **Measured what the web app actually costs before changing it: bundle size for all 18 routes, and what a dashboard open looks like in production.** Two settings that were assumed rather than checked are now confirmed: the server functions really do run in Frankfurt next to the database, and Vercel's Fluid Compute is on. The useful surprise: the dashboard paints about 50 ms after the last query lands, so it is waiting on data, not on code.

Nothing about the rule itself changed.

## Leaving a gym stops meaning one blunt thing

- **"Remove" becomes two actions that mean different things.** **Archive** is the everyday one: the member loses access, their upcoming bookings are cancelled and those seats go back to the class, their dues stop, and nothing else is touched. They move to a new **Archived** tab where one click restores them with their attendance, rank, notes and payment history intact. A student who rejoins with the gym code lands on the same record either way. **Delete permanently** is the other one: it sits behind the row's `⋯` menu, makes you type the member's name, and erases every record the gym holds about that person. It is how an owner answers a delete-my-data request, which the privacy page already promises. Every action on a member row now lives in that one `⋯` menu, so the row itself stays quiet. ADR [84](docs/issues/84-archive-and-erase.md), migration `0026`.
- **Three bugs behind the old Remove are fixed.** The dues reminder kept pushing "your dues are due" at people who had left the gym, every month, forever. Their upcoming bookings were never cancelled, so classes counted seats nobody would use and other students still saw a departed member on the attendee list. And there was no way back: an owner could not undo a removal or even see who had gone.

## The post-login gate stops spinning forever

- **Signing in and landing on "Opening your gym…" forever is fixed.** The web client streamed its tRPC responses, and a streamed response sends its headers before the resolver runs, so the fresh session cookie Better Auth writes when you switch academy never reached the browser. With the five-minute session cookie cache from v4.0, the server then kept answering "no active academy" until that cookie expired, and the gate, which asks once and never retries, sat on a spinner the whole time. The client now uses the buffered link (the same one the phone always used), so the cookie rides the response. Same fix for "Start a gym", joining by link, and renaming yourself, which all re-sign that cookie. ADR [83](docs/issues/83-streamed-responses-drop-set-cookie.md).

## Membership becomes the key to booking — when the owner turns the key

- **The money loop finally has a consequence, and it is opt-in.** Dues existed since v1.3 but nothing happened when a student ignored them. A new **Booking rule** switch on Payments → Bank details (off by default — off means nothing anywhere changes) locks booking for an approved student who has no membership plan or a month unpaid past a **grace window** the owner sets (0–30 days, default 7). The window is one derived clock in `@matops/domain` (`bookingAccess`), consulted by the server guard, the warning strip, and every Book button, so the three can never disagree. ADR [82](docs/issues/82-membership-booking-gate.md), migration `0025`.
- **Nobody is locked without seeing it coming, and nobody is locked for paying.** The S11 strip counts down ("Payment overdue. Booking locks in 3 days.") and goes error-tone only past the window; tapping **I paid** unblocks booking instantly — the owner's confirmation latency is never the student's problem, and a rejected claim re-locks on its own. Flipping the switch on grants every plan-less member the full window (the clock anchors on the later of joining and enforcement), so turning it on never slams a door. Pending members, staff, cancel, and the gym QR check-in are never gated: booking is the lever, the door stays open.
- **Choosing a membership is part of arriving, not a form field.** The one-step join is untouched. A gym with one active plan assigns it automatically at approval; with several, the student picks once on the dues screen (web and phone) with one confirm. Either way the first payment lands on the **1st of next month** — the join month costs nothing in-app, and because the due date anchors on the 1st, the existing roll-forward keeps it there. The owner roster shows a "booking locked" tag so the desk knows who to talk to.
- **The green dues state stops claiming money changed hands.** A student who had just picked a plan saw "€50.00 · Paid" without ever paying a cent, because the status has always derived from the due date, not from a payment. The label is **"Up to date"** now (one shared constant, both clients, plus the O7 grouping header) — true for the fresh member, the postponed member, and the member who actually paid alike.

## The API stops paying for Frankfurt forty times a page

- **"Loading data feels slow" was never about bandwidth.** One Postgres statement costs 45 ms from here to Neon in Frankfurt, and a dashboard load sends about forty of them. Before a resolver reads a single row, each procedure pays 90 ms for the session, 45 ms for the membership and 179 ms to open the tenant transaction. In dev it also slept a random 100-500 ms, once per query, which is create-t3-turbo boilerplate meant to expose waterfalls and instead buried them. That sleep is gone. ADR [81](docs/issues/81-api-latency.md).
- **The session is read from a signed cookie now, not from two rows.** Five minutes of cache, so an authed request costs zero identity queries. The price is written down rather than hidden: a revoked session stays valid for up to five minutes. Approving, suspending and removing a member are unaffected, because the tenant tier still reads the `member` row live on every call.
- **Functions were running in Washington DC against a database in Frankfurt.** `vercel.json` held nothing but a `$schema` key, so Vercel used its `iad1` default and every one of those forty statements crossed the Atlantic twice. Pinned to `fra1`. Inferred from the config, not measured, so the next deploy's `[TRPC]` timing lines are the check.
- **The tenant transaction sets the role and the academy in one statement.** `SET LOCAL ROLE x` is defined as `SET LOCAL role = x`, so the role is a plain setting and goes through `set_config` beside the academy id. One round trip instead of two, and both values are bound parameters now instead of an interpolated identifier. The first test that runs the real `withTenant` came with it — every RLS test until now copied the seam by hand, which is exactly how a change here slips through.
- **The shell's two queries start on the server.** `prefetch()` had been defined and called nowhere, so every byte of data was fetched after hydration. The academy and the membership list now stream down with the HTML, which removes a whole serial wave from the cold open without touching what the loader draws.
- **The cookie cache needed three repairs before it was safe.** A write that changes the `user` or `session` row without going through Better Auth is invisible to a cached session. `createOrganization` is one: it sets the active academy on the session row and never re-signs the cookie, so "Start a gym" would have answered "No active academy selected" for five minutes, which is the whole owner onboarding path. Renaming yourself was the other: the sidebar kept the old name. `refreshSessionCookie` forces the read and rewrites the cookie, and academy create, profile update and join all call it.
- **Left alone on purpose:** ten procedures in one HTTP batch still open ten transactions and pay that 179 ms ten times. Sharing one is the biggest win left and it changes the tenant seam, so it gets its own note rather than a quiet edit.

## The owner rebuilds the schedule, and booking stops at a week

- **Pausing a template left its classes on the calendar forever.** So did changing a template's days or time: the old instants stayed behind as real, bookable classes, so a gym that reorganised its week ended up running two schedules at once. Nothing in the product could remove a generated class. **Rebuild schedule** sits at the foot of Schedule → Templates now, owner only: it throws the forward calendar away and regenerates it from the active templates alone. Before you confirm it names the damage from a live count, "Removes 34 upcoming classes and 12 bookings", the same way the announce button names its reach. ADR [79](docs/issues/79-manual-schedule-rebuild.md).
- **What a rebuild refuses to touch is the part that took the thinking.** A past class carries its attendance on the same row as its booking, so deleting one would erase the history behind training stats, visit counts, drift and rank: the wipe stops at now. A one-off you added by hand for a seminar survives, because no template would ever bring it back. A class you deliberately cancelled at a time the templates still want stays cancelled. What it does take: bookings on the removed classes, and per-instance edits. An owner who retimed one Tuesday gets the template's time back, because "rebuild" means the templates win.
- **Students are not told their booking went.** A deliberate call and the weak point of this slice. The machinery is one call away, so it gets revisited the first time a pilot owner rebuilds a live week.
- **Six months of calendar instead of six weeks.** Saving a template fills the whole window at once, so a gym that edits its templates never runs dry and one that does not still has half a year ahead. Nothing runs on a schedule any more: the daily tick that swept the horizon is gone, the dues tick is untouched, and the cross-academy sweep stays as a tested, callable seam for whenever a scheduler comes back.
- **Booking stopped at a week ahead.** Both schedules only ever showed a rolling seven-day week, so the six-week booking was reachable only through a direct link to a class detail. A hole, not a feature, and a booking that far out is noise because the gym's plans change first. Measured from now rather than midnight, so nothing that is on screen ever refuses to book.

## The gym stops sending email

- **A notice from matops arrived as bare text from a domain nobody recognises.** There are no mail layouts and no templates, so every cancelled class, dues reminder and gym announcement left as an unstyled paragraph, which is what a spam filter and a member both read it as. No gym message is emailed now: the notification center plus the push is the whole delivery, and the center was already the durable copy. Gone with it: `sendEmailBatch` and `BatchEmail` in `packages/notifications`, the `email` half of every message builder in `@matops/domain`, the `email` field on `Delivery` and `emailsFailed` on the dues sweep, the `notification_pref` table with its `pref` / `setPref` procedures and the switch on Profile, and the "Also send as email" tick on the compose box. `sendEmail` stays for the sign-in magic link, its only caller. Migration `0023` no longer creates `notification_pref`.

## Waiting looks like the thing you are waiting for, on both clients

- **Every screen had one loading state, and it was four grey bars.** `SkeletonRows` stood in for a seven-column week grid, a coach card of five numbers, a day rail of classes hanging off a hairline, and a notification feed. All of them jumped into place when the data landed. There is a vocabulary now, and each piece is cut from the component it replaces: the list row is `cardClass()`, the section rule draws `Section`'s real hairlines, the queue placeholder is the O1 strip's own tile geometry, the grid placeholder is the O2 column template and its 64px hour rows. Lines that are structure get drawn for real rather than pulsed, because the border is not the part we are waiting for. ADR [80](docs/issues/80-loading-states.md).
- **Clicking a nav item used to hold the old screen and then swap the page whole.** No route under `(app)/` had a `loading.tsx`. Twelve do, and each one renders the same skeleton the screen itself renders while its query is pending, so the placeholder appears once and is replaced once instead of re-flowing in between.
- **The cold open drew a skeleton of a layout that a new member never reaches.** The shell resolves the academy before rendering anything, and the answer is either the shell or the academy gate, which share no chrome. Both show the **mat loader** instead: the basketweave mark with its seam path split into six planks, each drawing on 90ms after the last in weave order, the two centre seams and then the four short ones. It is how a gym lays mats before class. Nothing new enters the identity, and the label says what is happening ("Opening your academy") rather than "Loading…".
- **A loader that flashes for one frame is worse than no loader.** The mark fades in on a 180ms delay with `backwards` fill, so a boot that resolves faster than that shows nothing at all. Reduced motion stops the weave and leaves the mark whole; every skeleton holds still under it too.
- **Two routes stay deliberately vague, on purpose.** `/` is the owner dashboard or the student week and `/payments` is claims or dues, but `loading.tsx` is a server file that runs before the shell mounts and knows no role. Both draw only what the two versions share, a title over a stack of cards. Drawing an owner's tabs and taking them away from a student would be the worse lie.
- **The phone had no skeleton at all.** One spinner covered every wait, so it sat where a week of classes, a class detail, a dues card, a notification feed and a training card were about to be. Eight screens draw their own shape now, from the same file split the web uses. Two tiers rather than three: Expo Router has no route-level boundary, so a screen's own `isPending` is the only place a placeholder goes.
- **The mark weaves on the phone too**, drawn the way the phone already draws it: positioned Views, no SVG dependency, each seam scaling from the end it starts at on the native driver. The full-screen `Loading` gate renders it, so the auth gate, the academy resolve, the magic link, the invite, the check-in gate and the profile session all took it without a call-site change, and the ones with something to say now say it.
- **One spinner job is left, and the button already had it.** After the pass, the only inline spinner on the phone was the onboarding gym search, sitting above a **Find gym** button that spins for the same fetch. The duplicate went and `InlineLoading` went with it. A spinner is feedback for an action in flight, not a stand-in for content whose shape we know.

## The notification path stops being two paths, and the calendar gets an owner

- **The fan-out was written twice in one wave.** The notification center added `deliverEach` beside `deliver` because the dues sweep gives every member a different message and a cancelled class gives everyone the same one. Both did the same four steps, and the copies had already disagreed: one put a whole class's tokens in a single push call and the other made one call per person; `sentBy` sat on the shared type and was ignored by one of the two. There is one `deliver` now, per recipient, with `each(userIds, msg)` for the five callers that send everyone the same thing. `sendPush` takes addressed messages, so any mix costs one call per 100 tokens instead of one per class or one per person. ADR [78](docs/issues/78-notification-and-horizon-seams.md).
- **The schedule read was doing the horizon's work.** Opening a week selected every stale template and materialized each one, serially, before returning a row, while the sweep that does the same job has a row limit and a time budget because it runs where a long run costs something. The read is a read again. The daily GitHub Actions tick curls `/api/cron/materialize` in the same guarded step as the dues sweep: ADR 46 removed that cron for locking us to Vercel, and the host is GitHub now, so it comes back at no cost. A gym would need 42 days without a template edit **and** a broken workflow to see a short week, and the workflow goes red rather than quiet. The sweep also takes an injected connection now, which is what finally gave it tests.
- **The one membership rule with a security consequence had no unit test.** Stopping an instructor from approving a pending instructor is the same escalation `setRole` is owner-gated against, and it lived as a throw in the router while every other membership rule sits pure and tested in the domain. `canDecideSeat(actor, member)` is next to `canApprove` now.
- **Both clients had copied the same four-line label fallback**, and the rate limiter's IP rule was the one part of it a test could not reach. `notificationKindLabel` comes from the domain and `clientIp` sits with the limiter it feeds.

## A notification center, and a way for the gym to say something

- **A notification used to exist for a few seconds and then not.** A student with push off, or one who reads mail on the laptop they left at home, had no way to learn that Tuesday's class was cancelled, and the product held no record that it had ever told them. Every message now writes a row in a per-academy feed at `/notifications`: cancelled, changed, class reminder, dues, approved, and gym news. The write happens **before** the push and in its own `try`, so a dead Expo token cannot cost the member the message. One row per recipient, which makes the unread count one indexed count and the feed one flat query. Migration `0023`, inside the tenant seam. ADR [77](docs/issues/77-notification-center.md).
- **The gym had no way to say "mats closed Friday".** It did not fit a class edit or a dues reminder, so it happened on WhatsApp with no idea who saw it. An owner **or an instructor** now writes a title and a message, picks everyone / students / coaches, and the button names the reach — `Post to 34` — from the same rule that picks the recipients, so nobody posts blind. Coaches can post because in the pilot gyms the owner is on the mat, and the coach who cancels Tuesday's class is the one who knows it is cancelled — the same reason the member desk moved to staff in ADR 76. Only active members receive one: pending has not been approved, suspended has lost access. The sender gets their own copy, which is the proof it went out. The compose box sits on the feed it writes into rather than on a screen of its own.
- **A post that reaches the whole gym should say who wrote it.** Every announcement copies the sender's display name onto each row it writes (`sent_by`, migration `0024`) and the feed shows it under the message. The name is stored, not the user id: it reads with no join and it keeps the history true when someone is renamed, changes role, or leaves. System messages carry no name, because they are from the system.
- **Opening the center marks it read, and the dots stay for that visit.** The alternative is a tap target on every row and a decision about what "read" means for a row with nothing to open. The badge in the nav counts unread and polls with the rest of the shell.
- **The phone gets the feed, and it does not cost a tab.** A fifth tab would crowd the four jobs the tab bar exists for, for a screen a student opens once a week. There is a **bell in the Schedule and My classes headers** instead: a red dot while anything is unread, and a tap pushes the feed over the tabs the same way the gear opens Settings. The web's mobile top bar gets the same bell and drops Notifications from its bottom tabs; the desktop sidebar keeps the item with its count, where a row costs nothing. A dot, not a number, because a header bell answers "is there anything", not "how many". The bell stays hidden until the membership is active, since the feed is members-only and a pending student would get a 403 out of it. The screen is the web one minus the compose box, and only a class row is tappable: the stored links are web paths and `/payments` has no phone route, so a dues row reads rather than dead-ends.
- **The phone's screens each had their own idea of a header.** Some drew a title with the mark on the right, some drew a title alone, so the new bell hung off a different edge depending on where you were. There is one `AppHeader` now, and it is the bar the web already shows on a phone: mark, academy name, then the icons. `Screen` grew a header slot so the bar runs edge to edge with a hairline under it, and the screen title moved below it into the content, which is where the web keeps it too. Schedule stops using the academy name as its title, because the bar says it.
- **Two of the icons were emoji.** An emoji is someone else's artwork at someone else's weight and colour, and it changes with the OS. The bell and the settings control are now the web sidebar's own glyphs, redrawn with positioned Views at the same stroke weight, the way the tab icons already were. The settings one is two sliders rather than a gear, because that is what the web draws. No SVG dependency for two shapes.
- **A gym-news row looked tappable and did nothing.** An announcement stored `/notifications` as its link, so the row was a link back to the page you were already reading. It points nowhere now, because the row already carries the whole message. The feed also refuses a link to itself, so the rows already written stay honest.
- **The linked feed row rendered as a broken card.** `<a>` is inline, and the row was the one card link in the app that never set a display, so its border split into fragments and the text fell outside it.
- **The daily dues tick now leaves a copy behind, and stops losing mail.** ADR [75](docs/issues/75-daily-cron-on-github-actions.md)'s schedule is unchanged and the class sweep stays off; the sweep writes its inbox row through the same helper as everything else. Email goes out through Resend's batch endpoint, up to 100 distinct messages a request instead of one request per person, because the old fan-out ran into a limit of about two requests a second and `sendEmail` could only log the 429. A gym-wide announcement had the same shape. The claim stamps the period before the send, so a dropped reminder is gone until next month: the sweep now counts what the transport refused and the workflow goes red instead of quiet. Live UI stays parked, the phone app is untouched, and the feed is capped at 50 rows with no pagination on purpose.

## The head coach can run the desk, and the calendar stops going quiet

- **In most gyms the owner is teaching, not at the desk.** Approving a member was owner-only, so at a friend's academy where the owner takes four classes a week, every new student waited for them to open a laptop. `membership.approve`, `reject`, `members` and `memberHistory` are the **staff** tier now: an instructor opens `/members`, clears the queue, sets rank and writes coaching notes. `rank.set` and the notes were already staff and only unreachable because the route was owner-gated. What stays with the owner: invites, drop-in leads, the CSV export, suspend, restore, remove, the student-to-instructor role picker, making a co-owner, and **the coach queue**. An instructor who could set roles could mint instructors and demote every owner but the last one, and `approve` grants the invited role, so clearing a pending **instructor** is the same act by another name. `requireOwnerForCoachSeat` refuses it in both `approve` and `reject`; the Members screen was already hiding those rows, and the screen is not the guard. ADR [76](docs/issues/76-pilot-blockers.md).
- **The coach sees the person, not the money.** `membership.members` returns `dues: null` when the caller is not an owner, so the plan, the price, the next due date and the payment status are blank for an instructor. The field was already nullable and both screens already branched on it, so this is one line and no type change. Contact details stay visible: a coach chasing someone who stopped showing up is a normal gym job.
- **A gym that stops editing its templates used to watch October empty out.** Classes are generated 42 days ahead, only when a template is saved, and there is no scheduler. `healHorizon` now runs on `class.week` and `class.mine` before they read, extending any template whose cursor no longer covers the window being asked for. It reuses `materializeTemplate` on the caller's own tenant transaction, so RLS does the academy filtering and no service connection is opened, and `UNIQUE(template_id, starts_at)` makes two concurrent readers harmless. On a healthy academy the select returns nothing and no write happens. This is ADR 46's own Option B, which it deferred.
- **The join QR goes on a public wall and had no brake.** A drop-in submission is now capped at 5 per 10 minutes per address, an academy or invite lookup at 30 a minute, and magic-link send at 5 per 5 minutes. The last one matters most: Resend is a quota shared by every academy, so one flooder would have broken sign-in for all of them at once. Twenty-five lines in `packages/api/src/rate-limit.ts` and a Better Auth config block, no new dependency. State is per process, so a Fluid-compute scale-out leaks; the upgrade is a table, and it is written down rather than discovered later. The 5,000-key cap clears the whole map when sweeping expired buckets frees nothing, because a flood from rotating addresses leaves every bucket live and the cap would otherwise cap nothing.
- **Sentry was installed on the wizard's defaults.** Full trace sampling, logs on and 10% session replay, against a free plan of 5,000 errors and 50 replays a month. The failure mode is silence, in a pilot whose whole point is seeing what breaks at a gym you are not standing in. Traces and logs off, session replay off, replay on error kept, extension noise ignored, every error still sampled.
- **A stranger handed over their name, phone and email behind one sentence.** A public `/privacy` page says who is responsible, what is stored, who processes it, and how to have it deleted, linked from the drop-in consent line and the join form. It ships with `[ENTITY]`, `[ADDRESS]` and `[CONTACT EMAIL]` **visible on the page**: a half-true privacy notice is worse than an obviously unfinished one, and a placeholder you can see cannot be forgotten. The link sits outside the consent `<label>`, because a link inside a label ticks the box.
- **Two small things that make a remote pilot legible.** A feedback link in the sidebar footer and on Profile, opening an email with the academy, role and screen already filled in. And a three-step checklist where a new owner's dashboard used to say "All clear." over an empty gym. Verified by lint 15/15 and typecheck 17/17; run `pnpm test` for the new `instructor-desk`, `materialize-on-read` and `rate-limit` suites.

## Dues reminders fire on their own, once a day

- **The engine was built and nothing was calling it.** ADR 46 removed both Vercel Cron jobs before the pilot, which also removed the only thing that sent a dues reminder. A gym on manual bank transfer then has one collection method: the owner walking up to people on the mat. `.github/workflows/cron.yml` curls `/api/cron/remind` once a day at **09:00 in Lisbon**, the pilot's time zone, with the `CRON_SECRET` bearer token the route already checks. The scheduler is not the host, so Vercel Cron stays removed and nothing is locked to a vendor. GitHub cron is UTC-only and Portugal moves between UTC+0 and UTC+1, so both hours are scheduled and one guard line keeps whichever tick is 09:00 local; a skipped tick exits 0, so a red run always means the sweep itself failed. ADR [75](docs/issues/75-daily-cron-on-github-actions.md).
- **Daily is set by Neon, not by taste.** Neon Free sleeps after 5 minutes idle and grants ~100 compute-hours a month, so every ping buys at least 5 minutes of compute. A 15-minute cron keeps the database awake permanently, around 730 hours a month, until it hard-suspends. Daily costs about 2.5 hours. Anything sub-hourly needs a paid Neon plan before it needs a better cron.
- **One message per member per billing period.** The sweep stamps `dues_reminder_period` with the `YYYY-MM` of the due date, so a member hears about it once when they are within three days of due, or once when overdue, and a member who stays overdue is never nagged again. That is the whole annoyance budget, and it is enforced in SQL rather than in a habit.
- **The materialization sweep stays unscheduled.** It was the obvious second curl, and it would have done nothing: lazy-on-save fills 42 days on every template edit and `healHorizon` fills the horizon on every schedule read, so a cross-academy sweep only reaches a gym nobody edits and nobody opens. The route stays a dormant, callable seam.
- **Class reminders stay off, on purpose.** They ride the same route, so it passes `leadMinutes: 0`, which makes the claim window empty: no class is claimed and none is stamped, so turning them on later loses nothing. The phone already schedules them on the device (ADR 54), their benefit is fewer no-shows and v1 does not track no-shows, and a daily tick would reach only the classes inside the 2h window and none of the rest. Verified by typecheck 17/17 and lint 15/15; no test changed.

## The owner can export the member roster as CSV

- **The emails were already on screen, one member at a time.** Member detail showed an email with a copy button, and an owner who wanted to mail the whole gym had to open every row. The Members tab now has an **Export CSV** button that downloads the roster: name, email, phone, role, status, joined date, visit count, plan, dues status, next due. It exports what the list is showing, so the search box and the Overdue filter also narrow the file. Spec O4.
- **No new procedure, no new request.** The file is built in the browser from the `membership.members` query the screen already ran, which is `ownerProcedure` and RLS-scoped, so the export cannot reach past the owner's own academy.
- **A name can be a formula.** A member called `=HYPERLINK("http://evil","click")` would run in the owner's spreadsheet, so a field starting with `=`, `+`, `-` or `@` is written with an apostrophe in front. A `+` value made only of digits, spaces and brackets is exempt, because that is a phone number. The CSV rule is `membersCsv` in `@matops/domain` with its own tests, quoting per RFC 4180. The object URL is revoked on a timer rather than in the same tick as the click, because the download is queued and Firefox cancels it otherwise. Verified by typecheck 17/17 and lint 15/15; run `pnpm test` for the new domain cases.

## The web shell owns the academy, the access table, and the booking call

- **Thirteen screens fetched the academy the shell had already resolved.** `AppShell` refuses to render a child until `academy.current` is a real membership, and every child asked again anyway and wrote its own loading / failed / none branches around a value that could not be null. The academy is a **React context** now: `useAcademy()` hands a screen the membership with no branch at all. Nothing changed on screen; thirteen dead loading / failed / none triples did not survive it.
- **Book and cancel were copied into three screens, and two of them disagreed.** The student schedule invalidated the `class` query path; My classes invalidated `class` and `booking`. Nothing said which was right, so a booking made on one screen could leave the other showing stale data. One `useBooking()` hook owns the pair, the invalidation set and the per-row busy flag, the same job `book-control.tsx` does in the phone app.
- **Only the sidebar knew which pages a role has.** ADR 73 fixed `/payments` and left the rest: an instructor who typed `/members` rendered the owner screen and watched its queries get refused. `routes.ts` is now one access table that both the sidebar and the shell read, so that URL says the page is not part of your account and offers the way home. The `ownerProcedure` / `staffProcedure` tiers are still the guard; this only decides what a person is offered.
- **Twenty-four date formatters across fourteen screens became twelve in one file.** `~/lib/format.ts` re-exports the shared `@matops/domain` rules and adds the web's own shapes, the arrangement the Expo app has had since v1.8. Two screens had imported the shared clock and then declared an identical local copy.
- **Three rules that existed once per client moved down to `@matops/domain`.** `dayKey` and `groupByDay` (the local-day bucketing loop, byte-for-byte the same in all three schedule screens) and `PAYMENT_STATUS_LABEL` (the words "Paid" / "Due soon" / "Overdue", written out in both clients). The first two came with tests; the grouping was the only real logic on the student schedule and it sat in the one layer with no test runner. Refactor only: no migration, no procedure, no schema. Verified by typecheck 17/17, lint 15/15, `next build`, and `pnpm test` 456 green. ADR [74](docs/issues/74-web-shell-seams.md).

## The student web app reaches parity with the phone app

- **The pilot runs on the web, and the web student was half a product.** ADR 57 gave them one screen: the seven-day week with Book and Cancel. That was right when the native app was the real client. `pilot-plan.md` moved the pilot to web from day one, so the only client a student has is now the one missing My classes, training stats, class detail, dues, rank and the overdue warning. An owner who set a member's rank or dues had built something the student could not see. Fixed: the student gets the app's four jobs minus Scan — **Schedule** (`/`) · **My classes** (`/training`) · **Dues** (`/payments`) · **Profile** (`/profile`) — plus the class detail screen at `/class/<id>`. ADR [73](docs/issues/73-student-web-parity.md).
- **The shell already had the navigation and was switching it off.** Both nav blocks are wrapped in `items.length > 1`, and a student qualified for exactly one item, so the sidebar and the bottom tab bar were built and hidden. Adding four items turns them on with no new chrome. The pending banner, the avatar link, the theme toggle and sign out already rendered for a student. Owner and instructor navigation is untouched.
- **A student in two gyms had no switcher.** It read `academy.listMine`, which filters by `isWebLensMembership` (owner, instructor, invited instructor), so a student-only user always got an empty list. It reads `academy.memberships` now, the same list the ADR 49 post-login gate offers, so the gate and the switcher finally agree on which academies exist.
- **A student who typed `/payments` got a screen of failed owner queries.** Nav hiding is convenience and the tRPC tier is the guard, which is correct for security and wrong for a person who lands on the URL. `/payments` branches on role now: the O7 screen for an owner, their own dues for everyone else. A **pending** member has no read on `payments.myDues` (it is a `memberProcedure`), so the tab is hidden and the page says dues appear after approval instead of erroring.
- **The overdue strip (S11) is in the shell**, under the pending banner, so it follows a student across every screen and self-clears one refetch after the owner confirms a payment. It carries more weight on the web than on the phone: there is no scheduler (ADR 46) and no on-device reminders (ADR 54), so it is the only thing that can chase a payment.
- **No backend work, and one pure rule moved.** Every procedure was already built and already on the right tier, and every rule the screens call (`splitMyClasses`, `nextClass`, `trainingStats`, `paymentStatus`, `formatRank`, `visibleAttendees`, `capacityDisplay`) is the same one the Expo app calls, so the two clients cannot drift. `lastClassLabel` was the exception, copied in the Expo card; it moves to `@matops/domain` with a test and both clients call it. What stays app-only is the in-app QR **scan**: the poster encodes a web page, so scanning it with a phone's camera app already lands on `/checkin/<academyId>` and works. Verified by typecheck 17/17, lint 15/15 and the first `next build` since v2.4.

## Sentry error tracking on the web app

- **We had no way to know the app broke.** Vercel keeps function logs, but nobody reads logs on a schedule, a browser-side crash never reaches them, and a minified stack trace names nothing. The pilot puts real academies on the app with no support channel, so a crash would have surfaced as an owner quietly giving up. `@sentry/nextjs` now reports from all three Next runtimes: server and edge via `src/instrumentation.ts`, the browser via `src/instrumentation-client.ts`, and a crash that escapes the root layout via a new `global-error.tsx`. `onRequestError` is wired, so a throw inside a tRPC procedure arrives with its request instead of as an anonymous 500. `withSentryConfig` uploads source maps at build time.
- **The wizard's own output broke the build and had to be fixed.** It appended CommonJS (`require`, `module.exports`) to `next.config.js`, which is ESM in this repo. Node refused the file outright (`ERR_AMBIGUOUS_MODULE_SYNTAX`) and `next dev` and `next build` both failed. Under that sat a second bug: the file never assigns `module.exports`, so the wrapper would have wrapped an empty object and dropped `transpilePackages`. It also tripped the repo's ban on bare `process.env` and the Turbo undeclared-env-var rule. Fixed, with `NEXT_RUNTIME` and `SENTRY_AUTH_TOKEN` added to `globalPassThroughEnv`.
- **The default setup reported far less than it looked like.** Three gaps, found by reading the error paths rather than trusting the wizard. (a) **The whole tRPC API was invisible**: `fetchRequestHandler` converts every procedure error into a JSON response and never rethrows, so `onRequestError` never fired for any of it. The existing `onError` hook now reports, filtered to `INTERNAL_SERVER_ERROR` only (an `UNAUTHORIZED` or a rejected form is normal behavior, not a defect, and reporting those burns the quota on noise), unwrapping `error.cause` so grouping is per real failure, and tagging the procedure path plus the caller's user and `academyId` so an error names which academy hit it. (b) **Sign-in failed silently**: both magic-link server actions ended in a bare `catch {}` that returned a generic error, so a broken send would have lost the user with no signal. Both capture now. (c) **No `error.tsx` existed at all**, and a boundary swallows the error before any global handler sees it, so one root boundary now captures and shows the `digest` as a reference. The cron routes need nothing: they propagate, so `onRequestError` already covers them. Verified by throwing on both paths and confirming the events in the dashboard, then reverting. A `captureException` event is **handled**, so tRPC errors never carry Sentry's `Unhandled` flag: an alert rule on `error.unhandled:true` would skip the whole API, so filter on the `trpcPath` tag.
- **`packages/api`'s deliberate error-swallowing is left alone.** `notify.ts` and two routers swallow on purpose (a failed push must not fail the mutation) and that is correct. The package is also consumed by the Expo app, so importing `@sentry/nextjs` there would break the mobile build. Reporting them needs a reporter injected through the tRPC context, which is more than a pilot justifies.
- **The DSN stays hardcoded** (it is public and ships in the bundle anyway), tracing samples every request while the pilot is small, and the build token lives in the gitignored `.env.sentry-build-plugin`, which must also be set as `SENTRY_AUTH_TOKEN` in Vercel or source maps silently stop uploading. Mobile reports nothing yet. Roadmap 5.2 is half done: rate limiting is untouched. ADR [72](docs/issues/72-sentry-error-tracking.md).

## A pinned map link for the academy

- **The address link was a guess.** ADR 68 rendered the gym's address as a Google Maps **search**, and a search lands on the wrong building for ordinary gyms: a unit in a mall, a basement, an industrial park, a building with no street number. The owner types the address once and never taps it. The person who taps it is a new student, on their first visit.
- **You cannot validate an address without a geocoder,** and a geocoder means an API key and billing for one field. So Settings does two cheaper things. While editing, a **Check the pin ↗** link opens exactly what the student's tap will open, so the owner sees the real result before saving. And an optional **Map link** field takes a share link from Google Maps, Apple Maps, OpenStreetMap, or Waze, which the student's tap prefers over the search. A share link came out of a map, so it always resolves — plus codes, mall units, and places with no address at all.
- **Only map hosts are accepted, on purpose.** The value is rendered as a tappable link for every member of the gym, so an open URL field would let one careless owner send the whole roster to a phishing page. The list is the narrow one: `maps.google.com`, `maps.app.goo.gl`, `maps.apple.com`, `openstreetmap.org`, `osm.org`, `waze.com`, plus `google.com` **only under `/maps`**. Bare `google.com` and `goo.gl` are out, because `/url?q=` redirects anywhere, a `goo.gl` shortlink resolves to anything, and `sites.google.com` hosts user-written pages — an allowlist that admits a redirector allows the phishing page it was built to stop. The host comes from `new URL()`, not a pattern: a browser reads the backslash in `https://evil.example.com\.google.com/` as a path separator, so any regex that lets `\` into the host group reads the wrong host. `@matops/validators` gets the `dom` lib for the `URL` type, the way `@matops/ui` already does. The field stays disabled until an address is typed: students tap the address **text**, so a pin with nothing to read shows up nowhere.
- **On mobile, the fallback stopped going to the browser.** With no pinned link, tapping the address now opens the phone's own map app (`maps://` on iOS, `geo:` on Android) instead of an https Google URL, which only reached the Maps app when it happened to be installed. Migration `0022`. ADR [71](docs/issues/71-academy-map-link.md).

## Check in by scanning, from inside the app

- **The Scan tab.** Checking in as a member cost four taps and a trip through the browser: open the camera app, tap the banner, wait for the poster's public page, tap "Open the app to check in", and hope a custom-scheme link hands off (it is the same hand-off that already fails for Google sign-in). The student app now scans the poster itself, from a fourth tab that does one job. Tabs are **Schedule · My classes · Scan · Profile**, which reverses ADR 45's three-tab rule on purpose.
- **The scanner is the phone's own.** `CameraView.launchScanner()` from `expo-camera` presents `DataScannerViewController` on iOS 16+ and the Google code scanner on Android, so no camera preview, framing overlay, or torch of ours ships untested. A phone that cannot present one (iOS 15, Android with no Play Services) is told to use its camera app on the poster, which is the old flow. Camera permission is asked on the first tap of the tab, never at launch, and a permanent refusal gets a link to system settings instead of a screen that does nothing.
- **Nothing about the QR changed.** Same poster, same `https://…/checkin/<academyId>`, same public drop-in page for a first-time visitor, same "Open the app" deep link, same `checkin.today` / `checkin.checkIn`, same `checkin/[academyId]` screen doing book + attend. The one new piece of logic is `parseCheckInLink`, a pure parser that returns the academy id or `null` (invite posters included), written as a regex because Hermes does not parse custom schemes.
- **`expo-camera` is a native module,** so the dev client must be rebuilt, and **a camera never works in the iOS Simulator**: the scan itself needs a real phone and is queued in `docs/mobile-device-test.md`. ADR [70](docs/issues/70-in-app-qr-scanner.md).

## The academy gets a time zone, an address, and a delete

- **The academy now has a time zone.** Nothing stored one before: each class template carried its own, defaulted from the **browser** of whoever created it into a free-text box, and the gym's zone was guessed by counting which zone its templates used most — so a typo silently mis-timed every class, a coach on a travelling laptop split the schedule, and a brand-new gym had its weeks and stats drawn in **UTC**. Settings now picks it from a real list. A **new** template inherits it; ones that already exist keep their own, because re-timing them would cancel classes students had booked. Settings names any template that disagrees, and the template form offers a one-click move.
- **The academy now has an address.** Free text with an **Open in Maps** link. Students see it on the mobile Profile tab and on the join confirm step, so a mistyped digit that lands on a real gym is caught before joining.
- **An owner can delete the academy.** They must type `delete <academy name>` — the phrase names the gym, so it cannot be done to the wrong one by habit. It is a **soft** delete: every member loses it at once and lands back on the post-login gate, its 6-digit code is never reissued to another gym, and the rows survive so a mistake is reversible in the database. No restore screen, no export, no hard purge in v1.
- **Migration `0021`** adds `time_zone`, `address` and `deleted_at` to `organization` (all nullable, applied to Neon). Soft delete is filtered at seven academy-resolution paths, `getMembership` being the load-bearing one — a deleted gym fails every tenant procedure at the middleware.
- **New tier `ownerIdentityProcedure`:** owner authorization, **no** tenant transaction, for the two writes that touch the `organization` row. `0020` revoked `matops_app`'s `UPDATE` there, so they need the base connection, and taking it from inside `withTenant` holds two pool connections (ADR 66) — on PGlite that is a hang, and it cost six timed-out router tests to find. `getAcademyCode` / `findAcademyByCode` / `getAcademyPublic` gained the `exec` parameter they were still missing. `pnpm test`: **416 tests green** across five suites. ADR [68](docs/issues/68-academy-time-zone-address-and-delete.md).

## Identity reads stop taking a second database connection

- **Running the router suite found a deadlock, and it was the code, not the tests.** Fourteen router call sites read `member` / `user` through `ctx.baseDb` from **inside** the tenant transaction. `withTenant` already holds one pool connection for the whole request, so each of those reads checked out a **second** one and held both: with `pool.max` at the node-postgres default of 10, ten concurrent requests can each hold a transaction while each waits for a connection nobody can release. It is the same shape as the problem ADR 60 fixed for notification sends, left behind in the read path.
- **On PGlite it was certain rather than probabilistic**, because there is only one connection. `member-scope` (12 tests), `payments` (7) and the new `coach-stats` (8) all timed out at 30s each, and a deadlocked transaction never releases, so every later test in the file timed out too. The api suite took **366 seconds** to report four failing files. Two of them predate this wave, so the suite had been red since ADR 60 added it.
- **Identity reads inside a tenant resolver now run on `ctx.db`.** Those tables carry no RLS policy and `matops_app` keeps SELECT on them (migration `0020` revokes only writes), so the rows are identical — and `template.list` and `class.week` have always left-joined `user` on the tenant handle. `architecture.md` had claimed identity "can never be read through the tenant transaction", which was the belief that produced the pattern; `0020`'s own comment says the opposite. The read helpers take `DbReader = DbExec | TenantTx` so each call site picks, and the base connection is now for pre-transaction lookups and identity **writes** only.
- **`listMembershipsForUser` gained the required `exec` that ADR 60 missed.** It was the last helper closing over the module singleton: in a test run it reached the real pool and died with `getaddrinfo ENOTFOUND api-test-dummy`, and in production it bypassed the single injection point the seam exists to provide.
- **Four permission tests were asserting the wrong thing** and are fixed in the tests, which is where that defect lived: they matched `/FORBIDDEN/i` against the error **message**, so guards that were refusing correctly with "Owner only" still failed. `rejectionCode()` asserts the tRPC error code instead, which is the contract; a message is user-facing copy and free to change. **Result: 62 api tests green in 18s, 410 across all five suites.** ADR [66](docs/issues/66-identity-reads-run-on-the-tenant-transaction.md).

## Coaches get a screen, and the column it reads finally means something

- **"Who taught this class" was never actually recorded.** `class.instructor_id` and `class_template.instructor_id` have been `NOT NULL` since Phase 2, but both create paths fell back to `input.instructorId ?? ctx.session.user.id`, no client ever sent the field, and the web never called `class.update` at all. The column held whoever typed the template in. A per-coach screen built on it would have reported confident wrong numbers, so the wave fixes attribution first: a **coach picker** on the recurring template form and the one-off class form, fed by a new staff-tier `membership.instructors`. It is deliberately not the owner-only `membership.staff`, which carries emails and returns `member.id` where this needs `user.id`.
- **The column had no foreign key and no RLS of its own.** Nothing stopped a staff member writing an arbitrary user id into the field every coach figure reads. `requireInstructor` now asserts the target is an active owner or instructor of the caller's academy, on all four write paths. It runs only when the value changes, so an unchanged edit never fails on a coach who has since left.
- **A cover night can be recorded, and correcting last Tuesday pushes nothing.** `class.setInstructor` sits behind a narrow schema, because reusing `UpdateClassSchema` would let a stale form overwrite the title, capacity and time as a side effect of naming a coach. Any staff member may set the coach on a class that has not started; only an owner may change one that already happened, since that rewrites reported history. `classChange` now takes `now` and returns `historyOnly`, so a past-class correction no longer sends "your class changed" to everyone who booked it. `now` is required rather than optional, so the compiler forced the existing call site to decide instead of letting the old behavior survive by default.
- **O10 Coaches shows workload and coverage, and refuses to be a leaderboard.** Classes led, time on the mat, students taught, average headcount, and how much of it got marked, over this month, last month, or 90 days. Cards are name-ordered and are never sorted by headcount: a 07:00 class fills less than a 19:00 one whoever teaches it, so ranking coaches that way measures the timeslot. An owner sees everyone; an instructor sees their own card only. Averages divide by **marked** classes, and the card says in words when some are unmarked, so a forgotten register does not read as a weak coach. Drop-ins are not counted as visits, so O10 always agrees with O5 and the roster visit count.
- **One planned slice was deleted instead of shipped.** The O1 "N classes were never marked" nudge turned out to already exist: `needsAttendance` has driven the dashboard "Classes to mark" queue since v1.2, and its rule is better (it skips classes nobody booked, which can never be cleared, and partly-marked ones, and stays inside the markable window). The duplicate rule written for this wave was removed rather than left as a second, worse definition of "unmarked". `localDate` also moved out of `stats.ts` into a shared `local-date.ts` so both stat engines draw academy-zone boundaries with one helper. **No migration.** ADR [62](docs/issues/62-coach-workload-and-coverage.md).

## The instructor invite link grants the instructor role

- **An invited coach could end up a student.** Opening the instructor link while already a member of that gym hit the idempotent branch of `createPendingMembership`, which kept the **old** `invitedRole`: a pending student stayed a pending student, and approval granted "student". A pending member now takes the **new** link's role (newest link wins), so the instructor link is approved as an instructor.
- **Joining twice no longer claims a fake success.** An already-**active** member who opens an invite link was told "You're in, pending approval" while nothing changed. The row is left alone (a link must not re-role an approved member) and the join screen says so.
- **Coach requests moved to the Coaches screen.** A pending **instructor** was queued next to pending students in Members, where approving them silently granted schedule and attendance tools. They now wait at the top of **Coaches** (owner-only) with Approve / Decline, the Members requests tab is the student queue, and the O1 dashboard carries "Pending approvals" and "Coach requests" as separate items pointing at the two screens. One pure rule (`isPendingCoach`) splits the list in all three places.
- **Owners can set a member's role.** The member detail Overview has a student ↔ instructor picker (`membership.setRole`, owner-only), the missing repair for anyone who joined by academy code or by the student link. It replaces `membership.demote`: same locked, never-ownerless transaction, now used for both directions, and `InviteRoleSchema` keeps it from ever granting `owner`; Coaches → Staff calls it for "step down to instructor". ADR [64](docs/issues/64-invite-role-and-coach-queue.md).

## The frontend review is closed out (ADR 59)

- **A crafted join link could rewrite a stranger's profile with no click.** `/join/[token]` auto-fired `membership.join` from the carried `?p=` blob, and `joinPending` writes name and phone to the **global** `user` row. ## Backend review fixes: a test seam for the API, and the bugs it uncovered (ADR 60)

- **`packages/api` had 17k lines of orchestration and no tests.** It has them now: `packages/api/test` drives the real routers through `appRouter.createCaller`, over the real `enforceTenant` middleware and the real SQL, against PGlite. That took **one** injection point instead of three: `ctx.baseDb`. Every base-connection helper (`withTenant`, `getMembership`, `getMemberById`, `getMemberIdForUser`, `listMembersOf`) now takes `exec` as a **required** parameter, because the `exec = db` defaults were the whole problem. A call site that forgot one kept working against the production pool with no compile error, so a test could pass while the code under it never touched the test database.
- **Three critical bugs.** The auth error hook logged the whole Better Auth context, which carries the **app secret** as a top-level property, so every bad request to `/api/auth/*` wrote it to the production log (**rotate the secret on deploy**). A template **timing** edit hard-DELETEd future classes, but `class_participation` and `drop_in` both reference `class.id` with `ON DELETE no action`, so one student booking meant the owner could never move that template again. It now **cancels and revives**, so an occurrence the new timing still covers comes back with its bookings intact and one it drops stays visible as cancelled instead of vanishing. And every recipient of a class email went in one Resend `to:` field, showing each booked student every other student's address; sends are one per recipient now.

The reminder sweep had always got this right, so the two disagreed. `template.update` fell back to `ctx.session.user.id`, and since no client sends `instructorId` on an edit, every edit **reassigned the template to whoever opened the form**. Both reminder sweeps stamp "reminded" before sending and then sent serially, so members past the timeout were marked and never messaged; they fan out now. Notifications moved to a new **`ctx.afterCommit`** hook so a network call no longer holds the tenant transaction open, and `academyName` catches its own errors so `notify.ts` keeps the promise its own doc makes. The drop-in upsert overwrote `class_id` and bumped `visit_count` on any repeat submit, erasing the visit a returning lead was recorded against.
- **Two migrations, both small.** `0019` indexes `member (organization_id, user_id)`, because `getMembership` runs on every authenticated request against a table that had only its primary key. `0020` revokes `matops_app`'s INSERT/UPDATE/DELETE on `user` / `organization` / `member` and **all** access to `session` / `account` / `verification` / `invitation` / `academy_invite`: migration `0001` granted DML on ALL tables so new tenant tables would be covered without editing it, and the side effect was full write access to the identity tables, none of which carry a policy.
- **Deletions.** `referral.dashboard` returned `metrics`, `referrerSummaries`, `plans`, `currentMonth`, `timeZone` and a per-student `plan` / `dues` that nothing has read since ADR 56 moved the aggregation to the screen. ## Every input is cleaned before it is measured (ADR 58)

- **The schemas bounded length and never looked at content.** `z.string().trim()` keeps zero-width spaces, control characters and the Unicode bidi overrides that make a stored name render backwards, so a member could be saved under a name that reads one way in the roster and another way anywhere else. Phone was worse: `min(3).max(30)` with no charset accepted `<script>alert(1)</script>` and `call me` in the field the gym dials. `@matops/validators` now exports `lineText` / `blockText` / `NameSchema` / `PhoneSchema` / `EmailSchema` / `HttpUrlSchema` / `IdSchema`, and every field in the package composes from them. Each one caps the raw string _before_ it transforms it, so a megabyte of junk is thrown out before any regex touches it, and the real bounds are then measured on the cleaned value. Loose on format, strict on charset: `+380 50 999 88 77` and `Renée O'Neill-Souza` still pass.
- **Three input surfaces had no schema at all.** The sign-in server actions validated nothing, and a server action is a public endpoint: whatever the client binds can be posted directly with any value. `sendMagicLinkAction` handed an unbounded string to Better Auth as an email, and `callbackURL` arrived unchecked, which is an open redirect that also lands attacker text inside the sign-in email we send. Both now parse with the same schemas tRPC uses, and `callbackURL` is pinned to a same-site relative path (`//evil.com` reads as a URL to a browser, so a leading-slash test alone is not enough). The join page parses the base64url profile carried in `?p=` instead of trusting it, and the magic-link URL is escaped before it goes into an `href`.
- **Three smaller holes closed on the way past.** `proofUrl` used bare `z.url()`, which accepts `javascript:` and `data:`. Nothing renders it as a link today, so this was a trap for whoever adds the "view receipt" button. `UpdateClassSchema.timeZone` skipped the `isValidTimeZone` refine that both create schemas apply, so a bogus zone reached the DST math on the reschedule path. The schedule week window had no span limit, so one request could ask for a decade of classes; it is capped at 400 days.
- **No API, domain, or migration change**, and no client type changed (every transform is `string` to `string`). Stored rows are not re-validated, so a phone already saved as `"123"` only fails on its next edit. `@matops/validators` now runs vitest like `@matops/domain` does: `pnpm -F @matops/validators test`, 18 tests. ADR [58](docs/issues/58-input-validation-and-sanitization.md). Green: typecheck 17/17 · lint 15/15. **Rate limiting is explicitly not in this pass.** The public procedures and the magic-link action are still unthrottled, which is Phase 5 work.
